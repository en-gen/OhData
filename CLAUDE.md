## Build & Test

All commands run from the repo root.

```bash
# Build everything
dotnet build src/OhData.sln

# Run all tests - all eight test projects in one pass. CI (.github/workflows/ci.yml) runs the
# same eight one project at a time, so this is the local equivalent, not a superset.
dotnet test src/OhData.sln

# Run the main suite only - the fast inner loop (~80% of the tests; no companion-package,
# client, or test-bench coverage)
dotnet test src/OhData.AspNetCore.Tests/OhData.AspNetCore.Tests.csproj

# Run a single test by name
dotnet test src/OhData.AspNetCore.Tests/OhData.AspNetCore.Tests.csproj --filter "FullyQualifiedName~GetAll_Returns200"

# Run a single test class
dotnet test src/OhData.AspNetCore.Tests/OhData.AspNetCore.Tests.csproj --filter "ClassName~EndpointMappingTests"

# Run the test bench (interactive demo, browse to http://localhost:5099/scalar)
dotnet run --project src/OhData.TestBench.AspNetCore
```

## Architecture

OhData is a convention-based OData server framework that turns declarative profile classes into registered ASP.NET Core minimal API endpoints at startup - no controllers required.

### The core flow

```
EntitySetProfile<TKey, TModel>
    └─► IVisitModelBuilder       → builds the OData EDM model (Microsoft.OData.ModelBuilder)
    └─► IEntitySetEndpointSource → runtime-typed interface for OhDataEndpointFactory to call handlers

AddOhData(builder => builder.AddEntitySetProfile<MyProfile>())
    └─► OhDataBuilder collects profile types + prefix
    └─► Profiles registered as AddScoped (not singleton) to support DbContext injection
    └─► OhDataRegistration (keyed singleton) built lazily:
          temporary scope resolves each profile → visits EDM, collects IEntitySetEndpointSource
    └─► Stored in DI as AddKeyedSingleton<OhDataRegistration>(name)

app.MapOhData()  →  returns RouteGroupBuilder
    └─► OhDataEndpointFactory.MapAll()
        ├─► routes.MapGroup(prefix)  ← outer group for the whole OData surface
        │      endpoint filters: OData-Version response header, OData-MaxVersion request-header
        │      validation (§8.2.7 - rejects < 4.0 with 400), $format/Accept negotiation
        ├─► GET  ""              → service document
        ├─► GET  /$metadata      → CSDL XML
        ├─► startup validation: throws InvalidOperationException if a structural property name
        │      collides with an entity-level bound function name, if a navigation property's
        │      `post` handler collides with an entity-level bound action name (both POST
        │      /{EntitySet}({key})/{segment}), if a navigation ROUTE's name collides with an
        │      entity-level bound function name (#416/#492, both GET
        │      /{EntitySet}({key})/{segment}), if an unbound function/action name collides with
        │      another unbound operation or with an entity set's own collection GET/POST route,
        │      or if a BindEntityFunction/BindEntityAction handler's first parameter isn't the
        │      entity key (TKey), or (#313, opted-in registrations only) if an entity-level bound
        │      function name collides with a PAGEABLE navigation's continuation route, or (#465)
        │      if a Priority-1 profile (GetODataQueryable) also sets a Search handler, or (#468)
        │      if EdmValidator.Validate rejects the built EDM as invalid CSDL, or (#486) if
        │      .RequireResource() covers a KEY-BASED route the profile registers (Read/Update/
        │      Delete, the navigation-POST create route, or an entity-bound operation) while
        │      GetById is null. Every one of these compares OrdinalIgnoreCase (#492).
        │      Earlier still, at BIND time (the profile constructor / AddFunction / AddAction):
        │      duplicate bound-operation names within one kind and binding level (#492), and the
        │      three operation-signature rules of #498 - a void-returning FUNCTION, a non-trailing
        │      or nullable CancellationToken, and an IResult return type - and (#487) a
        │      .RequireResource() on an UNBOUND operation's authorize lambda, which has no {key}
        │      entity to evaluate against.
        └─► per profile (only routes whose handler delegate is non-null):
            GET    /{EntitySet}              (GetAll or GetQueryable)
            GET    /{EntitySet}/$count
            GET    /{EntitySet}({key})       (GetById)
            POST   /{EntitySet}              (Post - deep insert / @odata.bind handling, see AllowDeepWrites below)
            PUT    /{EntitySet}({key})       (Put - nested navs stripped unless AllowDeepWrites)
            PATCH  /{EntitySet}({key})       (Patch - nested navs never enter the Delta unless AllowDeepWrites)
            DELETE /{EntitySet}({key})       (Delete - returns Task<bool>; false→404 or 204, per IdempotentDelete)
            GET    /{EntitySet}({key})/{nav}          (navigation routes with handler, batch or per-entity)
            GET    /{EntitySet}({key})/{nav}?$skip=N  (#313: bare-$expand continuation, delegate-LESS navs only,
                                                       registered only when ExpandPagingEnabled && MaxExpandTop is set)
            GET    /{EntitySet}({key})/{nav}/$count   (collection-navigation count)
            GET/POST/PUT/DELETE /{EntitySet}({key})/{nav}/$ref  (addRef/setRef/removeRef)
            POST   /{EntitySet}({key})/{nav}          (HasMany `post` - create a related entity)
            GET    /{EntitySet}({key})/{Property}          (structural property read - rides GetById, gated by PropertyAccessEnabled)
            GET    /{EntitySet}({key})/{Property}/$value   (raw property value, same gate)
            PUT/PATCH/DELETE /{EntitySet}({key})/{Property} (structural property write - rides Patch, gated by PropertyAccessEnabled)
            GET    /{EntitySet}/{FunctionName}  (bound functions, query-string params)
            POST   /{EntitySet}/{ActionName}    (bound actions, JSON body params)
            Each route gets .WithTags(EntitySetName) and .RequireAuthorization(...) if configured.
```

### Key design decisions

**Handler presence drives route registration.** If a profile sets `GetAll = null` (the default), no `GET /EntitySet` route is registered.

**Two paths for GET collection.**
- `GetQueryable` (IQueryable): framework constructs `ODataQueryOptions<TModel>` and applies `$filter`/`$orderby`/`$skip`/`$top` via `ApplyTo(IQueryable)`, enabling EF Core SQL pushdown. `$select` is applied via JsonNode post-processing to keep camelCase consistent. **Its delegate is `Func<IQueryable<TModel>>` — alone among the eight it carries no `OhDataResult`, no `Task` and no `CancellationToken` (#653).** It is the only handler return the framework further COMPOSES before executing, so at the moment it returns there is no result to report on, no I/O has happened for a `Task` to represent, and nothing has started that a token could cancel — the framework owns the execution, and cancellation with it. Each removal is measured, not argued: of the assignments in this repo, **0 of 164 were `async`**, **0 returned a rejection**, and **0 of 263 referenced the token they were handed** (158 discarded it as `_`, 105 named it `ct` and never used it). Rejecting a collection read goes through `ConfigureExceptions`. `GetODataQueryable` (Priority-1) keeps `Task<ODataQueryResult<TModel>>`, correctly — there the profile HAS applied the options and may have executed a count, so it holds a result plus paging metadata.
- `GetAll` (IEnumerable): simple enumeration - developer chose the opt-in simple path. It is **not** "no query options applied": `$top`/`$skip` are applied in-memory as `Skip()`/`Take()` after materialization, and `$select`/`$expand` in the JSON pass. But `$filter` and `$orderby` are **rejected with `501` (`UnsupportedQueryOption`)** - *"This resource does not support $filter or $orderby. Configure GetQueryable to enable server-side query processing."* - not silently ignored. `501` and not `400` because the refusal is flag-INDEPENDENT: this path has no `IQueryable`, `FilterEnabled = true` changes nothing here, and the remedy is a different handler - §9.3.1's *"functionality not implemented"*. Same for the `/$count` route's GetAll-backed `$filter` fallback. Pinned by `OpenTypeLimitationTests.OpenTypeDynamicKeyReadPathTests`, which asserts it for a declared property as well as a dynamic key, since the rejection is about the path having no `IQueryable`, not about what is being filtered.
- `IODataEntitySetEndpointSource` (Priority 1): profile receives `ODataQueryOptions` directly and applies them itself.

**`$select` uses JsonNode post-processing** (not `ISelectExpandWrapper`) to avoid the PascalCase/camelCase inconsistency that `ApplyTo` with `$select` introduces.

**A malformed query option returns 400, whatever it throws (#402).** Two separate guards, with deliberately different catch widths. (1) `ODataQueryOptions` construction runs inside `TryBuildQueryOptions`, whose try contains *nothing but* the construction and whose catch is **everything except `OperationCanceledException`** → `400` `InvalidQueryOption`. (2) The surrounding whole-handler try on each read route keeps its narrow `catch (Microsoft.OData.ODataException)`, which covers the deferred, parse-on-first-access failures (most malformed values parse lazily) and `ValidatePropertyAllowlists`. The widths are not interchangeable: the whole-handler try also contains `InvokeGetQueryableAsync`, so broadening the catch *there* would relabel a database outage as a client error and destroy the guarantee below from the other direction; conversely narrowing (1) to a type list is what produced the bug. **Measured** construction-time throw set (`QueryOptionConstructionFaultTests` probes every system query option the framework accepts with empty, malformed and hostile values, and pins the result as a live regression): `ODataException` for an empty `$filter`/`$orderby`/`$top`/`$skip`/`$count`/`$search`/`$apply`/`$compute`, and **`System.ArgumentException`** for `$skiptoken=` or a valueless `$skiptoken` — from `SkipTokenQueryOption`'s own ctor, which is what escaped to the group filter as a client-reachable 500. That set is a measurement, not a contract: `BuildQueryOptions` news up one option object per recognized `$`-option, each with its own argument validation, and nothing in `Microsoft.AspNetCore.OData`'s contract restricts those to `ODataException`. `ODataException` keeps its message pass-through (so the eight empty-value cases stay byte-identical); anything else gets a generic message and the real exception is logged at `Warning`. **All five** construction sites are guarded — Priority-1 collection, `GetQueryable` collection, `GetAll` collection, `/$count`, and `GetById` (which builds options only when `$select`/`$expand` is present). Since #359 the `/$count` and `GetById` guards are no longer *reachable* via `$skiptoken` — neither route implements it, so it is refused by name (now `501`) before construction; the guard itself is unchanged and is still exercised end-to-end by the three collection routes. **`QueryOptionConstructionFaultTests.EmptySkipToken_ReturnsODataErrorEnvelope` is the sharpest statement of the 501/400 taxonomy in the suite**: one option, one empty value, five routes — `400 InvalidQueryOption` on the three that implement it (a malformed VALUE for supported functionality) beside `501 UnsupportedQueryOption` on the two that do not (unimplemented FUNCTIONALITY).

**`ODataQueryContext` is per request; `ODataQuerySettings` is not (#426).** `TryBuildQueryOptions` takes the `IEdmModel` and builds a fresh `ODataQueryContext` on every call — deliberately, so no caller can hand it a shared one. It used to be built once per entity set at startup and captured by all five read-route closures under the comment *"Both are read-only after construction"*, which was **false and production-reachable**: `ODataQueryOptions`' constructor WRITES `context.RequestContainer` and `context.Request` on every use (`ODataQueryOptions.cs:76-80`, opening with `Contract.Assert(context.RequestContainer == null)` — Microsoft stating the type is per-request), and `Initialize` reads `context.Request` back off that shared field (`:1165`) rather than using the constructor's own `request` parameter. Two concurrent requests therefore race on `Request`, and the loser dereferences another request's `HttpContext` — concurrently with its owner, or after it has been recycled — which tears the `FeatureReferences` read and throws `NullReferenceException` out of `DefaultHttpContext.get_RequestServices`. #402's deliberately broad catch then relabels it `400 InvalidQueryOption`, so a **valid** request, including one with no query string at all, intermittently 400s under load. **Measured**: 16-89 failures per 32,000 constructions across 16 threads sharing one context, 0 per 32,000 with a fresh context (`QueryContextPerRequestTests`, which also pins the invariant deterministically — two sequential requests must not be handed the same instance — via the Priority-1 profile seam, the only place the framework's context is observable). #384's intermittent `ConcurrencyTests` failure was this, not a flaky test. **The `(IEdmModel, IEdmType, ODataPath)` overload is NOT the cheap path** it looks like: it leaves `ElementClrType` null and `ODataQueryOptions<TEntity>`'s constructor throws on that (`FilterQueryOption.ApplyTo` too), and it skips only the CLR-to-EDM lookup, not `GetNavigationSource`'s linear scan of every entity set — which both overloads run on every construction. **Cost** (`QueryContextConstructionBenchmarks`): +263 to +362 ns and +448 B per options build, i.e. under 1% of the time and 2.7% of the allocation of the cheapest measured end-to-end read route (GetById, 36.8 us / 15.95 KB) and under 0.05% / 0.4% of a collection page. The `ODataQuerySettings` instances cached on the same startup line **stay** cached: verified against the `Microsoft.AspNetCore.OData` source, every consumer those instances reach (`FilterQueryOption`/`OrderByQueryOption`/`SkipQueryOption`/`TopQueryOption.ApplyTo`, and `QueryBinderContext`, which holds one behind a get-only property) only reads them, and every settings-mutating path there mutates an instance it created itself — `ODataQueryOptions.ApplyTo` opens with `querySettings = Context.UpdateQuerySettings(querySettings, query)`, which `CopyFrom`s into a new object. Safe because of how it is used, not because the type is immutable; it is a mutable POCO.

**Query-capability flags and property allowlists are enforced at runtime, not just advertised.** `FilterEnabled`/`OrderByEnabled`/`SelectEnabled`/`ExpandEnabled`/`CountEnabled` (all default `false`) and `FilterProperties`/`OrderByProperties`/`SelectProperties`/`ExpandProperties` gate the `GetQueryable`, `GetAll`, and Priority-1 collection paths, plus `$select`/`$expand` on `GetById`: a disabled option in the request returns `400` (`UnsupportedQueryOption`) - `400` and not the `501` of the sigil rule below, because the service implements the option and this resource switched it off, which is not §9.3.1's *"functionality not implemented"*; a non-allowlisted property returns `400` (`InvalidQueryOption`) via the EDM's model-bound `NotFilterable`/`NotSortable`/`NotSelectable`/`NotExpandable` annotations. `$expand` is also implemented on the single-entity `GetById` route (reuses the collection expansion pipeline). Every read route additionally rejects any `$`-prefixed option it does not implement at all - see the next paragraph, which supersedes the closed name lists this sentence used to enumerate. **One exception to the allowlists, and it is not a bug in the enforcement (#401): a dynamic (open-type) property is not in the EDM, so it carries no `NotFilterable`/`NotSortable`/`NotSelectable` annotation and is not gated at all** - `Microsoft.AspNetCore.OData` behaves identically. Do not read the allowlists as a security boundary over a model with an open complex type; `docs/open-types.md` has the measured matrix, and `OpenTypeAllowlistBypassTests` pins it. **The allowlists are scoped per CLR model type, not per entity set, and that is now enforced at startup (#458).** `EntitySetProfile.VisitModelBuilder` applies them via `entityType.Filter/OrderBy/Select/Expand`, and `entityType` is the shared per-CLR-type `EntityTypeConfiguration<TModel>`; `ModelBoundQuerySettings` is keyed by type while OhData's configuration surface is keyed by entity set, so two profiles over one model type **unioned** their allowlists and each set silently accepted what the other allowed - **measured for all four options, in both registration orders**, with responses byte-identical to the correctly-gated case. **Per-entity-set model-bound settings do not exist**: in `Microsoft.OData.ModelBuilder` 2.x the fluent `Filter`/`OrderBy`/`Select`/`Expand`/`Count`/`Page` API is declared only on `StructuralTypeConfiguration<T>` and `PropertyConfiguration` (`EntitySetConfiguration`/`NavigationSourceConfiguration` expose bindings, `EntityType`, `Name`, `ClrType`, `VocabularyTermConfigurations` and nothing else), every `GetModelBoundQuerySettings` overload in `Microsoft.AspNetCore.OData` resolves off an `IEdmStructuredType` (optionally plus an `IEdmProperty`) rather than a navigation source, and the capability-vocabulary annotations that *can* sit on an entity set are never read by the query validators - metadata-only advertisement. So `ModelBoundAllowlists.Validate` throws `InvalidOperationException` from `MapOhData()` on a divergent pair, mirroring `IgnoredPropertyJsonOptions.BuildIgnoredPropertyMap`'s `Ignore()` check. It compares the **literal arrays handed to the model builder** - recorded at the four call sites, post EDM-name resolution and post navigation merge - because that array *is* the shared state; re-deriving from the raw profile allowlists would both miss and invent divergences. Not a conflict: two unset (permissive) allowlists, a sibling whose capability flag is off (it makes no call, and its own requests die at the flag gate), an `AdvancedConfigure` override (ejects before the call sites), or a separate registration (its own `ODataConventionModelBuilder`). `SiblingEntitySetAllowlistTests` pins all of it, including that `WidgetProfile`/`QueryableWidgetProfile` still co-register.

**An unrecognized or unimplemented `$`-prefixed option is REFUSED with `501` on every read route, by the sigil rather than by a name list (#359/#380/#353).** Part 1 §11.2.5 - *"If a data service does not support a system query option, it MUST fail any request that contains the unsupported option"* - Minimal item 7. Three separate closed lists used to answer this and between them left most of the surface unexamined: four names on the collection GETs (`$apply`/`$compute`/`$index`/`$deltatoken`), seven on the navigation route, and **nothing at all** on `GetById`, on `/{Set}/$count`, or on the navigation `/$count`. **Measured on `3781681`**: `?$unknown`, `?$slect`, `?$fliter`, `?$expandx` and a top-level `?$levels` were all `200` on every collection route - and echoed verbatim into the `@odata.nextLink` the server itself generated; `GET /Set(1)?$filter=…` was `200` with the entity and the filter dropped (a client reasonably concludes it was applied); `GET /Set/$count?$search=alpha` was `200` with the **unfiltered** total while the sibling collection route honoured the same option. **`FindUnsupportedSystemQueryOption` is the one matcher**, consulted by sixteen route shapes - the three collection GETs, `/{Set}/$count`, `GetById`, **both branches** of the navigation route, its `/$count`, the #313 continuation (whose own inline `$`-sigil loop was the precedent and which now shares this one instead of carrying a copy, #467's "one site, N consumers" rule), the six operation routes (four bound, two unbound), and (#560) the two structural-property READ routes. Three wordings ride on it and only three: the generic *"The query option '$x' is not supported."* - **byte-identical to the message the four names have carried since 1.0.0**, because generalising a rule must not re-word the cases it already covered - and the navigation route's two, one per branch, each naming what that branch actually accepts.

**`501` OR `400`: `501` IS "CAN'T", `400` IS "WON'T".** An earlier revision of this change answered `400` everywhere, reasoning from §11.2.5's status advice being a SHOULD. That reading does not survive two other clauses: **§9.3.1** is a MUST - *"If the client requests functionality not implemented by the OData Service, the service MUST respond with 501 Not Implemented and the response body SHOULD describe the functionality not implemented"* - and **§13.1.1 item 7** puts that same `501` inside the **Minimal Conformance MUST list**, which this project claims. So every sigil refusal is `501`, and `400` now means one specific thing. **The test is mechanical: could any setting on the profile make this same request succeed on this same route? Yes -> `400` ("won't"). No -> `501` ("can't").** `501`: an unrecognized `$`-name; `$apply`/`$compute`/`$index`/`$deltatoken` (implemented nowhere); an option implemented on OTHER routes but not the one addressed; and the two flag-INDEPENDENT structural refusals (`GetAll`'s `$filter`/`$orderby`, and the `/$count` GetAll fallback's `$filter`), which no profile setting turns on. `400`: a capability flag left false, a property allowlist rejection, `$search` on a route that HAS a `$search` leg but no configured handler, everything #402 owns (a malformed or empty option VALUE), and an out-of-range value (`MaxTop`, `MaxExpandTop`). **`$search` splits on that test and is the worked example**: no `Search` handler is `400` on the collection GETs (the route invokes one when configured) and `501` on `/$count`/`GetById` (no `$search` leg exists there at all). **A consequence worth stating so nobody "fixes" it: the SAME option can be `501` on one entity set and `400` on another**, decided by which read handler the profile supplies - `$filter` is `501` on a `GetAll`-backed set (no `IQueryable`, so the framework CANNOT filter it under any configuration) and `400` on a `GetQueryable`-backed set with `FilterEnabled = false` (it can, and the adopter chose not to expose it). Correct rather than inconsistent: conformance is per-RESOURCE, and the two answers tell a client genuinely different things - *"no configuration of this endpoint will ever do that"* versus *"this endpoint could, and is not offering it"*. **BREAKING, and the largest wire change on the branch**: `$apply`/`$compute`/`$index`/`$deltatoken` answered `400 UnsupportedQueryOption` from 1.0.0 through 1.6.0 and answer `501` now. The error CODE and the message BYTES are deliberately unchanged on every route (§9.3.1's *"body SHOULD describe"* is already satisfied by text naming the option), so a client matching on the envelope keeps working and only status-code branching moves - `ErrorEnvelopeFidelityTests` pins those bytes across the change. One condition still produces one envelope; what moved is which envelope, not how many.

**The navigation route is ONE template with TWO handlers, and gating them with one set was a defect of exactly the kind #380 names.** `GET /{Set}({key})/{Nav}` is mapped once and branches on `NavigationRouteDefinition.IsCollection`. Every option it applies is applied inside the collection branch - `$select` in `BuildNavEnvelope`, `$orderby`/`$skip`/`$top`/`$count` in the branch body - while the single-valued branch (`HasOptional`/`HasRequired`) returns `ODataEntityNode(...)` and reads nothing off the query string. **Measured**: `?$select=Name` served the full entity, `?$top=1`/`?$orderby=Name`/`?$count=true` were `200` and ignored, i.e. #380's own sentence - *"known, implemented-elsewhere options being silently dropped on a route that does not implement them"* - one route over, and `GET /Set(1)?$orderby=X` a `400` beside `GET /Set(1)/Owner?$orderby=X` a `200`. `s_navSingleImplementedOptions` is `$format` alone. Refused rather than taught `$select`: this rule is about refusing what is not implemented, and `$select` there needs the projection, the allowlist validation and the `@odata.context` projection suffix `ODataEntityResult` carries and `ODataEntityNode` does not. The set is chosen from the **startup-captured** `navIsCollection`, so the message describes the branch the request will actually reach.

**The operation routes carry #359's `@odata.nextLink` half, and nothing else did.** `TryApplyOperationCollectionPaging` calls `BuildNextPageLinkWithSkip`, which copies the **whole** incoming query string, and #357/#543 gave that route a `nextLink` in this same release while it had no option gate at all. **Measured** on `MaxTop = 2`: `GET /odata/SqOps/TopRated?$unknown=evil` -> `200` with `"@odata.nextLink": ".../TopRated?%24unknown=evil&%24skip=2"`, and `?$apply=...` -> `200` + `nextLink` where the sibling collection route says `400` - byte for byte #359's evidence block. `s_boundOperationImplementedOptions` is `$top`/`$skip`/`$format`; `s_unboundOperationImplementedOptions` is `$format` alone (no collection branch, no `MaxTop` bound, no continuation there). **`$top`/`$skip` are listed UNCONDITIONALLY**, not derived from `BoundOperationDefinition.ReturnType` the way `AddBoundOperationPagingMetadata`'s `TopSkipSupported` is, and the asymmetry is the point: the ceiling is applied in the RUNTIME collection branch (#357 decision 2 - a `Task<object>` handler returning a `List<TModel>` must not be a way around it), so such a route really can emit a `$skip=N` link, and deriving the set from the declared type would make the server refuse a link it had just issued. Where the result is not a collection they are accepted no-ops - the same ANSWER the two `/$count` routes give them, reached by a different road (there §11.2.9 requires them to be present and ignored; here they are real on the collection shape and the declared type cannot tell the route which shape it will get). An operation's own parameters are non-`$` keys and are never examined. The gate runs **before** parameter binding and before the handler delegate, so a refused ACTION provably mutates nothing.

**Three properties of the rule, each of which would be a defect if changed.** (1) **The sigil, not a name list.** Part 2 §5.2 reserves `$` for system options, so a non-`$` key is a *custom* option and is untouched (`ohdata-skiptoken`, #360's continuation offset, is deliberately spelled without one), and a `@`-prefixed parameter alias (§5.3) likewise. A `$`-name is refused whether or not any OData version defines it: fail-closed, so a future system option cannot quietly start being dropped. (2) **`OrdinalIgnoreCase`, which is ALIGNMENT and not leniency.** `ODataQueryOptions.IsSystemQueryOption` lowercases the name before comparing whenever the URI resolver enables case-insensitivity, which is the default (`ODataQueryOptions.cs:283` for the comment, `:284-287` for the branch it guards, `:289-290` for the lowercasing), so `$Select`/`$TOP` are applied today and stay applied. #359 reported *"`$Select` is applied while `$slect` is ignored and neither is rejected"* as one inconsistency; it is resolved by rejecting `$slect`, **never** by starting to reject `$Select`. The change *is* a deliberate divergence from MS in the other direction - its own `BuildQueryOptions` carries `default: // we don't throw if we can't recognize the query` (`:1061`) - and §11.2.5's MUST is what outweighs `feedback_align_with_msodata_conventions` here. MS's `IsSystemQueryOption` (`:172-198`) recognizes **thirteen** names and `$index` is **not** among them, so nothing here should read as "MS knows `$index`"; it is refused by the sigil like `$unknown`. **This `OrdinalIgnoreCase` is itself a behaviour change on one route**: the #313 continuation's own loop compared `Ordinal`, so `$SKIP`/`$FORMAT` were `400` there and are honoured now - the only direction in which this change makes the server more accepting, pinned by `MixedCaseSkipAndFormat_AreHonoured_NotRejected`. (3) **The set is per route and the sets differ** - and on ONE route it is per PROFILE (#475): the Priority-1 collection GET hands the whole `ODataQueryOptions` to the profile, so the framework cannot know which options are honoured and asks instead (`HonouredQueryOptions`, defaulting to what `ApplyTo` applies). That default excludes `$search`, because `SearchQueryOption.ApplyTo` returns the query untouched without an `ISearchBinder` (*"If the developer doesn't provide the search binder, let's ignore the $search clause"*) - so a P1 profile that merely calls `ApplyTo` used to answer `200` with the FULL collection to a client that asked for a subset, undetectably (an unfiltered result is indistinguishable from a search matching everything). §11.2.5's MUST outweighs aligning with MS here, exactly as it did for the sigil rule itself. The rest of the sentence still holds: `$filter` is implemented on a collection GET and meaningless on `GetById`; `$skiptoken` is honoured on the `GetQueryable` path and was never read on `GetAll` (#201 continues that one with `$skip`), so it is accepted on one and refused on the other. A recognized-but-not-implemented-here name and an unrecognized one share **one** code, because the client's remedy is identical; a second code would distinguish nothing actionable.

**`$format` is in every set and must stay there** - not a data option: §11.2.10 negotiation is implemented once on the group filter wrapping the whole surface, never reaches a route handler, and cannot change a row; an unsupported *value* is still rejected there. **A `/$count` route's implemented set is decided by §11.2.9, which partitions the system query options into exactly two classes and specifies the answer for each.** Verbatim: the count MUST be *"of items matching the request after applying any `$filter` or `$search`"*, and *"MUST NOT be affected by `$top`, `$skip`, `$orderby`, or `$expand`"*. So: an option that AFFECTS the count (`$filter`, `$search`) is applied where the route can and **refused** where it cannot - ignoring one would answer a wrong number under a `200`, which is #353's defect; an option the clause says MUST NOT affect it (`$top`/`$skip`/`$orderby`/`$expand`) is **accepted and IGNORED**, because under §13.1.1 item 7's disjunction (*"either follow the specification or return 501 ... for any unsupported functionality"*) ignoring it IS following the specification; anything outside the clause (`$apply`, `$compute`, `$index`, `$deltatoken`, `$skiptoken`, `$count`, any unrecognized `$`-name) is refused as everywhere else. `s_countRouteImplementedOptions` is therefore `$filter` + `$top`/`$skip`/`$orderby`/`$expand`/`$select` + `$format`; `s_navCountImplementedOptions` is the same **minus `$filter`**, because that handler invokes the navigation delegate and counts the result, so it can apply neither `$filter` nor `$search` and refuses both. **A previous revision refused all five of `$top`/`$skip`/`$orderby`/`$select`/`$expand` here, asserting in the code that §11.2.9 "mandates nothing either way". The clause had not been consulted; it names four of those five.** That refusal was reverted before shipping - the options behave exactly as they did from 1.0.0 through 1.6.0 and no wire change reached a release. **`$select` is accepted-and-ignored by ruling**: §11.2.9's MUST-NOT sentence does not name it, but the positive half is exhaustive about what moves the number (*"items matching the request"*), and `$select` changes an item's SHAPE, never its membership - the body is a bare `text/plain` scalar besides. Refusing it alone among the five options a grid URL carries would be the unprincipled split the revert removed. **`$format` is accepted-and-ignored by ruling too, and it is the OPPOSITE error, so the array says so**: §11.2.9 states content negotiation *"is not allowed"* on this segment, so the entry cannot mean "negotiated here" as it does everywhere else - it means "not refused". Refusing it was rejected on three grounds - the clause binds the CLIENT and prescribes no server response; `$format` IS implemented service-wide, so `501` would be false while the `400` arm needs a capability flag this condition has none of; and the group filter already answers `400 UnsupportedFormat` for a non-JSON `$format` BEFORE the route runs, so refusing here would give one disallowed option two envelopes (`$format=xml` -> `400`, `$format=json` -> `501`). **`Accept: application/xml` used to `406` here and does NOT any more (#580)**, reversing the ruling this sentence carried - *"§11.2.9 forbids the CLIENT to negotiate, not the server to decline a media type the client refused (RFC 9110 §12.5.1)"*. Defensible in isolation, but it was never checked against `Microsoft.AspNetCore.OData`, which settles it the other way: `ODataCountMediaTypeMapping` matches every `/$count` path at quality **1** and `ODataOutputFormatter.CanWriteResult` then OVERRIDES the content type (*"If a media mapping was found, use that and override the value specified by the controller"*), so MS never negotiates on this segment and never `406`s. §11.2.9 is the SPECIFIC rule over minimal item 5.1's general *"MUST conform to the semantics [of] Accept ... or fail the request"*, and this is the direction that un-breaks a working client rather than breaking one. `$format` moves with it - the clause names both in one sentence, so refusing one while ignoring the other would give a single disallowed act two answers; `$format=xml` on `/$count` was `400 UnsupportedFormat` and is now `200 text/plain`. The negotiation filter skips the segment entirely rather than widening its producible list, so nothing else changes: an ordinary read still `406`s a client that refuses JSON. **This AGREES with `Microsoft.AspNetCore.OData`, and the agreement is load-bearing**: verified against the vendored source at `a05e1ad0` (9.5.0-7), `ODataQueryOptions`' constructor synthesises `Count = "true"` for any path ending in `/$count` (`ODataQueryOptions.cs:1072-1084`), so `ApplyTo`'s `Request.IsCountRequest()` early return (`:425-429`) always fires - before the `$orderby`/`$skip`/`$top` block and before `SelectExpand` - and MS ignores all five. **`Microsoft.OData.Client` DEPENDS on it**: it translates `LongCount()` by appending `/$count` to the query string it has ALREADY built and strips nothing, so `q.OrderBy(...).LongCount()`, `q.Take(n).LongCount()` and `q.Skip(n).LongCount()` all send the option along - measured against 8.4.4, and refusing them broke standard pagination for the industry-standard OData client rather than merely a hand-built grid URL. `MsODataClientIntegrationTests`' `Count_*` cases pin every one of those shapes through the real client, which is the coverage whose absence let the narrowing pass a full green suite. The bound-OPERATION routes reach the same accepted-no-op answer for `$top`/`$skip` by a different road: there the option really can be real on the collection shape and the route cannot know at startup which shape a `Task<object>` handler will return, so refusing them would refuse a link the server itself issued. **`OhDataQueryOptionsMetadata.TopSkipSupported` stays `false` on the entity-set `/$count`** - the field means "this route HONOURS this option", and §11.2.9 requires the opposite, so documenting a parameter that provably cannot change the response would be the advertise-vs-serve mismatch #467 exists to remove; the nav `/$count` carries no `OhDataQueryOptionsMetadata` at all. **`GetById`'s zero-cost no-option path is intact**: the check reads query-string KEYS only - no parsing, no `ODataQueryOptions` - and returns on `Request.Query.Count == 0` before touching anything, so a request with no query string allocates nothing new on the hottest read route. **#359's nextLink half needed no separate fix on the routes that were already gated, and needed exactly the operation gate on the ones that were not** - see the operation paragraph above; on a gated route, once the option is refused no link is built at all (`Collection_UnrecognizedOption_IsNeverEchoedIntoANextLink`, against a control on the same fixture that does emit one). Riding along, **two routes changed error CODE AND STATUS**: `GET /{Set}({key})?$select=…&$skiptoken=` and `GET /{Set}/$count?$skiptoken=` answered `400 InvalidQueryOption` from #402's construction guard and now answer `501 UnsupportedQueryOption`, because neither implements `$skiptoken` and it is refused by name before any option object is built - strictly better, since the old message implied a non-empty value would have worked. #402's guarantee is untouched and still exercised end-to-end on the three collection routes. **Deliberate residuals, three of them.** (1) The structural-property WRITE routes (`PUT`/`PATCH`/`DELETE /{Set}({key})/{Prop}`), the service document and `$metadata` still ignore every query option - measured, `GET /odata?$unknown=1` -> `200` - and none of them generates a link, so none carries #359's echo. `docs/query-options.md` names them so its table is not read as the whole URL surface. The writes are ungated *consistently with the entity writes* (`PUT`/`PATCH`/`DELETE /{Set}({key})`, also ungated), so no two routes over one resource disagree. **The property READS were in this list and are not any more (#560)**: they were the one residual that produced exactly the split this rule exists to remove - `GET /Widgets(1)?$filter=…` -> `501` beside `GET /Widgets(1)/Name?$filter=…` -> `200` with the filter dropped, measured on both the `/{Prop}` and `/{Prop}/$value` routes for every option probed. Their set is `$format` alone: the handler goes from the property accessor straight to the envelope and reads no option, so `$select`/`$expand` are refused there although `GetById` implements them - the `s_navSingleImplementedOptions` situation exactly, one route over. The gate runs **before** the `/$value` complex-property `400`, so the answer does not depend on which property was addressed. (2) The `GetAll` route answers `InvalidQueryOption` rather than `UnsupportedQueryOption` for an *empty-valued* unimplemented option (`?$skiptoken=`) because `TryBuildQueryOptions` runs before the gate there - a pre-existing asymmetry `$apply=` has had since #196, not one this change introduced. (3) **The one thing that WAS honoured before and is refused now**: a Priority-1 profile reading a `$`-prefixed option of its own off `options.Request.Query` (a shape #465's note endorses) never sees the request. Remedy is to spell it without the `$`, which Part 2 §5.2 requires of a custom query option anyway. `UnrecognizedSystemQueryOptionTests` pins every gated route in both directions, and `BareExpandContinuationFailClosedTests.MixedCaseSkipAndFormat_AreHonoured_NotRejected` pins the one acceptance widening.

**A provider fault is classified by WHEN it was raised, not by what it was (#494).** The three `$expand`-pushdown execution sites (the count-carrier materialization, the #305 Include fallback, and the ordinary pushed-query materialization) wrapped a whole `ToArray()` in `catch (ex is InvalidOperationException or NotSupportedException or ODataException)` and answered `400 InvalidQueryOption` - *"could not be translated by the underlying data provider"* - logging the real exception at **`Debug`**. The rationale, recorded in those comments **and pinned by `ExpandPushdownExceptionClassificationTests`**, was that a real infrastructure fault could only arrive as a `DbException` subclass or a `TimeoutException`. **That taxonomy is false**, and the counterexamples are the ones that matter under load: SqlClient reports connection-pool exhaustion as a plain `InvalidOperationException` (*"Timeout expired … max pool size was reached"*) from `SqlConnection.Open`, raised at enumeration inside those exact `try` blocks; **`ObjectDisposedException` derives from `InvalidOperationException`**, so a disposed `DbContext` matched; and EF's *"a second operation was started on this context instance"* is one too. Under any of them an `$expand` request answered **`400` - telling client retry logic not to retry** - while the same request without `$expand` correctly `500`d, and at `Debug` the operator saw a spike of client errors and no server-side signal at all. **The type cannot separate the populations, so it is no longer asked to.** `TranslateThenMaterialize` splits the provider's **translation** phase from its **materialization** phase: `IQueryable<T>.GetEnumerator()` is what compiles the query (`EntityQueryProvider.Execute`) and the connection is not opened until the first `MoveNext()`. **Verified** on EF Core 10 / .NET 10.0.11 against SQLite - an untranslatable `Where` throws `InvalidOperationException` out of `GetEnumerator()`, enumerator never created. Only the translation window (the query **factory** too, so `ApplyIncludeFallback`'s reflective `Include` construction stays a 400 - it deliberately unwraps its own `TargetInvocationException` so the real type reaches the classifier) yields the 400, now logged at **`Warning`** to match `TryBuildQueryOptions`/`BadKeyError`; everything from the first row onward propagates untouched to the group filter's logged 500. `ObjectDisposedException` is excluded from the translation window as well - *"the object is gone"* is never a statement about the client's query. A provider that translated lazily inside `MoveNext` would surface translation failures as 500 rather than 400: loud either way, never a false *"retry is pointless"*, and EF Core does not do it. **The expression-*construction*-time catch in `TryBuildProjectionInit` keeps its type list** and is not an inconsistency: no database I/O happens inside it, so there is no materialization phase to separate translation from. The pinning test's expectation was **inverted, not deleted** - its injection point (`ReaderExecuting`) was always the materialization phase, which is exactly what made the suite assert the defect as correct behaviour - and the "IOE ⇒ 400" branch is now covered by a **real** EF translation failure (`MlAuthorUntranslatableProfile`, a client-side method in a `Where` over the existing `MlAuthor` fixture) instead of an injected one.

**Unhandled handler exceptions get the OData error envelope, not an empty 500.** A group-level endpoint filter (registered alongside the `OData-Version`/`OData-MaxVersion` filters in `OhDataEndpointFactory.MapAll`) catches any exception a handler throws - as opposed to an `ODataError` result a handler deliberately returns - and converts it into `500` + `{"error":{"code":"InternalServerError",...}}`, logging the real exception (never leaking its message/stack trace to the client). Two exclusions: startup-time validation exceptions (`MapOhData()` throws those once, before any request is served), and **a cancellation on a request the client actually aborted** - left to ASP.NET Core's own client-disconnect handling, because there is no response left to write.

**It is NOT the outermost group filter, and the comment that said so was false (#496 finding 3).** The #200 observability filter is added first and therefore wraps it, so the guarantee register's *"Registered as the outermost group filter (added first)"* was wrong on both halves. What the filter really covers is every route handler plus every filter registered **after** it - the #203 body-limit filter, the `$format`/`Accept` filter, the `OData-MaxVersion` filter. What escapes it: an exception raised in the observability filter's own body (`DescribeOhDataEndpoint`, activity/tag setup, the instrument calls) or in its `Response.OnCompleted` callback. That is **accepted rather than closed**: making the claim true means putting the exception filter outermost, which moves its `LogError` outside the request's `Activity` and loses trace correlation on the single most important log line the framework emits - a worse trade for framework-only code that does no I/O and runs no user code. Riding along, **the `OData-Version: 4.0` header moved to the outermost filter** (#496 finding 2): it was written by the `$format`/`Accept` filter, fourth of five, so the #203 `Content-Length` fast-reject `413` - registered third - short-circuited above it and shipped with no `OData-Version` at all (measured), which §8.1.5 requires on every response. Its placement in the first-registered filter is load-bearing; `Issue496ErrorHandlingTests` pins it from the outside by asserting the header on that 413.

**A read route's narrow catches used to claim USER code's exceptions, and now cannot (#496 finding 4).** Two clauses, one shape, both wider than the condition their message describes. (1) Every keyed route wraps its whole body in `catch (FormatException) -> BadKeyError`, so a handler throwing `FormatException` from its own code (a downstream parse, a `decimal.Parse` on a CSV column) was answered `400 "Invalid key format for <set>: '<key>'"` for a request whose key had parsed one line earlier. Fixed **structurally**: `ODataKeyParser.Parse` has exactly one throw site and it now raises `ODataKeyFormatException : FormatException`, which is the only thing the eighteen clauses catch. (2) Every read route's `catch (Microsoft.OData.ODataException)` answers `400 InvalidQueryOption` with `ex.Message` **verbatim** - a targeted bypass of the no-disclosure rule for one exception type - and that try also encloses handler invocation, so a handler proxying a downstream OData service turned a dependency fault into a client-blamed 400 carrying its own message. That catch **cannot** be narrowed by scope: `Microsoft.AspNetCore.OData` parses most option values lazily, and the framework itself deliberately THROWS `ODataException` from inside `ApplyCollectionPipelineAsync` (`NestedWindowRejection`, `EnsureWithinExpandCeiling`) precisely because these clauses convert it to a 400. So the marking goes on **user code**, not on the framework's option-touching calls - the direction matters, because enumerating framework calls fails toward turning a legitimate 400 into a 500 (a missed one), while marking user code fails toward the status quo (a missed seam behaves as before). `AsHandlerFault` wraps the seam in `HandlerFaultException`; the group filter unwraps it for the log. It takes the already-started `Task` rather than a `Func` so nothing is allocated on the hottest routes, which is safe only because every `Invoke*` member returns a Task that already carries a synchronously-thrown exception - for seven of them because they are `async` methods, which capture a throwing lambda into the returned Task. **Two members have had to earn that property explicitly.** `InvokeDeleteAsync` was a plain forwarder until #581 made it `async`; a synchronously-throwing `Delete` escaped while the arguments were still being evaluated, before any wrapper around the call could see it (measured: #581's mapping fired on all seven other seams and not on `Delete`). `InvokeGetQueryableAsync` is **not** `async` since #653 - its delegate is synchronous, so there is nothing to await - and it therefore wraps the invocation in `try`/`catch` returning `Task.FromException`. **Measured which consequence that prevents rather than assuming it**: with a plain forwarder the generic 500 envelope still appears (the throw is inside the route handler, so the group filter catches it), and what breaks is `WithExceptionMapping`, which never sees the exception - so a `ConfigureExceptions` rule that should answer `403` answers `500`. Since `ConfigureExceptions` is #653's documented replacement for returning a rejection from that seam, that is the regression `Issue653SyncGetQueryableTests` pins. Both fixture shapes are in the suite, so the invariant is pinned rather than assumed. Marked seams: the five read routes' `InvokeGetODataQueryableAsync`/`InvokeGetQueryableAsync`/`InvokeGetAllAsync`/`InvokeSearchAsync`/`InvokeGetByIdAsync`, `GetById`'s ETag selector, `ApplyCollectionPipelineAsync`'s whole ETag stage (one try per page, not one closure per row), and `ExpandLevelAsync`'s `Handler`/`BatchHandler` calls. **Deliberate residual**: the *enumeration* of a deferred `IQueryable` a handler returned runs later, inside `EvaluateQueryWithArithmeticFaultGuard`, and is not marked - user LINQ raising `ODataException` from a provider callback would still be a 400.

**A `Post` handler returning `null` is a logged 500, not a 400 (#496 finding 1).** It answered `400 {"code":"BadRequest","message":"Post handler returned null."}` - a server-side contract violation reported as a client error, with the server's own handler named back to the client, and the only 4xx null policy in the framework (`GetAll` -> 200 with an empty collection, `GetById`/`PUT`/`PATCH` -> 404, a bound operation -> 204). It throws now, which is the same invariant-assertion shape `DeltaFactory` uses for a `false` from `TrySetPropertyValue`: after the framework's own checks a null here means the handler broke its contract, so the group filter's logged 500 is the correct and only honest answer. A profile that means to reject a create deliberately has to do it BEFORE the handler - `Post` is typed `Task<TModel?>`, as is every other entity-set handler delegate, so it cannot return an `IResult` and there is no "return an `ODataError` from the handler" idiom here. Use a `Create` authorization rule, `RequestBodyNullabilityValidationEnabled`, or throw (the same 500).

**That second exclusion is a statement about the REQUEST, not about the exception type (#493).** The filter condition used to be `ex is not OperationCanceledException` alone, so the whole OCE family escaped whether or not anything had been aborted - and `TaskCanceledException` is what `HttpClient` throws on **its own timeout**, i.e. a server-side dependency fault wearing cancellation's clothes. Blast radius: every handler that awaits `HttpClient`, a database driver, or any API using linked or internal tokens. **Measured** on the pre-fix tree, a `GetAll` throwing `TaskCanceledException` on a request that was never aborted: HTTP `500` with an **empty body**, no envelope, and **no OhData log at all** - only Kestrel's - which is exactly the failure mode this filter exists to eliminate, on arguably the most common outbound-dependency failure there is. The condition now also asks `ctx.HttpContext.RequestAborted.IsCancellationRequested`, and `TryBuildQueryOptions`' catch got the same refinement (lower stakes - no handler runs inside its try - but the asymmetry would invite the bug back). `CancellationTests` still pins the genuine-abort path unchanged; `ErrorEnvelopeFidelityTests` pins the new one. Until this fix the sentence above ("catches any exception a handler throws") was simply false for that family.

**That filter only covers what runs *inside* the pipeline, so nothing may defer serialization (#396).** A minimal-API `IResult` is executed by `RequestDelegateFactory` **after** the endpoint-filter chain has unwound, so a fault while the result executes is outside the filter's `try` — and the status line and headers are already committed. Measured on the pre-fix tree: a bound function whose result faults during serialization logged `Request finished … - 200` and shipped a truncated body, with nothing logged. That is worse than an envelope-less 500 — a success status with a malformed body defeats client-side error handling completely — and it is generic to any throwing converter, cyclic graph, or faulting getter. The invariant is therefore **every route materializes its response body before returning**: most already did, because they build a `JsonObject`/`JsonArray` in the handler (`SerializeBounded` / `ODataEntityNode` / `ApplyCollectionPipelineAsync` / `BuildNavEnvelope`), so all user code runs where the filter can see it and executing a materialized `JsonNode` afterwards cannot re-enter it. The four routes that handed a **raw CLR graph** to `Results.Json` now go through `PreRenderedJson`, which serializes to UTF-8 bytes in the handler and returns a `Utf8JsonHttpResult` that only writes: the two unbound function/action results, `WrapBoundOpResult`'s final branch (a non-`TModel`, non-Edm-primitive DTO — its other two branches emit a materialized `JsonArray` or an Edm primitive), and the structural-property read envelope (whose `value` is a complex property's whole sub-graph). Byte-identical by construction — same declared `TValue`, so the same `JsonTypeInfo` resolves; do **not** "simplify" those call sites to pass `object`. `Content-Length` is now explicit. **Measured cost** (`OperationResultBufferingBenchmarks`, against a free `Stream.Null` write): a small DTO — the common shape — gets *faster* (0.74×, the async state machine dominates a tiny payload); 189 KB costs +18%, 9.4 MB +74%, all of it the extra full-payload `byte[]`. A pooled `Utf8JsonWriter` beats every arm (0.66×/0.97×/1.43×, no LOH traffic) and is deliberately **not** shipped: it requires transcribing the `JsonSerializerOptions`→`JsonWriterOptions` mapping by hand, and one wrong or missing member changes the response bytes. The residual this paragraph used to declare - *"only a host-registered converter for a **primitive** type could fault there"* - was **under-scoped in two directions, and #495 closed both.**

**Every OData envelope built as a `Dictionary<string, ...>` was serialized at execute time under the HOST's `HttpJsonOptions` (#495).** Two separate consequences, and the non-faulting one is the worse of the pair. (1) **Shape.** System.Text.Json applies `DictionaryKeyPolicy` to dictionary keys, and OhData's envelope keys - `error`/`code`/`message`/`target`, `@odata.context`/`value`/`@odata.count`/`@odata.nextLink` - are contractual identifiers, not names a policy may rewrite. **Measured** with the host's `DictionaryKeyPolicy` at `SnakeCaseUpper`: `{"ERROR":{"CODE":"NotFound",...}}` on **every** error response the framework produces, and `{"@ODATA.CONTEXT":...,"VALUE":[...]}` on **every collection GET, the service document, and both `WrapBoundOpResult` envelopes** - the collection route being the half #495 itself did not name. It ships a parseable body no OData client can read, under a 200 or a 4xx, with nothing anywhere reporting a problem. (`JsonObject` responses - GetById, the nav-single route - were never affected: STJ writes a node's member names verbatim.) (2) **Fault.** The fault surface is not the primitives; it is any converter matching `string`, `Dictionary<string, object>`, or a primitive. A throwing host `JsonConverter<string>` took the **group filter's own 500 envelope** with it, so the last-resort error path was itself the thing that failed: an empty, envelope-less 500 with no OhData log.

The split is **OhData owns the envelope's names; the host owns value formatting** - #252's division, one level out. Concretely: `ODataError` and the service document, whose content is *entirely* framework-generated, pre-render through `PreRenderedJson` with `_frameworkEnvelopeSerializerOptions`, a standalone host-free instance; `WrapBoundOpResult`'s collection and Edm-primitive branches pre-render with the registration's own options; and every remaining payload-bearing envelope (the three collection GETs, the nav-collection route, the #313 continuation, the four `$ref` shapes) goes through `ODataEnvelopeResult`, which stays **deferred** (`Results.Json`, no buffering - its `value` is an already-materialized `JsonArray`, so there is no user code left to fault and buffering a whole page would cost for nothing) but passes `EnvelopeOptions(...)`. `EnvelopeOptions` returns the source instance **by reference** when `DictionaryKeyPolicy` is null - i.e. always, on a default host - so no options are copied and no second `JsonTypeInfo` cache is created; only a host that really set one pays. `_frameworkEnvelopeSerializerOptions` sets `Encoder = UnsafeRelaxedJsonEscaping` **explicitly and load-bearingly**: ASP.NET Core's own `Http.Json.JsonOptions` overrides the Web default the same way, and a bare `new JsonSerializerOptions()` is *not* the same bytes (measured: a 404 quoting the requested key went 78 -> 88 bytes, every apostrophe escaped). `ErrorEnvelopeFidelityTests` pins the default-host bytes for all seven shapes, captured pre-fix and pasted verbatim, and pins each defect with a throwing-converter and a key-policy probe. **The remaining residual is now measured rather than assumed, and it is not the one #396 named.** A `JsonNode` does **not** re-enter host converters when it is written: `JsonValuePrimitive<T>.WriteTo` goes through `JsonMetadataServices`' own converter, not `options.Converters` - verified directly on .NET 10.0.11 with a throwing `JsonConverter<string>` and a throwing `JsonConverter<int>` over a `JsonObject` carrying both, neither of which fired. So #396's original claim about nodes was right, and every `Results.Ok(JsonNode)` route is genuinely immune. What a host converter *can* still reach at execute time is the **framework's own** members of the deferred envelopes - the `@odata.context` / `@odata.nextLink` / `@odata.id` strings and the `@odata.count` number, which are `object`-typed dictionary values and so resolve a converter. A throwing one there is an envelope-less 500 (reachable only when the payload itself contains no string to fault on first, e.g. an empty page); a merely reformatting one rewrites a framework-generated URL. Left open deliberately: closing it means either buffering every collection page or allocating a second `JsonSerializerOptions` per registration unconditionally, and neither is worth it for a surface this size.

**Advertise only what the route serves; the EDM is validated at startup (#465/#467/#468).** Three separate claims the server did not honour, one shape. (1) The **Priority-1** collection route appended `", $search"` to its OpenAPI description whenever the profile had a `Search` handler and never invoked it — there is no `$search` leg in that route body at all. Invoking is **not** coherent with the Priority-1 contract: on the `GetQueryable`/`GetAll` paths `Search` *replaces the source* and the framework applies the remaining options on top, which it can because it owns the pipeline there; Priority-1 hands the whole `ODataQueryOptions` to the profile, so there is no seam to feed a search-derived source into, and honouring it would mean bypassing the profile — dropping `$filter`/`$orderby` on exactly the requests carrying `$search` (the same defect one option over) and routing around any row-level scoping the handler applies, which is a common reason to choose Priority-1. So the advertisement is gone and `GetODataQueryable` + `Search` is **refused at startup**; `$search` there is the profile's own business via `options.Search`. (2) **`OhDataQueryOptionsMetadata` fields mean "this route honours this option", never "this route is of kind X"** — it is attached to five route shapes (three collection GETs, `/$count`, GetById) and read by three companion packages, so a field with two meanings produces the same wrong document in all three. `$top`/`$skip` were added on metadata *presence* alone (documented on GetById and `/$count`, both of which drop them) → new `TopSkipSupported` field; `/$count` set `CountEnabled: true` to mean "this route IS a count" while the transformers read "documents the `$count` option" → reduced to the single meaning, `false` there; and `/$count`'s `FilterEnabled` mirrored the profile flag although its GetAll fallback answers `400` for any `$filter` → gated on the source (`countSourceAppliesFilter`), matching the "B1 fix" the sibling collection route already had. **The fix site is `OhDataEndpointFactory`'s metadata attachment, not the transformers** — one site, three consumers, which is why they agree byte-for-byte; keep it that way. (3) `$metadata` emitted `IncludeInServiceDocument="true"` on every unbound **function** import (the `Microsoft.OData.ModelBuilder` default, never set) while the service document was hand-built from `registration.Profiles` and listed entity sets only. For a **parameterized** import that claim is invalid CSDL (§13.6 — it cannot be invoked by name alone); those now clear the flag, parameterless ones keep it and are really listed, and the service document is **derived from the EDM container** so the two generators cannot diverge again. Action imports are never listed (not GET-addressable, no such attribute in CSDL). Riding along: **`EdmValidator.Validate` is now called from `MapOhData()`** — it was called nowhere in the assembly. `CsdlWriter.TryWriteCsdl` does not run these rules and `CsdlReader.TryParse` does not police them either, so an invalid construct reached the wire and broke only consumers that validate (codegen tools). Measured when first wired in: it catches this issue's own violation in four fixtures, **and** the compiler-generated name from `AddFunction` with an un-named lambda (`InvalidName`, `<Method>b__0_1`), which had been shipping invalid `$metadata` silently. That second one is now caught **earlier and better**, at registration: `AddFunction`/`AddAction` validate the resolved name themselves and throw `ArgumentException` naming the parameter and the remedy (pass an explicit `name`), because a generic CSDL-validation failure quoting `<Method>b__0_1` at `MapOhData()` tells a developer neither what caused it nor what to do. **They call `OpenTypeJsonOptions.IsValidDynamicPropertyName` — the shipped validator, never a second transcription of the ABNF**; the whole point of the fast-path/rune-walk oracle relationship recorded above is that a third hand-rolled copy would drift from it. The `*Cached` variant is deliberately not used: its 1024-entry cache memoises per-request dynamic keys on the serialize path, and startup-time operation names would only evict them. `EdmValidator` remains the backstop for what a name check cannot see — the parameterized `IncludeInServiceDocument` violation among them.

**ETags.** Set `GetETag = model => "..."` to opt in. Adds `ETag` response header to GET/POST/PUT/PATCH. `CheckETagAsync` is the single precondition gate, and it now covers **every state-changing route the framework owns and can key** (#478): entity PUT/PATCH/DELETE, the structural-property writes, all three `$ref` link-management routes (`POST`/`PUT`/`DELETE /{Set}({key})/{Nav}/$ref`), the navigation-POST create route and (#566) the entity-bound ACTION route (`POST /{Set}({key})/{Action}`). Read the route list literally — the four `$ref`/nav-POST routes previously **discarded** `If-Match` and performed the write with a 204/201, which was a lost update on relationship state. **Collection-bound and unbound actions remain excluded, and that half survives on its own reasoning** - neither has a `{key}` segment or an addressed entity, so there is nothing to load an entity tag from, and §11.5.4.1's *"or collection of entities"* half would need a collection ETag the framework does not compute. The ENTITY-bound action was excluded too until #566, defended by saying the action-invocation resource *"has no representation and so no entity tag"*, citing Protocol §11.5.4; **that phrase appears nowhere in Part 1** (`grep -ic "no representation"` returns 0), and four clauses say the opposite - §11.4.1.1 is a MUST for *"a Data Modification Request **or Action Request**"*, §8.2.4 names Action Requests in both its `428` and its `412` sentences, §8.3.1 says the ETag may be used *"in updating, deleting, **or invoking the action bound to the entity**"*, and §11.5.4.1 tells the client to send `If-Match` for exactly this case. Measured before the fix: `POST /v1/Movies(3)/Rate` with a stale `If-Match` answered `200` and MUTATED the entity while `PATCH /v1/Movies(3)` carrying the same header answered `412`. Do not re-derive the withdrawn justification. The gate fires **before** the body is read and before the handler delegate runs, so a refused write provably mutates nothing (`ConcurrencyTests` asserts delegate non-execution, not just the status code). It is still **not atomic** — no transaction is opened, so the TOCTOU window between the gate's `GetById` and the delegate's write is unchanged and `docs/etags.md` says so. Comparison follows RFC 9110 §13.2.2 evaluation order: `If-Match` first (**strong** comparison per §13.1.1 — a `W/`-prefixed entry is *dropped*, never unwrapped, so `If-Match: W/"<current>"` is a 412), and `If-None-Match` only when `If-Match` is absent (**weak** comparison per §13.1.2, so `W/"<current>"` *does* match there). `ParseETagList` and `ParseStrongETagList` are the two readers and are **not** interchangeable; both delegate to `SplitETagList`, which detects the `W/` sentinel case-insensitively on purpose — leniency there is the fail-closed direction for both headers. A non-`*` `If-None-Match` on a write is now honoured (412 on match); the separate `AllowUpsert` `If-None-Match: *` create-guard on PUT stays where it is because it must work **without** `UseETag`, which `CheckETagAsync` requires.

**Named registrations.** `AddOhData("v1", ...)` / `MapOhData("v1")` uses `AddKeyedSingleton<OhDataRegistration>("v1")`. Unnamed `AddOhData()` uses the `__default__` key. Multiple registrations coexist.

**Bound functions and actions.** `BindFunction(delegate)` / `BindAction(delegate)` in the profile constructor registers HTTP routes at startup and registers the operation in the EDM. Functions: `GET /{EntitySet}/{Name}?param=value`. Actions: `POST /{EntitySet}/{Name}` with JSON body `{ "paramName": value }`. A **trailing** `CancellationToken` parameter is detected and passed automatically; one anywhere else, or a nullable one, is refused at bind time (#498).

**A bound FUNCTION returning a collection of TModel is bounded by `MaxTop` and pages (#357, BREAKING).** `WrapBoundOpResult`'s collection branch used to hand the whole collection back with no cap, no `@odata.nextLink`, and `$top`/`$skip` neither applied nor rejected - so the DoS ceiling the framework advertises and enforces on all three ordinary collection routes was fully bypassable through any operation that returned a collection (measured on `MaxTop = 50`: `?$top=1000` -> 400 on the collection route, 200 with all 77 entities on `/TopRated`). `TryApplyOperationCollectionPaging` is **#201's `ApplyGetAllPaging`, not a new scheme** - the situation is identical (a fully materialized array, the framework owning the pipeline from there, so an offset continuation is one it can always honour), and it is a second implementation only because that one is a local function closing over the route's `ODataQueryOptions`, which a bound-op route does not build. `$top`/`$skip` are read the way the **navigation-collection** route reads them (`int.TryParse` + that route's existing *"is invalid. It must be a non-negative integer."* wording), the other place in this file that pages a materialized collection with no `ODataQueryOptions` behind it: building a whole `ODataQueryOptions` would additionally start rejecting malformed values of options this route still ignores (`$filter=`, `$skiptoken=`), a wire change #357 does not ask for and whose surface is set by somebody else's constructors, and MS's individual `TopQueryOption`/`SkipQueryOption` both require an `ODataQueryOptionParser` that needs an `ODataPath` this route never parses. The `$top > MaxTop` message **is** shared with the collection routes verbatim - the same condition must not produce two envelopes depending on which route reached the same set.

Three decisions worth keeping. (1) **Breaking by default**: `EntitySetDefaults.MaxTop` is `1000`, not null, so an operation returning more than 1000 entities now truncates to a page plus a continuation. `MaxTop = null` opts out, exactly as on `GetAll`. (2) **The bound is applied in the RUNTIME collection branch, the metadata from the DECLARED return type.** A handler declared `Task<object>` returning a `List<TModel>` must not be a way around the ceiling; conversely `AddBoundOperationPagingMetadata` attaches `OhDataQueryOptionsMetadata` (only `TopSkipSupported` + `MaxTop`; every other field false) off `BoundOperationDefinition.ReturnType`, at the ONE metadata site #467 requires, sharing `DeclaresCollectionOf` with `AddBoundOperationProduces` so the three consumers cannot disagree. The only divergence this leaves is serving a bound the document did not promise - the safe direction. (3) **The paging source is the STARTUP source, and that is load-bearing**: `WrapBoundOpResult`'s `source` parameter is the request-scoped instance, whose `MaxTop` is null (profiles are `AddScoped`; `_resolvedMaxTop` is assigned in `VisitModelBuilder`, which only runs on the startup instance), so reading the ceiling off it silently disables the whole bound - measured, 25 rows returned and `$top=1000` accepted on a profile with `MaxTop = 10`. It is the two-sources rule stated above, and `MaxTop` is named in it. **Actions were excluded and that exclusion is REVERSED by #543; see below.**

**A bound ACTION is bounded too, and a result that does not fit is REFUSED (#543, BREAKING).** #357 excluded actions and defended it with two claims, both **measured false on `d2d96d8`**. Its `pagingSource` parameter was doing two jobs at once - "is this route pageable" *and* "here is the startup source" - and both action call sites passed `null`, so an action skipped the bound entirely: on `MaxTop = 10` over 25 rows, `POST /Set/Dump` answered `200 len=25 nextLink=<none>`, and so did `?$top=999`, `?$top=5`, `?$skip=20` and `?$top=abc`, while the sibling **function** capped at 10 with a `$skip` continuation and `400`d `$top=999`. That is the exact wire shape #357's own entry says it closed. Refuted claim 1: *"a handler declared `Task<object>` returning a `List<TModel>` is not a way around the ceiling"* - it was precisely that, for an action. Refuted claim 2: *"moot in practice besides, `ActionConfiguration.Returns`/`.ReturnsCollection` refuse an already-declared entity type"* - true only of a **declared** entity return (that throw is real and is #539); `Task<object>` registered fine. The flag is now `continuable`, a separate parameter, and every caller passes the startup source: **an action IS bounded, it just cannot be CONTINUED.** Conflating "no continuation available" with "no ceiling applies" is how the ceiling became bypassable.

Everything except one branch is shared verbatim with the function path - an explicit `$top` applied and validated against `MaxTop` with the identical message, `$skip` applied, a malformed value the same `400` - because the same condition must not produce two envelopes depending on which route reached the same set. The branch that differs is **no `$top`, result larger than `MaxTop`**: three shapes were available and two are unavailable here. *Cap and emit `@odata.nextLink`* is invalid (§11.2.5.7 makes a nextLink a URL the client **GETs**, while §11.5.4.1 invokes an action by **POST** to its action URL - there is no GET-addressable continuation of an action invocation, so the link would answer 405, and re-POSTing a side-effecting action to collect page 2 is not a continuation). That argument used to run through §11.5.4 "has no representation" and #478's ETag exclusion; the phrase is not in the spec and the exclusion is a known deviation (#566), so neither is cited here any more. *Cap silently* is forbidden by M1. So it **throws**, which the group filter turns into `500` + the OData envelope with the count, the ceiling and the three remedies logged - and it is a `500` rather than a `400` for #496's reason: the condition is decided entirely by server-side state (the profile declared the ceiling, the handler exceeded it, identically for every request), so blaming the client would be the defect #496 removed one route over. `Prefer: maxpagesize` is deliberately **not** honoured on an action and no `Preference-Applied` is emitted - RFC 7240 makes preferences advisory and forbids claiming one that was not applied, and there is no paging here to drive. `AddBoundFunctionPagingMetadata` is renamed `AddBoundOperationPagingMetadata` and attached to the two action routes as well (an action now really does honour `$top`/`$skip`, which is what an `OhDataQueryOptionsMetadata` field means under #467); the dangling *"see `AddBoundFunctionPagingMetadata` for why actions are excluded"* cross-reference in `WrapBoundOpResult` - which pointed at a method containing no such rationale - is gone with the exclusion it described.

**An entity return is declared through `ReturnsFromEntitySet`, on BOTH operation kinds (#539, BREAKING).** `ActionConfiguration.Returns<T>()`/`.ReturnsCollection<T>()` throw `InvalidOperationException` **at the call**, not at `GetEdmModel()`, for a CLR type already declared as an entity type, naming `ReturnsFromEntitySet`/`ReturnsCollectionFromEntitySet`; the `FunctionConfiguration` twins accept it (measured, ModelBuilder 2.0.0 / .NET 10.0.11). OhData called only the first pair, so `BindAction` over `TModel` or `IEnumerable<TModel>` - `POST /Widgets/Archive` answering with the archived rows - died at `MapOhData()` quoting a method OhData neither called nor exposed, while the function twin worked. `RegisterEdmReturnType` calls the `FromEntitySet` pair whenever the (element) return type is the profile's own `TModel`, **unconditionally across kinds** rather than behind an is-this-an-action branch: the CSDL is byte-identical either way (no `EntitySetPath`, no extra attribute - pinned by `BoundActionEntityReturnTests.BoundFunction_MetadataDeclarationIsUnchanged`), it is what MS's own E2E fixtures do for an entity return on both kinds, and one unconditional rule cannot drift between them. **The entity-set name is always the one `VisitModelBuilder` opened with**, never derived from the return type, because `ReturnsFromEntitySet` does **not** validate that the name exists - it CREATES the set (measured: a bogus name silently added `EntitySet:Ghosts` to the container and to `$metadata`). Residual, and the #539 "floor": an entity return of some *other* profile's model type still cannot be expressed, and now throws an OhData-authored message naming the operation and the remedies with MS's as the inner exception, rather than a raw ModelBuilder string. The two issues interact - #539 turns #543's ceiling from a `Task<object>` corner into the ordinary shape.

**Type erasure via `IEntitySetEndpointSource`.** Profiles are generic (`EntitySetProfile<TKey, TModel>`) but the factory iterates them as `IEntitySetEndpointSource` (non-generic, internal). The factory re-introduces the generic types via `MakeGenericMethod(KeyType, ModelType)` once per entity set at startup - not per-request.

**Profiles are scoped; two sources per handler.** Each route handler closure captures two `IEntitySetEndpointSource` references: the startup `source` for structural queries (`HasGetById`, `MaxTop`, auth config, nav route metadata) and a per-request `s = ResolveHandlers(ctx)` resolved from `ctx.RequestServices` for all `Invoke*()` calls. This allows profiles to safely inject scoped dependencies (e.g. `DbContext`) in their constructor. Compiled delegates that don't capture scoped state (ETag, key-to-string, key-to-URL) are cached in `static ConcurrentDictionary<Type, ...>` so `Expression.Compile()` runs at most once per type.

**"Don't capture scoped state" was an ASSUMPTION ABOUT USER CODE, and the cache enforced nothing (#483).** The three caches are keyed by `GetType()` and store a delegate compiled from the **first-constructed** instance's expressions — which is the startup-scope instance, whose scope `OhDataBuilder` disposes as soon as the registration is built. `UseETag`'s comment declared the delegate safe to share because it "accesses model properties only (no DI dependencies)"; nothing checked, and `TryExtractDirectMemberNames` merely disables `$select` pushdown for a non-member selector rather than rejecting one. So `UseETag(x => _scopedDep.Stamp(x.Version))` compiled fine and then ran the **disposed** startup dependency on every request for the process lifetime — and for a *non-disposable* dependency, silently reused another scope's instance with no signal at all. The framework invites exactly that constructor shape: profiles are `AddScoped` **specifically** so they can inject scoped services, `DbContext` being the documented motivating case. The fix is that the caches stop pretending: `CapturedState.IsCapturedByExpression` walks the selector and a capturing one is **compiled per instance** instead, while a selector reading only its lambda parameter is cached exactly as before. **"Per instance" is per REQUEST** — `UseETag` runs in the profile constructor and profiles are `AddScoped`, so losing the cache pays an `Expression.Compile()` on every request that reaches the route, which is what the adjacent `s_keyToStringCache` comment has always said (*"caching avoids per-request compilation under scoped resolution"*). **Measured** end-to-end on `develop` @ `7211a6f` (TestServer, 200 requests each after warm-up, two runs) on `GET /Set(key)`: **0.63–0.69 ms/req** capturing against **0.20–0.26 ms/req** non-capturing — roughly **2.5–3.5x**, about **+0.4 ms per request**. An earlier "~100 µs per construction" figure here was wrong on both counts (per-request, not per-construction; ~4x the quoted magnitude) and is withdrawn (#548). Correctness is unaffected either way — measured by reference identity in `Issue483CapturedSelectorLifetimeTests`, `Assert.Same` for the plain profile and `Assert.NotSame` for the capturing one. Nothing is rejected, so no working configuration breaks; a capturing selector simply becomes correct. **Constants are the whole hazard and statics are not**: C# compiles a capture into a `ConstantExpression` holding the display class (or `this`), frozen when the lambda is compiled, whereas a static field is read at INVOCATION time and is per-process by construction. Value-typed and `string` constants — a literal, an enum such as `StringComparison.Ordinal` — are immutable and belong to no instance, so they do not count; anything else non-null does, and the judgment deliberately errs toward "captured" — which is not free: a false positive costs that `Expression.Compile()` on every request, not one cache entry. The remedy for a selector that really must read an outside value is to hoist it so the lambda reads nothing but its parameter (fold it into a model property); assigning it to a local first does NOT help, because a captured local is still compiled into a display class, and promoting it to a `static` restores caching only for a value that genuinely is per-process. The **key** selector gets the same gate on both its caches even though the constructor's direct-property-access check leaves only `x => captured.Member` reachable there — degenerate as a key, but uniformity is what makes "no cache in this type stores instance-derived state" a property rather than a case analysis. `s_structuralAccessorCache` is untouched: it is keyed by property name and derived from `TModel` alone.

**`MapGroup` slash insertion - critical routing rule.** `MapGroup` inserts a `/` between the group prefix and any route template that doesn't start with `/`. This breaks OData key syntax (`Widgets({key})` vs `Widgets/({key})`). All entity-set routes are therefore mapped on the top-level `/prefix` group with the entity set name embedded in the template (e.g. `"/Widgets({key})"`) rather than on a per-entity sub-group. If you add new routes, follow this pattern.

**Authorization is declared per profile.** `RequireAuthorization()` / `RequireRoles()` on a profile applies the same auth requirement to every route for that entity set. `ConfigureAuthorization(...)` narrows that per operation category - `Read`/`Create`/`Update`/`Delete`/`Invoke`, plus the `Writes` and `All` selectors and a named `Invoke(name, ...)` - and `.RequireResource()` adds ASP.NET Core resource-based authorization against the `{key}` entity. Evaluation is entirely ASP.NET Core's; profiles store plain policy/role/claim names.

**Three auth seams compose into a quiet fail-open; two are closed, the third is documented (#487).** No single one was an undocumented bypass - `docs/authorization.md` was candid about all three. The finding is the composition, and the absence of any startup signal. All three were **confirmed by measurement** before anything changed.

**(1) Unbound operations had no per-operation authorization at all, and no way to acquire one.** `MapUnboundOperations` took no auth configuration; they are mapped on the outer group, so no profile's `RequireAuthorization()`/`RequireRoles()`/`ConfigureAuthorization(...)` reaches them. **Measured** on a registration whose only profile declares `RequireAuthorization()`: `GET /odata/{Set}` -> `401`, `POST /odata/Mutate` -> `204` **with the handler executed**, `GET /odata/Peek` -> `200` with its body. This is the seam where a warning alone would have been wrong: the docs' own remedy is "apply group auth", which also covers `$metadata`, so a developer who wanted a *gated* unbound operation beside anonymous schema discovery had no expressible configuration and a warning with no opt-out. So the **capability was built** - `AddFunction`/`AddAction` take an optional `authorize` lambda over the same `ICategoryAuthorizationBuilder` `ConfigureAuthorization` uses, and all four overloads funnel through one `AddUnboundOperation` so #468's name check and #498's signature check cannot drift between the authorized and unauthorized spellings. `RequireResource()` is **refused at the call site**: Layer B evaluates against the entity loaded from a `{key}` segment and an unbound operation has neither key nor entity set, so the rule could only ever be a silent no-op - the exact fail-open shape the overload exists to remove. `AllowAnonymous()` there deliberately does **not** emit `AllowAnonymousAttribute`: it means "I am not adding a requirement", never "I am removing the host's", so an unbound operation cannot open seam 3.

**(2) A `ConfigureAuthorization` category with no rule fails OPEN, silently.** **Measured** on the migration shape `.Read(r => r.RequireAuthenticatedUser()).Writes(w => w.RequireAuthenticatedUser())` - which reads as a refinement of `RequireAuthorization()` and is a **widening**: the collection `GET` answered `401` while `POST /{Set}/{Action}` and `POST /{Set}({key})/{Action}` both answered `204` with the handler executed. The identical surface under the legacy `RequireAuthorization()` answered `401`. Made loud, not changed.

**(3) A category-level `.AllowAnonymous()` overrides a host-applied group requirement - UNCHANGED and UNWARNED, deliberately.** Confirmed, and confirmed to be **ASP.NET Core's own `AllowAnonymousAttribute` semantics rather than OhData's**: a control test containing no OhData at all - a plain `MapGroup` with `RequireAuthorization()` applied *after* its routes - serves the `.AllowAnonymous()` endpoint `200` while its sibling answers `401`, whichever order the two were applied in. Not warned about because `.AllowAnonymous()` is the ONLY way to express a deliberate public hole in an otherwise-gated surface, so a warning would fire on correct configuration with no silencer - the failure mode #440 and #481 both establish as worse than no warning. `docs/authorization.md` gains the section that owns the composition, and the "Global auth" section's claim that a group requirement covers every route in the group is narrowed: it is a backstop for routes nobody has an opinion about, not a floor.

**The diagnostic runs from an `IEndpointConventionBuilder.Finally` convention, and it has to.** `MapOhData()` returns the group and the host applies `RequireAuthorization()` to it *afterwards* - the mitigation the docs recommend for exactly these routes - so at map time a route with no rule of its own is indistinguishable from one about to inherit that backstop, and warning inside `MapAll` would fire on the correct configuration. `Finally` runs after every convention on the endpoint, the host's included. **Measured** on .NET 10.0.11: a `Finally` registered before `group.RequireAuthorization()` observes that requirement's `IAuthorizeData` on every endpoint, including endpoints under a nested `MapGroup("")` - which is how every entity-set route is mapped. It can run more than once per endpoint, so `AttachAnonymousRouteAudit` dedupes on `OhDataAnonymousRouteAudit.Key`; one warning per unbound operation and per (entity set, category), never per route. `ApplyOperationAuth`'s "no rule" branch and `ApplyUnboundOperationAuth` attach the audit metadata, so all the static reasoning stays where the route is mapped and the `Finally` only asks "did anything authorize this in the end". A `Require*` anywhere on the profile (for a category) or anywhere in the registration (for an unbound operation) is the **intent gate** - a service that is simply public is never reported, and an explicit `AllowAnonymous()` never reaches the audit because it produces a non-null rule. **Firing scope across the repo's own seven test projects: emissions come only from single-purpose auth fixtures that deliberately configure one category; the TestBench and all six other projects are silent, and no test outside `Issue487AuthSeamTests` changed.** (A "46 emissions / 24 distinct subjects" figure stood here and is **withdrawn** - it is not reproducible from source and no test pins it, which this repo's measurement-provenance rule does not permit. Restore it only with a test that asserts it.) `ApplyAuthRequirements` is the one endpoint-gate replay, shared by `ApplyOperationAuth` and `MapUnboundOperations` rather than transcribed - the two authorize the same `AuthRequirement` list. **No request-path behaviour changed anywhere**; the whole fix is a diagnostic plus one opt-in capability.

**A named `Invoke` auth rule is matched case-insensitively and must resolve, or startup throws (#525).** `ResolveOperationRule` compared `OperationAuthRule.BoundOperationName` with `StringComparison.Ordinal` while every route template and operation segment it governs matches case-insensitively, so `ConfigureAuthorization(a => a.Invoke("stamp", …))` against an operation declared `Stamp` matched **nothing**: the rule was discarded in silence and the route fell back to the generic `Invoke` rule — or, with no generic rule, to **no requirement at all**. Fail-OPEN on an authorization rule, with no startup error and no warning. The comparer is `OrdinalIgnoreCase` now, and that alone is **not the fix**: a *misspelled* name evaporates identically and no comparer rescues it, so `MapEntitySet` also refuses any `Invoke(name, …)` rule that resolves to no declared bound operation (`source.BoundFunctions ∪ source.BoundActions`, entity- and collection-level alike), naming the rule and listing the declared operations. Refused rather than warned: there is no configuration in which authorizing a nonexistent operation is meaningful. The startup check uses **the same comparer as the resolution it guards** — a stricter one there would reject exactly the miscased rules the comparer fix just made work, i.e. this bug re-introduced one layer up wearing an exception. Placed **before** the #486 GetById guard, which itself resolves rules by name, so a typo is reported as a typo. `Issue525NamedInvokeAuthRuleTests` pins both halves plus the generic-rule-fallback direction.

**Two named `Invoke` rules resolving to ONE operation are refused at startup (#546).** #525's `OrdinalIgnoreCase` is correct, but `ResolveOperationRule` keeps last-write-wins, so two rules differing only in case now collapse onto each other and **the declaration order decides whether the operation is protected**: `.Invoke("Stamp", RequireRole("admin")).Invoke("stamp", AllowAnonymous())` answered `200` anonymously while the reverse order answered `401`, both starting cleanly under #525's new validation. The first order was deterministically PROTECTED under the pre-#525 `Ordinal` comparer, so #525 fixed a fail-open and created one - which its own check could not see, because it asks only *"does this name resolve to a declared operation?"* and both members of a colliding pair do. `MapEntitySet` now throws `InvalidOperationException` naming both spellings and the operation, **including for two identically spelled rules** (same mechanism, same consequence; case only changes how easy the pair is to spot). Grouped by the declared operation each rule resolves to, under the **same comparer `ResolveOperationRule` uses** - a second, independently derived comparison would reject a different set of configurations than the one that actually collapses at runtime, which is #525's own reasoning. **Generic `Invoke(...)` rules are deliberately unaffected**: `generic = rule` is last-write-wins by design there, as for every category selector, and `All(...)` then `Invoke(...)` is a documented refinement idiom. BREAKING in the security direction - an app in this state is running under an authorization rule it did not choose, and there is no configuration in which two rules for one operation are meaningful.

**It also does not COMPOSE ACROSS A NAVIGATION, and that is a warning rather than a gate (#481/#368).** There are exactly two authorization-state reads in `OhDataEndpointFactory` (`source.Authorization`, `source.OperationAuthorization`) and both are on the profile being mapped, so every navigation-family route and every `$expand` call site runs under the **declaring** set's rule; the target set's own profile is never consulted. **Measured across 19 route shapes**: with an admin-gated child set and an anonymous parent declaring a navigation into it, the nav `GET`, its `/$count`, all four `$ref` shapes, the nav-`POST` create route and `$expand` (delegate, batch and pushdown) all succeeded anonymously — and `$ref` `POST`/`PUT`/`DELETE` and nav-`POST` **executed the write**, so this was never read-only disclosure. **Enforcement was refused** (owner ruling): `Microsoft.AspNetCore.OData` behaves identically and cannot do otherwise — verified against its source, it contains **no authorization code at all** and routes the navigation action onto the *parent's* controller — so fail-closed would be a divergence from OData norms; it would also break the idiomatic scoped-navigation shape with no opt-out flag to point at, is undefined where sibling sets share one EDM type (#458), and is precisely the retroactive poisoning #293's frozen Model B forbids one concern over. So `WarnNavigationTargetAuthorization` emits one `Warning` per (declaring set, navigation, stricter target set) at `MapOhData()`, `WarnWireShapeIsFlat` being the precedent for shape and tone. **Three targeting rules, each a probe result, each silently wrong if changed**: (1) the target is the **EDM navigation property's own target type** resolved through `ResolveProfilesForEdmType` — NOT `ChildEntitySetName` (the `batchGetAll` overload never sets it; probe case 7 leaked through exactly that) and NOT `NavItemType` (`HasOptional`/`HasRequired` never set it); (2) it fires on the **DECLARED** navigation, not the routed one — probe B-1, a bare `HasMany(x => x.Children)` with no handler and no route, still leaks via `$expand`, while an **undeclared** convention-discovered navigation (probe B-2) is deliberately silent because #440/#446 made it reachable by nothing and `WarnUndeclaredConventionNavigations` already names it, which is why the two checks partition the EDM's navigations on the *same* `NavigationPropertyNames` test; (3) the **union**, never the binding — per the decision at `ResolveProfilesForEdmType`, exactly one exposing set yields a real `IEdmEntitySet` (and a one-element union, so they agree) while two-or-more and none both yield an `EdmUnknownEntitySet` placeholder, so a binding-only check stops working the moment an unrelated second set is registered over the child type. The comparison is **per operation category** (`Read` always — `$expand` needs no route; `Create` only with a `post` handler; `Update` only with `$ref` handlers; `Delete`/`Invoke` never, no nav route is mapped in either) because a target declaring `Read(AllowAnonymous)` + `Writes(RequireRole)` is an ordinary shape that a read-only navigation loses nothing to, and a warning that fires on correct configuration gets ignored. `NavigationTargetAuthorization` normalizes both authorization models to one token vocabulary, sorting role and claim-value lists so a re-ordered declaration is not reported as a difference. **Measured over the repo's own seven test projects: zero emissions from any pre-existing fixture.** `docs/authorization.md`'s *"there's no bypass"* sentence is narrowed to the declaring profile's own rule in the same commit.
**API-model / entity separation lives in a companion package, and it is a Priority-1 profile (#651).** `EnGen.OhData.AspNetCore.Mapper` serves a `TModel` that differs from the `TEntity` behind it. The adopter declares **correspondences** through a closed vocabulary - `Property/From` (Direct, Rename or Path, decided by the shape of the entity-side expression), `Format` (an interpolation), `Compute` (anything else), `Reference`, `Collection/From/Element`, `Ignore` - and `MappedEntitySetProfile<TKey,TModel,TEntity>` composes the query. `$filter`/`$orderby` are parsed against the model, bound by **`Microsoft.AspNetCore.OData`'s own `FilterBinder`/`OrderByBinder`** (the same `BindNavShape` call shape the core uses) and only then **substituted** into entity terms by `ModelToEntityRewriter`, so every operator, canonical function and lambda the framework supports is bound by the framework's binder and the package adds only a mechanical member swap.

Three facts about it that are load-bearing and were each established by measurement rather than argument. (1) **Priority-1 is affordable only because the P1 route calls the same `ApplyCollectionPipelineAsync` as every other collection route** - so `$select`, `$expand` (through the profile's navigation delegates, #650's nested options included), ETags and the envelope stay the core's, and the profile owns only `$filter`/`$orderby`/`$top`/`$skip`/`$count` plus paging. The design doc's original rejection of P1 assumed the package would have to clone the whole expand pipeline; it does not. (2) **The projection is composed onto the entity query, never applied after materialisation.** Map-after-materialisation was implemented first and the conformance oracle rejected it on its first run: EF returns an entity with its references unloaded, so a Path member (`o.Category.Name`) rendered `null` on every row, and `Include`ing every reference on every request is the over-fetch the package exists to avoid. The projection is **scalar-only** - no navigation appears in it, so this is not the DTO-typed-queryable strategy that was ruled out - and `$expand` is served by one batched query per navigation per page (`MappedNavigationLoader`), which is where a reshaped collection's join entity is elided. (3) **`MappedPageSize` is the profile's own ceiling, not `MaxTop`.** A P1 profile that emits its own `@odata.nextLink` skips the framework's cap, and `_resolvedMaxTop` is assigned in `VisitModelBuilder` on the **startup** instance while handlers run on a request-scoped one - the two-sources rule - so reading it at request time would silently disable the bound. The default is 1000 because that is `EntitySetDefaults.MaxTop`'s own default. Continuations are spelled with `$skip`, an option the profile provably re-reads, so `$skiptoken` is refused with `501` rather than implemented twice.

Validation is **unconditional** (`ModelMapValidator`): a member with no binding and no `Ignore()`, an unconstructible model, a navigation whose target has no `Nested<,>` map or whose map is declared from a different entity, and a `Format` that is not an interpolation. `Compute` is the one kind whose shape cannot guarantee translatability, so `ProbeTranslatability` probes it against the adopter's provider - through an `OrderBy`, **not** a `Select`, because a final `Select` is one of the few clauses EF Core will still evaluate on the client and a `Select` probe would pass for a member no `$filter` could ever use. `docs/api-model-mapping.md` is the guide.

**`AdvancedConfigure` eject hatch.** Overriding `AdvancedConfigure(EntitySetConfiguration<TModel>)` gives full EDM control and disables automatic EDM config. Detected at startup via `MethodInfo.DeclaringType` comparison.

**That eject drops `Ignore()`'s EDM half, and the residue is a value oracle — documented and warned, deliberately not fixed (#489).** `Ignore()` withholds on two levels: the EDM removal rides the `_configurators` pipeline, runtime suppression (routes, wire, PATCH binding) is applied separately from `IgnoredPropertyNames`. `VisitModelBuilder` returns **before** the pipeline runs when the override is present, so the property is back in `$metadata` and query-addressable while the wire still omits it — `$filter` over it answers truthfully one predicate at a time, so the value is never served and still discoverable, and `$metadata` discloses its name and type regardless of which capabilities the override re-enabled. In the ordinary case the EDM removal makes the property indistinguishable from one that never existed (ODL fails with the same *"could not find a property named…"*), so the 400 cannot confirm existence. **Not fixed**, on two grounds: re-imposing `Ignore()` on top of the override defeats the hatch outright, and `HasOptional`/`HasRequired`/`HasMany` ride the same pipeline and stay ejected — a half-ejected pipeline whose membership is decided by consequence severity is a worse contract than the one it replaces. So it takes the `WarnWireShapeIsFlat` shape instead: `WarnIgnoredPropertiesStillInEdm` logs one `Warning` per affected property at `MapOhData()`, naming the entity set, the property and the one-line remedy (`configuration.EntityType.Ignore(...)` inside the override). **Gated on the EDM as built**, not on the mere presence of an override — re-applying the removal by hand is what the docs prescribe, and warning on the *correct* configuration teaches developers to tune the warning out. The query-capability half is deliberately not in the gate (taking the hatch also drops the automatic `Filter()`/`OrderBy()`/`Select()` calls, so a capability added later must not silently un-warn). CLR→EDM name resolution goes through `ODataPropertyNaming`, so a `[JsonPropertyName]`-renamed ignored property is still found. `docs/ignoring-properties.md` carries the security warning and the fix; `docs/architecture.md` cross-references it. `Issue489IgnoreUnderAdvancedConfigureTests` pins the oracle itself as characterization on both sides, the warning's content, and its targeting.

**Profile types have no ASP.NET Core dependency.** Auth config is stored as plain `AuthorizationConfig` data; the factory applies `RequireAuthorization`. Keep it this way. The one place a profile touches an ASP.NET Core type is #498's `OperationSignatureValidation.Validate`, which asks `typeof(IResult).IsAssignableFrom(returnType)` to refuse a handler that returns the HTTP envelope the framework owns — a bind-time *rejection*, not configuration a profile carries, and it lives in its own file so the division above stays legible.

**Property routes ride `GetById`/`Patch`; no new handler delegates.** `PropertyAccessEnabled` (profile-level `bool?`, inherits `EntitySetDefaults.PropertyAccessEnabled`, **default `true`**) gates `GET /{EntitySet}({key})/{Property}` and `/$value` (requires `GetById`) and `PUT`/`PATCH`/`DELETE /{EntitySet}({key})/{Property}` (requires `Patch`, built as a one-property `Delta<TModel>`). Structural properties are computed once at startup as every public readable CLR property minus every navigation property name, so property and navigation routes never collide by construction. The one remaining collision risk - an entity-level bound function sharing a name with a structural property - is caught by a startup validation pass in `app.MapOhData()` (`InvalidOperationException`), since two routes can't otherwise register the same `(template, method)` pair.

**`AllowDeepWrites` controls what the three entity write handlers receive, not a new route.** Profile-level `bool?` (inherits `EntitySetDefaults.AllowDeepWrites`, **default `false`**), entity-level granularity only - no per-navigation opt-in. Default: nested navigation-property values that System.Text.Json already bound during deserialization are stripped (nulled) before `Post` and `Put` run, and never enter the `Delta<TModel>` on `Patch`. Opt-in (`true`): the full deserialized graph is passed through; the handler owns atomic persistence (the framework does not open a transaction).

**The strip is gated on the body having NAMED the navigation; it was not, and the comment that said why was false (#506).** `deepWriteNavPropsToStrip` filters on `p.SetMethod is not null`, above which a comment claimed *"properties without a public setter can't be deserialized into by STJ in the first place, so they're excluded — nothing to strip."* **`PropertyInfo.SetMethod` returns non-public accessors**, so it excludes nothing of the sort: `{ get; private set; }` - the standard EF-encapsulation shape, and a navigation the convention builder discovers - was in the set, and the `POST`/`PUT` loops nulled *every* member of it unconditionally. **Measured**: `PUT {"id":1,"title":"t"}`, naming no navigation at all, handed the handler `Kids == null` where the constructor had put an empty list; a handler diff-syncing that collection against the loaded entity gets an NRE in `.Count` or reads it as "clear the relationship". The filter is deliberately **left wide** - narrowing it to a public setter would exempt a `[JsonInclude] { get; private set; }` navigation STJ binds perfectly well, which OPENS a deep-write hole - so the *gating* is what changed: `deepWriteNavByBodyName` (startup, EDM name then CLR name as a non-overwriting alias, `OrdinalIgnoreCase` because the write options set `PropertyNameCaseInsensitive = true` unconditionally) plus `CollectPresentBodyMemberClrNames` (called `CollectPresentNavClrNames` until #544 gave it a second caller), which reads the **root object's members only** - `deepWriteNavPropsToStrip` holds properties of `TModel`, so a same-named member of a nested value names nothing. A lookup TABLE, not a `FindClrPropertyByEdmName` call per body key: that helper memoizes on `(Type, string)` process-wide keyed by the exact string, so calling it with client-supplied names grows an unbounded cache (`PATCH` already does; pre-existing, not widened). Two overloads because the two branches hold different things - `JsonElement` for the collection POST and PUT's open-types branch (the **prepared** body, which is what the binder sees), raw UTF-8 over #456's existing buffer for PUT's streaming branch, whose `JsonException` is **swallowed** exactly as `ContainsODataBindAnnotation(ReadOnlySpan<byte>)`'s is so `DeserializeAsync` stays the sole author of the `Path: $` message (#389 L1). **`PATCH` was already correct and is untouched** - its `continue` fires while iterating the body's own properties, so it can only ever withhold what the body carried. The collection **POST** changed alongside PUT and is a **separate breaking change**: it has nulled unnamed navigations since 1.0.0, and leaving one verb gated with the other unconditional would put back the per-verb write-path divergence this milestone spent ten PRs removing. #504's actual purpose is intact - a client-sent nested graph is still stripped on every verb.

**It covers `PUT`/`PATCH` because deep UPDATE was documented out of scope and never enforced (#457).** Two spec features, not one: deep insert is §11.4.2.2 and is **POST-only in the spec**, so the old `AllowDeepInsert` name was correct for what the flag did; deep update - a nested graph in `PUT`/`PATCH` - is the separately named 4.01 §11.4.3.1, an Advanced-conformance item, and `docs/deep-insert.md`'s "Deep update is out of scope, and enforced" section has declared it out of scope since 1.0.0 (it was cited here by line number, which had already drifted). The declaration was never backed by code: `deepWriteNavPropsToStrip` was declared **inside** `if (source.HasPost)`, so STJ bound the nested values on the update verbs too and `PUT` forwarded them to the handler while `PATCH` bound them into the delta (measured: `GetChangedPropertyNames()` contained both `Children` and `PrimaryChild`). So this is **enforcement of an already-documented scope decision**, not a widening of the flag past its name - and once one flag governs both features a name saying only "insert" describes one of the two, hence the rename (the old names survive as `[Obsolete]` forwarding properties on `EntitySetProfile` and `EntitySetDefaults` over the same storage; the 1.5.0 `PackageValidation` baseline rejects removal with `CP0002` and this repo has no suppression file). **`PATCH` withholds rather than nulls, and the distinction is load-bearing**: `Delta<T>` is a change SET, so a nulled navigation is still named by `GetChangedPropertyNames()` and still written by `delta.Patch(existing)` - turning a graph the client sent into an unrequested relationship CLEAR - and a navigation in the delta contradicts the subsystem it feeds (`Delta<TEntity>` and `DeltaMappingCompiler` are scalars/structural only). The set was **hoisted, not copied**: one `deepWriteNavPropsToStrip` above all three `if (source.HasX)` blocks, plus `deepWriteNavClrNames` (a CLR-name projection of that same array, for the PATCH loop which already holds a `PropertyInfo`). The setter filter (`p.SetMethod is not null`) is not a hazard for `PATCH` - `Delta<T>.TrySetPropertyValue` only tracks properties with a public getter AND setter - though the "so setter-less properties are excluded from the set" premise that claim was hung on is false; see #506 above. Deliberate residual: the `200` echo on `PUT`/`PATCH` still omits un-expanded navigations unconditionally even when opted in, unlike the `201` on POST - #457 is about what the handler receives, and widening the echo is a separate wire-shape change with its own #240 consequences.

**A scanner that reads the body differently from the binder is a FAIL-OPEN, and three configurations made it one (#511).** Two raw-UTF-8 span scanners shadow `JsonSerializer.DeserializeAsync(Stream)` on the buffered write paths - `ContainsODataBindAnnotation(ReadOnlySpan<byte>)` (#456, `PUT` and the nav-POST create route) and `CollectPresentBodyMemberClrNames(ReadOnlySpan<byte>, …)` (#506, `PUT`; named `CollectPresentNavClrNames` at the time) - and both constructed a **default** `Utf8JsonReader` while the binder reads with the registration's serializer options. Each scanner **swallows** its `JsonException`, correctly, so `DeserializeAsync` stays the sole author of the malformed-body message (#389 L1's `Path: $`); the swallow's safety argument - *"a body this reader cannot finish is a body the deserializer is about to reject"* - holds **only while the two readers accept the same bodies**. Where they diverge the scanner throws on a body the binder then binds, the throw is swallowed, and the scan reports **"nothing found"**: the strip does not fire and the annotation is discarded under a `200`/`201`. **Three measured manifestations.** (1) A leading **UTF-8 BOM**, needing no configuration at all: `Utf8JsonReader` throws at its first byte while `DeserializeAsync` *and* `JsonDocument.ParseAsync` both skip it - so `PUT EF BB BF {…"lines":[…]}` reached the handler with the graph **unstripped**, and the same bytes carrying `category@odata.bind` answered `200` on `PUT` and `201` on nav-POST where the collection POST said `501`, recreating exactly the per-verb divergence #456 exists to remove. (2) A **non-case-preserving `PropertyNamingPolicy`**: `deepWriteNavByBodyName` was keyed by `ResolveEdmName` (deliberately policy-free: `$metadata` advertises the CLR/EDM identifier whatever casing payloads use - OData JSON Format, not a Part 1 clause; Part 1 has no §4.4) plus the CLR name under `OrdinalIgnoreCase`, and camelCase differs from the CLR name only by case - so the comparer hid the divergence for the one policy anyone had configured, while `SnakeCaseLower`/`KebabCaseLower` did not (measured: nav `BackOrders`, body `back_orders`, bound and **unstripped**). (3) **Host-relaxed JSON options**: `startupJsonOptions` copies the host's `Http.Json` options, so the binder honours `ReadCommentHandling.Skip`, `AllowTrailingCommas` and a raised `MaxDepth`; the default reader dies at the first such token and - because the throw is swallowed - the scan **stops there**, so every navigation and every annotation named *after* it is invisible. **The fix is `CreateBinderParityReader`**, the one place either scanner gets a reader: it skips a leading `EF BB BF` (which **closes** a divergence rather than widening acceptance - every other reader on the write path already accepted it) and derives `AllowTrailingCommas`/`CommentHandling`/`MaxDepth` from the serializer options, which is precisely what `JsonSerializerOptions.GetReaderOptions()` derives internally for `DeserializeAsync`. .NET 10's `AllowDuplicateProperties` is deliberately **not** derived - `OhData.AspNetCore` multi-targets `net8.0`, where the member does not exist, and the residual divergence runs the safe way (a host enabling duplicate-rejection makes the binder stricter than the scanner). **(2) was fixed structurally, not by adding a third key.** `PropertyNamingPolicy?.ConvertName(...)` as an extra key would close one policy and not the class, which is *two things that must agree, derived independently* - #454's exact shape, in this same release. The table's primary key is now read **off the contract the binder resolves**: `JsonTypeInfo.Properties[].Name` is by construction the string System.Text.Json matches a body key against, whatever produced it (policy, `[JsonPropertyName]`, a resolver modifier, a source-generated contract), so no second derivation is left to drift. `TryResolveWriteContract` resolves it on a **probe copy** of the options, mirroring `OpenTypeJsonOptions.ValidateOrThrow`, because resolving a contract calls `MakeReadOnly()` and `MapAll` must stay free to keep configuring the real instance (`PrimeNavSuppression` states "resolves no `JsonTypeInfo`" as an invariant, and `OpenTypeModifierOrderingTests` exists because the modifier order is load-bearing); it pairs `JsonPropertyInfo.AttributeProvider` back to a `PropertyInfo` with **`HasSameMetadataDefinitionAs`, never `==`** - `PropertyInfo` equality also compares `ReflectedType`, and for an *inherited* member the two reflection walks disagree about it, which is #462's third defect measured on .NET 10.0.11 and would appear here as an inherited navigation silently losing its contract key. The comparer follows the binder too (`PropertyNameCaseInsensitive`, read rather than assumed - the "unconditionally" in #506's note above was inherited from the host's `JsonSerializerDefaults.Web`, not set by the framework), and the EDM/CLR keys **stay** as non-overwriting aliases because `FindClrPropertyByEdmName` is what `PATCH` resolves through and dropping them would trade a per-host divergence for a per-verb one. On a default host every alias collapses onto the contract key under the comparer, so nothing shipped moves. `DeepInsertTests` pins all three manifestations plus both fail-closed directions (a named navigation is still stripped under each configuration) and both `Path: $` invariants. The residual #511 left open - the collection POST parsing with a default `JsonDocumentOptions` - is **closed by #514**, below.

**The `JsonDocument` parse sites read the body the way the binder does too (#514).** #511's rule applied to the two raw-UTF-8 scanners; the same divergence survived at the three places the write path materialises a body with `JsonDocument` - the collection `POST`, and `PUT`'s and the nav-POST route's **open-types** branches - each of which used a **default** `JsonDocumentOptions` while `startupJsonOptions` carries the host's `ReadCommentHandling`/`AllowTrailingCommas`/`MaxDepth`. **Measured**: with the host at `Skip` + `AllowTrailingCommas`, `{"Id":1,/*c*/"Name":"Ada",}` answered `200` on `PUT` (which streams into the binder) and `400` on the collection `POST` - the per-verb divergence #456 exists to remove, one option over. Unlike #511 it fails **closed** (the stricter reader rejects rather than silently disabling a guard), which is why it was a consistency defect and not a safety one; leaving it in place under the rule #511 had just established was the actual cost. `CreateBinderParityDocumentOptions` is the one place those three sites get their options, deriving the same three members from the same source and for the same reason (`JsonSerializerOptions.GetReaderOptions()`), with .NET 10's `AllowDuplicateProperties` deliberately not derived on the same `net8.0` grounds. **`OpenTypeJsonOptions.RewriteWithoutUnbindableKeys`' re-parse had to move with them**: it is a *third* reader over the same body, and once `ParseAsync` honours a raised `MaxDepth` a body it accepts would be rejected by a default-options re-parse - a divergence the fix would have **created** rather than merely exposed, so it is closed in the same change. Residual, unmeasured and left: `Utf8JsonWriter`'s own 1,000-level depth ceiling sits below a host `MaxDepth` raised past it, which would surface from that rewrite as a 500 on a registration with an open complex type. `WriteBodyContractTests` pins the collection POST, both open-type branches, and both directions of the `MaxDepth` derivation.

**Client-supplied body keys never reach the memoizing name helper (#510).** `ODataPropertyNaming.FindClrPropertyByEdmName` memoizes on `(Type, string)` in a **process-wide** `ConcurrentDictionary` keyed by the caller's exact string, and the `PATCH` delta loop called it once per **body property name** - so a caller could grow that dictionary without bound by sending bodies full of distinct unmatched keys, each a permanent entry for the life of the process. The lookup is what caches, not the result. No single request costs anything measurable; the growth is cumulative and never reclaimed, and it is out of line with the posture recorded above for `OpenTypeJsonOptions`' `ValidatedKeys` (1024 entries, non-ASCII only). #506 had already avoided extending the same exposure to `PUT`/`POST` by building `deepWriteNavByBodyName`; `PATCH` now has the equivalent, `patchPropByBodyName`, so the names it can encounter are bounded by the **model** rather than by the request. It is **behaviourally identical to the call it replaces, to the letter**: same reflection walk, EDM name then CLR name as non-overwriting aliases (which is exactly that helper's two-stage `FirstOrDefault`, since insertion follows `GetProperties()` order and `TryAdd` keeps the first writer), and `OrdinalIgnoreCase` **unconditionally** - matching the helper rather than the binder, because the helper has always matched case-insensitively regardless of `PropertyNameCaseInsensitive` and following the binder here would change what `PATCH` binds. Deliberately **not** keyed off `JsonTypeInfo.Properties[].Name` the way #511 keyed the deep-write table: that would make `PATCH` start binding names it does not bind today (a `snake_case` body key against a PascalCase property), which is a real per-host divergence but a separate behaviour change that does not belong inside a memory fix. That separate change is **#536, below** - the identical-by-construction property above still holds for the startup-sourced strings the table is built from, and the aliases it describes are still there; what changed is that a contract key now sits in front of them. Both halves of #454's guard resolve through the new table, so "the guard validates exactly what the loop applies" stays structural.

**That per-host divergence WAS the defect, and #536 closed it. ⚠ BREAKING.** #510 preserved it deliberately; #511, in the same release, established the rule it violates - *a component that reads a request body differently from the deserializer is a fail-open* - and fixed the deep-write table by keying it off the binder's own contract. `PATCH` was the one route not converted, so #511 manifestation (2) survived there: the table resolved through the policy-free EDM name plus the CLR name while the **value** it binds is deserialized with the registration's serializer options, and under a non-case-preserving `PropertyNamingPolicy` the two disagree. **Measured** with `SnakeCaseLower` against a `FirstName` property: `PATCH {"first_name":"Ada"}` -> `200`, delta empty, nothing changed. camelCase differs from the CLR name only by case, so the `OrdinalIgnoreCase` comparer hid it for the one policy anyone had configured - which is precisely why #511 measured `SnakeCaseLower` and `KebabCaseLower`. Direction: fail-**closed** on the write, so data loss under a `200` rather than an unauthorized mutation; the mirror of #511's direction, and still a silent wrong answer. The fix is #511's, applied to the second table: primary key from `JsonTypeInfo.Properties[].Name`, resolved through the same `TryResolveWriteContract` probe **copy** of the options (resolving a contract calls `MakeReadOnly()`), pairing `JsonPropertyInfo.AttributeProvider` back to a `PropertyInfo` with `HasSameMetadataDefinitionAs` and **never** `==` - #462's third defect, and here it would leave an inherited property carrying the unfixed defect on its own (verified: restoring `==` fails exactly the two inherited cases and nothing else). The EDM and CLR names **stay** as non-overwriting aliases, so `FindClrPropertyByEdmName` parity is kept and a default host moves nothing. **The comparer stays `OrdinalIgnoreCase` unconditionally and does NOT follow `PropertyNameCaseInsensitive` the way `deepWriteNavByBodyName`'s does** - the two tables answer different questions. That one shadows a separate reader, so a table wider than the binder strips a navigation the binder never bound (#506's destruction case); this one has no reader to shadow, because `PATCH` enumerates the body's own members and deserializes each value individually, so the table **is** the matcher for the root object. What moves on an affected host: `PATCH` binds body keys it used to discard, and - since both halves of #454's guard resolve through this table - the entity **key** named in its policy spelling is now seen, so a mismatch answers `400` (target `key`) where it was silently dropped. An `Ignore()`d property is *removed* from `typeInfo.Properties`, so it gains no contract key and cannot become newly bindable. `Issue536PatchBinderContractTests` pins both policies, the inherited property, the key guard, the alias survival, the `Ignore()` bound, and a default-host no-movement control.

**The strip set is the profile-declared navigations UNIONED with the EDM's (#461)** - the write-side twin of #446, and the same "the EDM is the authority on what is a navigation" subtraction pointed at `deepWriteNavPropsToStrip`. It used to read `source.NavigationPropertyNames` alone, so a navigation the `ODataConventionModelBuilder` discovered but the profile never declared with `HasOptional`/`HasRequired`/`HasMany` was **not in the strip set at all**: STJ bound it and it reached `Post` intact with `AllowDeepWrites` at its default of `false`, so a handler doing `db.Add(model); SaveChanges();` persisted nested rows nobody opted into. The exposed shape is the most ordinary one there is - **a profile that declares no navigations at all**, over `public Customer? Customer { get; set; }`. `NavigationPropertyNames` itself is still **not** re-sourced from the EDM (Model B's DB/DL partitioning depends on its "declares nothing" category; see #446's note), and `deepWriteNavPropsToStrip` is the only write-side consumer - the other `NavigationPropertyNames` reads are all read-path (`pushdownExpandNavs`, `ResolveNavTreatment`, `ResolveExpandPagingNavigations`, the #313 ceiling). `Issue440UndeclaredConventionNavWarningTests.Symptom3_*` pins it, on the *existing* #440 fixture (`W440OrderProfile`, which declares nothing) with a `Post` handler added - asserted **at the handler**, because #240 omits every EDM navigation from the POST echo whether it was stripped or not, which is why this was invisible on the wire. #440's startup warning gained the write-path sentence in the same commit.

**`@odata.bind` anywhere in a write body is `501 Not Implemented` on EVERY verb (#456).** Not implemented at all, and `AllowDeepWrites` does not change it. The check used to live *below* `PrepareWriteBody`'s `OpenTypesActive` early return, so on any registration without an open complex type - the majority - `PUT`, `PATCH`, the navigation-POST create route and the structural-property writes accepted the annotation with `200`/`201` and **silently discarded** it: the client asked to bind a relationship, got a success, and nothing happened. The check now runs *above* that gate (it needs nothing the gate protects - it is a pure `JsonElement` walk over a body the caller already materialised), which covers `PATCH`, the property writes and every bound/unbound action parameter. **That hoist alone is NOT sufficient**, and the reason is worth keeping: `PUT` and the nav-POST create route never call `PrepareWriteBody` on the non-open path at all - they stream `ctx.Request.Body` straight into `JsonSerializer.DeserializeAsync`, so there is no `JsonElement` to walk. Those two buffer the body once (`BufferRequestBodyAsync`) and scan the raw UTF-8 with a `Utf8JsonReader` (`ContainsODataBindAnnotation(ReadOnlySpan<byte>)`, matching the `JsonElement` walk's semantics including escaped names), then hand the buffer to the **same** `DeserializeAsync(Stream)` overload as before. Going through `JsonDocument` instead is the #389 L1 regression: the two readers word a malformed body differently (`Path: $` versus not), which `OpenTypeDefaultOnIsByteIdenticalTests` exists to catch and which `DeepInsertTests.WritesWithoutTheAnnotation_StillSucceed_AndPutStillWordsAMalformedBodyItself` now pins directly. The collection POST keeps its own earlier, unconditional check because its message is richer (it names the entity set and mentions `AllowDeepWrites` for the adjacent case - a client that meant to CREATE the related entity inline rather than link an existing one). Residual, deliberate: the property-write route scans the `value` member, not the whole envelope, and the `$ref` bodies are not scanned - `@odata.bind` has no meaning in either place.

**`BufferRequestBodyAsync`'s capacity hint is CLAMPED to 81,920 bytes, and must stay clamped.** `Content-Length` is a client claim that arrives in the request head, *before* any body byte does; pre-sizing the buffer from it hands an unauthenticated caller a remote allocation primitive - declare 30 MB, send one byte, never finish, repeat across N connections, and the server has committed N x 30 MB against N bytes of traffic. The streaming path this replaced allocated in proportion to bytes **received**, so honouring the header would have been a regression, not a wash. 81,920 is `Stream.CopyTo`'s own default buffer size (an honest small body still lands in one right-sized allocation) *and* under the 85,000-byte LOH threshold (a bogus hint costs a collectable gen0 array). Beyond it `MemoryStream` just doubles. **The collection POST is not a precedent for the hint** - only for the materialisation: `JsonDocument.ParseAsync` grows incrementally from pooled buffers and never reads `Content-Length`. `DeepInsertTests.Put_BodyLargerThanTheCapacityHint_IsScannedAndBoundInFull` guards the growth path (verified to fail when the scan is truncated to the cap). **`PipeReader`/`ReadOnlySequence` was considered and does not win**: it avoids a copy, not the materialisation (the pipe's pooled segments hold the same bytes), the accumulate-everything shape is the documented unbounded-buffering pattern, and feeding those bytes to `DeserializeAsync(Stream)` - required for the `Path: $` invariant - would mean either a different overload or a hand-written stream adapter. A pass-through scanning stream *would* preserve streaming and is rejected on correctness: it makes the answer depend on where in the body the annotation sits, so `{"Id":"notanint","x@odata.bind":1}` would 400 on PUT while the collection POST says 501 - reintroducing the per-verb divergence #456 exists to remove.

**A buffered write body now has an OhData-level ceiling by default, and it is Kestrel's own number (#474). BREAKING for one configuration.** What used to bound it was the HOST's limit alone: #203's filter does *both* of its jobs - the `Content-Length` fast-reject **and** setting Kestrel's per-request `MaxRequestBodySize` - only when `OhDataBodyLimitMetadata` is attached, and that metadata existed only when a profile or `EntitySetDefaults` set `MaxRequestBodyBytes`, **which defaulted to `null` at both levels**. So on a default configuration neither half ran, and if the host raised or disabled its own `MaxRequestBodySize` - routine for an app that also accepts uploads - nothing in OhData bounded the materialisation at all. Not introduced by #456 (the collection POST has materialised whole bodies under the same (non-)guarantee since 1.0), but shared by `PUT` and nav-POST since it, and the #203 commentary read as more protective than the code was.

`EntitySetDefaults.MaxRequestBodyBytes` now defaults to `EntitySetDefaults.DefaultMaxRequestBodyBytes` = **30,000,000**, which is **Kestrel's own documented default** and therefore *not an invented number* - the failure mode `MaxExpandTop` had to undo (#313). Choosing it means a **default host sees no behaviour change**: the same byte count was already refused one layer down, and all that moves is which layer reports it (OhData's `413` envelope instead of Kestrel's). The behaviour change lands on exactly the exposed population - a host that raised or removed its own limit, which now gets a `413` where a large body used to succeed. Remedy is one line: raise `MaxRequestBodyBytes`, or set it to `null` server-wide to restore "the host's limit is the only limit". There is no per-profile "unlimited" - a profile-level `null` means *inherit*, as it does for `MaxExpandTop`. The group filter also **falls back** to the registration's copy of the server-wide value (`OhDataRegistration.DefaultMaxRequestBodyBytes`) for routes that carry no per-entity-set metadata, i.e. the **unbound** actions, which belong to no profile and so had nothing to resolve a limit from. **A limit the framework chose may only LOWER the host's own per-request ceiling, never raise it.** #203 assigns `IHttpMaxRequestBodySizeFeature.MaxRequestBodySize` unconditionally, which was right while the value could only come from the adopter - *"this set accepts up to 4 MB"* is a deliberate override and still behaves that way in both directions. Left unconditional under a non-null default it would **raise** the ceiling on a host that had deliberately lowered Kestrel's below 30 MB: **measured**, a 1,000,000-byte host limit became 30,000,000 on every OData write, i.e. a security fix quietly undoing a hardening step on a registration that configured nothing. The filter now clamps with `Math.Min` when the resolved limit *is* the framework's constant. "The framework chose it" is read off the value rather than tracked through a configured/not-configured flag; the only case that misreads is an adopter explicitly setting exactly 30,000,000 on a lower-limit host and wanting it raised, and clamping is the safe direction there. A **null** host limit still gets the assignment - that is #474's central case. `RequestBodySizeFeatureTests` exists because `Microsoft.AspNetCore.TestHost` supplies **no** `IHttpMaxRequestBodySizeFeature` at all (measured - absent from `HttpContext.Features`), so #203's own suite only ever exercised the `Content-Length` arm; it installs a controllable feature through an `IStartupFilter` and pins all four outcomes.

This is a different question from `BufferRequestBodyAsync`'s capacity-hint clamp and neither substitutes for the other: the clamp is about a *declared* length driving an allocation before any byte arrives, this is a ceiling on the bytes actually received. `WriteBodyContractTests` pins the default, the profile override in the raising direction, the server-wide opt-out, and the unbound-action fallback.

**Request bodies are validated against the EDM's own nullability, and the CLR is no longer a second opinion about it (#355).** A `null` for a structural property the framework's own `$metadata` declares `Nullable="false"` reached the handler unvalidated, and the persistence layer's rejection surfaced as a generic **`500`** - *measured on the shipped TestBench*, `POST /v1/Movies {"Title":null}` → `500 InternalServerError` from EF's *"Required properties '{'Title'}' are missing"*, for a violation the framework could see at its own boundary before any handler ran. `BuildEdmRequiredProperties` asks the **EDM**, once per type at startup, and `ValidateEdmRequiredProperties` / `ValidateEdmRequiredDelta` answer `400` (`InvalidBody`, `target:` the property) on the collection `POST`, `PUT`, `PATCH`, the navigation-`POST` create route and the structural-property writes. **The property-write route is the reason "ask the EDM" is not a stylistic preference**: it already had a nullability check, built on `IsNullableClrType`, for which *every reference type is nullable* - so a `Nullable="false"` string sailed straight through it and `PUT .../Name {"value":null}` was a `204`. Two independently derived answers to one question, which is the hazard #454/#458/#511 each record; there is one answer now, and the CLR one survives only as the fallback for a property the EDM does not declare (an `AdvancedConfigure` model may omit one).

Four deliberate exclusions, each of which would otherwise reject a legal request: the **key** (every EDM key is `Nullable="false"` and a server-generated key is routinely omitted on create - taken from `edmType.Key()` so entity and navigation-child types are answered alike); a **non-nullable value type** (`int Year` cannot hold null, so a JSON `null` is already a `JsonException` → `400` worded by the deserializer, and checking it would cost a boxing read to answer a question with one possible answer); a member no readable CLR property backs; and anything the EDM does not declare at all, which is what makes `Ignore()`d properties exempt for free. `PATCH` and the property writes check only what the body **named** (a `Delta<T>` is a change set; an absent property is "leave it alone"). Per-entity-set opt-out `RequestBodyNullabilityValidationEnabled` (default `true`, inherits `EntitySetDefaults`) for a service whose handler legitimately supplies a value the client is not expected to send. **BREAKING** for any adopter relying on a `null` required property reaching the handler. Deliberate residual: nullability *inside* a nested complex value is not checked - that needs its own recursion and cycle decisions. `#356`'s `DbContextLifetimeTests` changed with this: its poison step used the very `500` #355 removes, and now asserts the `400` and poisons the change tracker with a duplicate primary key instead.

**#355 also refused an OMITTED property on `POST`/`PUT`, and that leg is gone (#544/#545, BREAKING - it un-breaks).** It cited **§11.4.2**, which requires nothing of the kind: its only MUST-fail is *"The service MUST fail if unable to persist all property values **specified in the request**"* - about values sent. §11.4.2 also permits omission outright, for exactly TWO categories rather than the broad set once claimed here: *"Properties computed by the service (annotated with the term `Core.Computed` ...) and properties that are tied to properties of the principal entity by a referential constraint, can be omitted and MUST ignored if included in the request."* **No clause in Part 1 mandates a `400` for an omitted property.** The nearest one, **§11.4.3**, is PUT-only and prescribes the OPPOSITE remedy: *"Missing non-key, updatable structural properties not defined as dependent properties within a referential constraint MUST be set to their default values"* - what the service STORES, which OhData leaves to the handler that owns persistence. **An earlier revision of this file quoted §11.4.3 as conditioning the refusal on *"no service-generated or default value"*; that phrase is NOT in the specification** (the only "service-generated" hit in Part 1 is §11.3.1, delta links), and the framework could not have evaluated it anyway: `ODataConventionModelBuilder` writes no `Core.Computed` annotation (measured: **zero** vocabulary annotations on any property, and `[Required] string?` is byte-identical in CSDL to `string = null!`), and a CLR initializer is invisible to the EDM. `Microsoft.AspNetCore.OData` lands exactly here too - `ODataResourceDeserializer.ApplyStructuralProperties` loops over *payload* properties only with no reverse pass, and nothing on the ENTITY-PAYLOAD path validates required presence, while `ReaderValidationUtils.ValidateNullValueAllowed` rejects an explicit `null`. (Read that narrowly: `Microsoft.OData.Core` 8.4.4 does contain a `ValidateRequiredProperty`, but its adjacent resource string is `ODataJsonServiceDocumentDeserializer_MissingRequiredPropertyInServiceDocumentElement` - service documents, not entity payloads.)

**What that resolves is #545, and it is the whole point.** *"The check reads the BOUND INSTANCE"* made the wire answer depend on the CLR initializer: three properties `$metadata` describes **identically** as `Nullable="false"` answered differently on an omission. Measured, before → after: `string X = ""` **201 → 201**; `string X = null!` **400 → 201**; `int Year` **201 → 201** - and all three still `400` on an explicit `null`, the middle row by this rule and the last by the deserializer. One rule, derivable from the wire, independent of `= ""` versus `= null!` and of CLR value-versus-reference. #355's own defect is untouched: `POST {"Title":null}` is still the `400` that replaced EF's `500`.

**Mechanically it is an intersection, not a rewrite**, which is what makes "nothing newly rejects" structural rather than argued. `ValidateEdmRequiredProperties` still reads the bound instance and now `continue`s on any property the body did not name, so the condition is a strict narrowing of the shipped one. "Did the body name it" is answered by **`CollectPresentBodyMemberClrNames`** - #506's scanner, renamed from `CollectPresentNavClrNames` and shared rather than transcribed, because the deep-write strip and this gate ask one question of two tables and a second copy of that walk is the independently-derived-second-model hazard #454/#458/#511 each record. It is not a fourth scanner either: every site already had the bytes (`postPrepared.Body`, `putPrepared.Body`, #456's `putBuffered`/`navBuffered`), and on the streaming branches it is `CreateBinderParityReader`, so #511's parity holds. The required-property table is not `deepWriteNavByBodyName`'s twin, it is **the same builder** - `BuildBinderBodyNameTable`, which #544 extracted from the deep-write strip's inline block and which all three sites (the strip's navigation table, and the required-property tables for `TModel` and for the navigation-POST child type) now call through `Array.ConvertAll`. Two verbatim copies of that derivation is the same hazard one level down, and this site has already realised it: **#536 exists only because #511 rebuilt one of these tables and not the other.** So the contract key from `JsonTypeInfo.Properties[].Name`, the `HasSameMetadataDefinitionAs` pairing and the EDM/CLR aliases are stated once. The comparer **follows the binder** (unlike `patchPropByBodyName`'s, which *is* the matcher and is deliberately NOT merged in), and both directions matter: for the strip a table WIDER than the binder strips a navigation the binder never bound (#506's destruction case), while for this gate a table NARROWER than the binder lets `{"uninitialized":null}` bind to null and slip through (fail-OPEN). `PATCH` and the structural-property writes were **already** withholding-based and are untouched. The `400` message drops *"or omitted"*. `Issue544NullabilityOmissionTests` pins the three-row table on the collection `POST`, on `PUT`'s streaming and open-type branches, on the open-type `POST` and on the nav-`POST` route - all four fixtures carry all three shapes - plus the renamed and case-differing spellings and the nested-member bound. **The table's contract key has its own tests and they are the load-bearing ones**: every required property in the shapes above is a SINGLE WORD, for which `SnakeCaseLower` differs from the CLR name only by case and so collapses onto the `OrdinalIgnoreCase` CLR alias - measured, the whole `TryResolveWriteContract` branch could be deleted with all 21 of the original tests and the entire 2,776-test suite still green. The multi-word `N544Stamped` fixture is what closes that: with the branch ablated `POST {"created_by":null}` answers **201 with the handler reached and `CreatedBy == null`**, a fail-OPEN, and five tests fail. `InheritedStamp` is the `HasSameMetadataDefinitionAs` half (#462's third defect) and carries `[Required]` because a bare NRT `= null!` declared on a BASE class comes out `Nullable="true"` in the CSDL - measured - and would never reach the gate; restoring `==` fails exactly those two cases and nothing else.

**Batch-aware `$expand` via an additive `BatchHandler`.** `HasMany`/`HasOptional`/`HasRequired` accept an optional `batchGetAll`/`batchGet` delegate (`IReadOnlyList<TKey> → ILookup<TKey,TNavigation>` or `IReadOnlyDictionary<TKey,TNavigation?>`) alongside the existing per-entity `getAll`/`get`. When present, `$expand` calls it once per expanded property per page instead of once per parent entity (collapsing N×P sequential calls to P). A per-entity `Handler` is auto-derived from the batch delegate by calling it with a single-key list, so the standalone nav-GET route, `$count`, and `$ref` keep working without a second handler. Falls back byte-identically to the per-entity path when no batch handler is registered.

**Entity-id URLs use a shared canonical key formatter.** `Location`/`Content-Location`/`OData-EntityId`/`@odata.id` values built from a CLR key (POST, and the parsed key on `GetById`/`PUT`/`PATCH`/`$ref`/nav-POST responses) go through `ODataEntityKeyUrlFormatter`, which single-quotes and percent-encodes string keys and doubles embedded quotes - the same escaping `ODataKeyParser` expects on the way back in. `int`/`Guid`/other non-string keys format unchanged.

**PATCH cannot move the entity key, and the guard validates exactly what the loop applies (#454).** The key-mismatch guard and the delta-building loop used to consult different sets: `TryGetJsonProperty` returns the FIRST case-insensitive match and stops, and matched on the key's CLR name, while the loop resolves EVERY body property through `FindClrPropertyByEdmName` (case-insensitive **and** `[JsonPropertyName]`-aware) into a last-writer-wins `Delta<T>` with no key exclusion. Three bodies therefore rewrote the key and returned `200`: `{"Id":1,"Id":999}`, `{"id":1,"Id":999}`, and - with a renamed key - a single `{"code":"ZZ"}`, which the CLR-name lookup could not see at all. Both halves now resolve through `FindClrPropertyByEdmName` against the same CLR property: every occurrence is validated, and the key is **never written into the delta**, so immutability is structural rather than a consequence of the guard having seen every occurrence. A mismatch is **rejected** with `400` (target `key`) rather than silently dropped - consistent with the pre-existing single-occurrence 400 and with the structural-property write route's `KeyImmutableError`. **PUT is structurally immune** and must stay that way: it deserializes to `TModel` first and reads the key off the materialized model (`InvokeGetKeyString`), so STJ has already collapsed duplicates to the value the handler will receive. `KeyImmutabilityTests` pins both halves, including two PUT tests whose only job is to fail if PUT is ever refactored toward raw-`JsonElement` parsing.

**POST/PUT/PATCH deserialize the request body by hand.** All three read and JSON-deserialize the body manually (rather than an ASP.NET Core minimal-API bound parameter) so malformed JSON, non-object bodies, and non-JSON `Content-Type` values return the OData error envelope (400/415) instead of ASP.NET Core's implicit binder short-circuiting with an empty body. This is also why PATCH's non-object-body case (JSON array/string/number/bool/null) is caught explicitly - `JsonElement.EnumerateObject()` throws `InvalidOperationException` for non-`Object` `ValueKind`, which is now caught and mapped to 400. **The `$ref` write route was the one exception, and is not any more (#455).** `handleAddOrSetRef` called `odataIdEl.GetString()`, which throws `InvalidOperationException` for every `ValueKind` except `String` and `Null`, and its only catches are `JsonException`/`FormatException` - so `{"@odata.id": 123}`, well-formed JSON that is merely semantically wrong, escaped to the group filter as a generic **500**. It is gated on `JsonValueKind.String` now and answers the same 400 envelope the missing-`@odata.id` case does. `JsonValueKind.Null` is rejected **too**, deliberately: it never threw - `GetString()` returned null and the `?? ""` handed the profile's `addRef`/`setRef` delegate an *empty* entity-id under a `204`, which is the silent-success failure mode the rest of the write surface exists to prevent. §11.4.6.2 wants the entity-id of the entity to link; a null member names none, the same client error as omitting it. `ActionBodyGuardTests` pins both, and asserts the delegate was never reached rather than only the status.

**Open types are EDM-driven, complex-only, attribute-free, and ON BY DEFAULT (#389).** `OhDataRegistration.OpenTypesEnabled` defaults to `true`; `AddOhData(o => o.WithOpenTypes(false))` is the escape hatch, and with it `MapAll` never builds the container map, `OpenTypeJsonOptions.Build` returns the base options reference-equal, and no write-path validation runs — that registration is byte-identical to pre-#389. Default-on because a complex type with a dictionary member **is** an open type: the CSDL has always said `OpenType="true"` and omitted the container, so a nested wire shape made `$metadata` and the payload disagree, and `Microsoft.AspNetCore.OData`'s `ODataResourceSerializer.AppendDynamicProperties` reads the same annotation and flattens with no opt-in flag at all. The hazard that justified opt-in is unchanged and is mitigated by a **startup warning**: flattening *re-binds* an existing adopter's body — once the container is extension data it is no longer a declared property, so `{"Meta":{"Bag":{...}}}` becomes a dynamic key named `Bag`, and the echo of that mis-bound value is byte-identical to the correct one (so it is **not** detectable by diffing responses). `OpenTypeJsonOptions.WarnWireShapeIsFlat` therefore logs one `Warning` per open complex type at `MapOhData()`, naming the CLR type and the container member and pointing at `WithOpenTypes(false)`; a model with no open complex type logs nothing. `OpenTypeJsonOptions` reads `ODataConventionModelBuilder`'s own `DynamicPropertyDictionaryAnnotation` (via `EdmAnnotationExtensions.GetDynamicPropertyDictionary`) for every complex type the EDM marks `IsOpen`, and layers one more `TypeInfoResolver` modifier onto `effectiveJsonOptions` that sets `JsonPropertyInfo.IsExtensionData = true` on exactly that member. Ordering: after `IgnoredPropertyJsonOptions.Build` and before the per-request nav-suppression modifier (which derives from these options, so `WithAddedModifier` chains all three) — but the three can never contend for a member. Nav suppression only removes EDM navigations, and a dynamic-property container is a dictionary member the EDM never calls one — **note that the reason this used to be stated as "of which a complex type has none" was itself the #507 defect**: a complex type *can* carry navigations (`ODataConventionModelBuilder` makes one for every entity-typed member of a complex type), and since #507 nav suppression really does remove them from a complex type's contract; the two modifiers still cannot contend, because the container is never among them. The ignored-property map is keyed by `profile.ModelType` (an **entity** type) while `Ignore(...)` takes a root member of that entity, so it and the open-type modifier never see the same `JsonTypeInfo` at all. Ordering is unchanged and still load-bearing: the open-type modifier snapshots `declaredNames` from `typeInfo.Properties` **before** nav suppression removes anything, so a bag key spelled like a complex type's navigation still collides and still hard-fails rather than quietly shadowing it — the same argument the `[JsonIgnore]` case rests on. The member is matched by `MemberInfo.HasSameMetadataDefinitionAs`, **not** `==`/`ReferenceEquals` — the builder's annotation and STJ's `AttributeProvider` come from independent reflection walks that disagree on `ReflectedType` (the builder can report a *derived* type there), so `PropertyInfo` equality returns false for the same member; `HasSameMetadataDefinitionAs` is *not* whole-member identity (it matches across generic instantiations), and what makes it safe is that the container is only ever resolved by walking the looked-up type's own CLR base chain against a map keyed by `DeclaringType`. Three behaviors that ride along: a dynamic key that is not an OData simple identifier is rejected with 400 (`OpenTypeJsonOptions.ScanWriteBody`, walked over the raw `JsonElement` against `JsonTypeInfo`) on **every** route that binds a body reaching a bag — POST/PUT/PATCH, the property-route writes, the navigation-POST create route, and each bound/unbound **action parameter** (checked per parameter against its declared type, so the `{"paramName": value}` envelope is never treated as a bag) — and the walk descends into the **value** of an accepted dynamic key at every depth, arrays and dictionary-valued declared members included (a `IDictionary<string, TOpenComplex>` member is `JsonTypeInfoKind.Dictionary`, so the walk recurses into its VALUES; its own map keys are declared-member keys, not dynamic property names, and are not policed), since everything below a bag key is stored verbatim; the grammar is the ABNF's Unicode categories (`L`/`Nl` leading, `L`/`Nl`/`Nd`/`Mn`/`Mc`/`Pc`/`Cf` following) counted in **code points**, not `char.IsLetter` over UTF-16 units, so NFD and NFC spellings of the same key cannot get different status codes for any name within the 128-code-point cap (decomposition adds code points, so only a name already at the cap can differ); and **two conditions throw** `InvalidOperationException` from the wrapped `JsonPropertyInfo.Get` (→ 500 + the OData error envelope via the group filter), checked in one pass over the bag per serialized instance. (1) A bag key equal to a declared property name, instead of emitting a duplicate JSON key — matching MS's `DynamicPropertyNameAlreadyUsedAsDeclaredPropertyName`, since the spec does not decide it (CSDL §6.3/§9.3 "uniquely named"; JSON Format defers to RFC 8259's SHOULD) and the condition is systematic rather than per-row (a client cannot cause it — STJ binds a body key matching a declared name to the declared property). (2) A bag key that is **not a valid `odataIdentifier`** — the same grammar the write path applies, so keys are policed identically in both directions (400 in, 500 out) and the container's contents are fully validated rather than merely checked for emptiness. This was widened from a bare `string.IsNullOrWhiteSpace` ("not a name at all"), which had let `"has space"`, `"@odata.type"` and a key of only `Cf` format characters through; the widening is a **deliberate divergence from MS**, which skips the empty key (`ODataResourceSerializer.cs:820`) and polices nothing else on this path. Affordability comes from `IsValidDynamicPropertyNameCached`: an ASCII `SearchValues<char>` + `ContainsAnyExcept` fast path (within `[A-Za-z0-9_]` the grammar reduces to a length test plus a leading-digit test) falling back to the unchanged rune-and-category walk — `IsValidDynamicPropertyNameByRuneWalk`, kept as the normative oracle the tests prove the fast path equivalent to — plus a 1024-entry process-wide cache of validated **non-ASCII** keys only, since an ordinal cache lookup hashes the whole string and so costs *more* than the fast path it would be memoising. Measured in isolation: 4.6 ns/key vs 16.9 naive and 5.4 for the declared-name lookup beside it. **In situ** (BenchmarkDotNet, 1,000 rows × 20 dynamic keys, full-grammar validation vs the whitespace-only check) the widening costs **+4.0%** on repeating ASCII keys — the common shape — at 5.8 ns/key marginal; **+6.1%** (9.0 ns/key) on 20,000 distinct ASCII keys; and **+14.7%** (28.8 ns/key) on 20,000 distinct non-ASCII keys, the only shape that saturates the 1024-entry cache and therefore implies a handler synthesising per-row non-ASCII key names rather than a schema-like vocabulary. An earlier stopwatch harness put this at ~+26% (~56 ns/key); that number is **refuted** and should not be requoted. Neither throw is quoted with the offending key when it is the grammar failure (it can carry control characters into a log line); the collision message does quote it, since a declared name is bounded developer-authored text. The getter now only *inspects* and always returns the same reference, which is what removed the old drop-and-clone machinery (`TryCreateEmptyLike`, the `Activator.CreateInstance` fallback, the read-only degradation) and with it the #389 M2 corner where a pre-seeded container silently lost every write. Comparison is **ordinal**, so a case-differing key does not throw. And a container STJ cannot use as extension data (getter-only, most often) throws from `MapOhData()` rather than being skipped. The per-request gate is `OhDataRegistration.OpenTypesActive` (enabled **and** the EDM really has an open complex type), **not** `OpenTypesEnabled` — and now that the flag defaults to `true`, that EDM half is the whole blast-radius bound; gating on the flag alone left a registration with no open types buffering every PUT body, which changed its malformed-body error message and broke the documented byte-identical no-op (`OpenTypeDefaultOnIsByteIdenticalTests` pins it across every write route and body shape). Entity-root containers and `$filter`/`$orderby` over individual dynamic keys are deliberately out of scope, and `PATCH` of a complex member is whole-value **replace**, not merge; `docs/open-types.md` and `OpenTypeLimitationTests` record all of it.

**Open types, #398 stages 0–2 (entity-root groundwork; the widening itself is stages 3–5 and is NOT done).** Three amendments to the paragraph above. **(1) Two false claims were corrected.** `IsNavVisibleInBaseOptions`' comment said `[JsonIgnore]` removes a member from `typeInfo.Properties`; measured false on .NET 10.0.11 — those members stay in `Properties` with `Get`/`Set` null and a `ShouldSerialize` returning false, so the method's answer comes from the `ShouldSerialize` branch, not the fallthrough. This matters because the open-type modifier snapshots `declaredNames` from that same collection, so a `[JsonIgnore]`d navigation still collides with a bag key rather than being shadowed by one. And `OpenTypeJsonOptions.cs` / `docs/open-types.md` claimed `Delta<T>` "has no mechanism" for routing an undeclared key — false: `Delta<T>` has had a `dynamicDictionaryPropertyInfo` ctor parameter all along (`DeltaOfT.cs:112`), MS supplies it from the EDM in `ODataResourceDeserializer.cs:270-286`, and it was measured working (merge semantics, dictionary creation, `updatableProperties` refusing a withheld name). That claim was the stated blocker for entity roots and it does not exist. **(2) `Ignore()` containment ships, and is a deliberate no-op at complex scope.** `Ignore()` works by *removing* a member in a `TypeInfoResolver` modifier, and extension data captures exactly what a modifier removed — so at entity scope a withheld name would bind into the bag and be echoed back under the withheld name (a write-then-read oracle; measured at raw STJ level). `IgnoredPropertyJsonOptions.BuildIgnoredJsonNameMap` captures the withheld **JSON** names off the *pre-ignore* contract (never re-derived from the naming policy) into `OhDataRegistration.IgnoredJsonNamesByType`; those cross into `OpenTypeJsonOptions` as **data**, checked as a **separate set alongside** `ThrowOnKeysThatCannotBeEmitted`'s `declaredNames` on the read side and dropped from the body on the write side. **The withheld sets carry the BINDER's comparer** (`IgnoredPropertyJsonOptions.WithheldNameComparer` - `OrdinalIgnoreCase` whenever `PropertyNameCaseInsensitive`, i.e. always in production) at the one place they are built and at all three places they are consulted; `declaredNames` stays **ordinal** and the two must never be merged. That merge is what made the containment case-sensitive while body binding was case-insensitive: a body key `secret` against a withheld `Secret` missed `declared` (the member is gone from the contract), missed an ordinal withheld set, and was bagged then echoed - measured on both the write and the read side, and they fail independently. The comparers answer different questions: ordinal for `declaredNames` because only a byte-for-byte repeat is a duplicate JSON key, the binder's for withheld names because a case-differing spelling is the bypass rather than a false positive. It cannot fire today — `Ignore(...)` names a root member of an *entity* type, containers live on *complex* types — and `OpenTypeIgnoreContainmentTests` asserts that no-op explicitly. A write naming a withheld property is **silently dropped**, not 400: the spec does not settle it (Protocol §11.4.2's "MUST fail if unable to persist all property values" turns on "property value" as a term of art that does not clearly cover a name the type does not declare, and no clause contemplates a server that *conceals* a declared property), so it follows MS, which clears `ThrowOnUndeclaredPropertyForNonOpenType` deliberately in `ODataInputFormatter.cs:203`. **(3) `@` is control information — a behaviour change to a shipped path.** Any unmatched key containing `@` at *any* position (JSON Format §4.5 leading form, §18 embedded `Property@annotation` form, and the `a@b`/`x@`/`@` residue, which `@` being `OtherPunctuation` already made ungrammatical) is classified as control information: not policed, and **stripped from the body before binding** by `RewriteWithoutUnbindableKeys`. Stripping is not optional — STJ bags every unmatched member, and the read path's identifier check would then 500 the row forever, which is worse than the 400 it replaces. So `@odata.type` inside a complex value goes **400 → silently ignored**. Declared names are matched first (a `[JsonPropertyName("weird@name")]` member still binds), `@odata.bind` is still 501 on **every** write route (that check runs earlier - it was on the collection POST alone for one commit, which turned a 400 into a silent 200/201 on PUT/PATCH/nav-POST/property-writes, and #456 then found that the fix for that had been placed below `PrepareWriteBody`'s `OpenTypesActive` gate and so only ever ran on a registration with an open complex type; see the `AllowDeepWrites` paragraph for where it lives now and why PUT/nav-POST needed a second, buffered scan), and an `@` key *below* an accepted dynamic key is still 400 (no contract down there; the subtree is opaque stored data). **`OpenTypeModifierOrderingTests` is the tripwire** for the modifier order the whole delegate-safety argument rests on (ignore → open-type → nav-suppression); verified to fail when nav suppression is derived from `startupJsonOptions` instead of `effectiveJsonOptions`. Every open-type fixture added here is an **existing feature's fixture with a container added** (`IgnProduct` gained `IgnSpec.Extras`), not a green-field model built around a bag — #395's suite was green while shipping a CRITICAL defect precisely because every fixture in it was the latter.

**Per-type configuration is resolved for the RUNTIME type, through one shared base-chain walk (#462/#343).** Both serialization substrates resolve the runtime type's contract - the batched collection path hands System.Text.Json an `object`-declared element, and the single-entity path calls `SerializeToNode(value, value.GetType(), ...)` - so **any** per-type map keyed by the exact CLR type silently misses a derived instance, which is an ordinary EF Core TPH shape. That had been fixed three times independently (#293, delegate-backed navigation names) before it was recognised as one defect class. `InheritedTypeConfig`/`InheritedNameSets` (`InheritedTypeConfig.cs`) is now the only route: `InheritedNameSets.Resolve(Type)` walks `Type.BaseType` (stopping at `object`, interfaces deliberately not walked) and **unions** every entry on the chain, memoized per runtime type; `InheritedTypeConfig.TryResolveNearest` is the other policy, nearest-wins, for a **single-valued** configuration where a derived declaration replaces the base's (`OpenTypeJsonOptions.TryFindContainer`'s `new`-shadowed dynamic-property container - the walk that was already correct and whose comment named the problem). The two policies are not interchangeable: a withheld-name set is a **disclosure boundary**, so a derived profile's own `Ignore(...)` set must not shadow its base's. Structural, not conventional: `IgnoredPropertyJsonOptions.Build`, `OpenTypeJsonOptions.Build`/`ScanWriteBody`/`RewriteWithoutUnbindableKeys` and `OhDataRegistration.IgnoredJsonNamesByType` all take/carry `InheritedNameSets`, whose entire callable surface is `Resolve` + `IsEmpty` - there is no longer a dictionary in scope for a fifth site to write `TryGetValue(typeInfo.Type, ...)` on, and `RuntimeTypeConfigResolutionTests` asserts that by reflection. The **single-contributor** case returns the declared set **by reference**, so each set keeps its own comparer (`WithheldNameComparer` for withheld JSON names, ordinal for CLR names - never merged; see #398 review HIGH-1); only a genuine multi-level union allocates.

Three concrete defects this closed, all reproduced on a **plain GET with no query string**. (1) **#462**, disclosure: `Ignore()`d `Secret` was withheld on the base row of a page and **served** on the derived row, on both the collection and GetById routes. (2) **#343**, unrequested data plus a reachable 500: `GetNavSuppressedOptions` built its suppression set from `edmType.NavigationProperties()` - the **declared** EDM type - so a navigation declared only on a derived EDM type never reached the set, emitted inline with no `$expand` naming it, and 500'd (`JsonException: A possible object cycle was detected`) when two derived instances referenced each other through one. Derived-declared navigations are **suppressed, never served** - JSON Format §4.5.1/§11.2.4.2 require a non-expanded navigation to be omitted, and the clause binds against the declared type (as does `SpliceKeptNavigations`), so such a nav can never be asked for and "serve it" would mean serving it unconditionally; consistent with #293's frozen Model B (which matches the **exact** EDM type and has no opinion about a nav no clause can name) and with #440's omit-rather-than-null split. (3) The **mirror image of #343**, found by the shared fixture and in neither issue: `IsNavVisibleInBaseOptions` compared `PropertyInfo`s with `!=`, which also compares `ReflectedType`, and for an **inherited** navigation on a derived instance the two sides disagree - **measured** on .NET 10.0.11, `FindClrPropertyByEdmName` reports `ReflectedType = RtDerived` while STJ's `AttributeProvider` reports `RtBase`, so `==` is false while `HasSameMetadataDefinitionAs` is true. The loop never matched, the trailing `return false` answered "not visible", and a navigation the client **explicitly `$expand`ed** was silently dropped from every derived row while base rows in the same page kept theirs. Now `HasSameMetadataDefinitionAs`, safe for the same reason `OpenTypeJsonOptions.Build` is: both sides are members of `clrType` or one of its bases, and one type's member list cannot hold two instantiations of a single generic definition.

**`RuntimeTypeConfigResolutionTests` is the fixture the whole area was missing.** Every serialization suite here - ignore, open-type, modifier-ordering, nav-suppression - used fixtures where runtime type == declared type, and the one suite that varies runtime type (`PolymorphicExpandSerializationTests`) gives its derived types only **scalar** members. **Three follow-ons in the same class, and the one that is NOT (#507/#508/#497/#344).** The section above names the class as "a per-type map keyed by the exact CLR type"; the wider statement is **a lookup keyed by something that is not what the thing being looked up actually is**, and three more sites were.

**(1) The key was an ENTITY type while the thing carrying navigations was a COMPLEX type (#507).** `SeedNavSuppressionModel` walked `model.SchemaElements.OfType<IEdmEntityType>()` and `AddNavClrNames` read `edmType.NavigationProperties()` off entity types, so `BuildNavClrNames` computed an **empty set for every complex CLR type**. But `ODataConventionModelBuilder` models an entity-typed member of a complex type as a navigation **on the complex type** (`<ComplexType Name="PxMeta"><NavigationProperty Name="Owner" …`), and `NavigationProperties()` is declared on `IEdmStructuredType` precisely because of that. **Measured on 1.6.0, both consequences on a plain GET with no query string**: `"Meta":{"Note":"y","Owner":{"Id":3,…}}` — navigation data inline with no `$expand` naming it — and `E.Meta.Owner = E` throwing `JsonException: A possible object cycle was detected`, i.e. the group filter's 500, on every request. Neither is order-dependent and neither needs open types (unlike #482, which needed a poisoning step). **#491's coverage claim for this case was FALSE and is now verified false rather than argued about**: its comment listed "a COMPLEX type carrying an entity-typed member" among the edges its seed had closed. The universal invariant test could not see it either, because `RuntimeTypeConfigResolutionTests.EveryEdmEntityType_ResolvesSuppressed_*` **quantifies over entity types**; `RuntimeTypeResolutionFollowOnTests.EveryEdmComplexType_ResolvesSuppressed_*` is its twin and fails pre-fix with `["PxMeta.Owner"]`. Suppressed, **not served**, for the same reason a derived-declared navigation is: `SpliceKeptNavigations` iterates the *entity* type's navigations, so a complex type's navigation has no route into `expanded` and "serve it" would mean serving it unconditionally. Deliberate residual: `$expand=Meta/Owner` — a complex-type path segment the OData parser accepts — is now omitted rather than expanded. That is a pre-existing feature gap (the splice never handled it) which previously *looked* like it worked because the whole un-suppressed graph leaked.

**(2) The key was the EDM type's FULL NAME while the model had been renamed (#508).** `model.FindDeclaredType(clrType.FullName)` is a **convention, not a fact**. #491 established it returns null for *every* type on a schema whose EDM names do not equal the CLR `FullName` — reachable through `ODataConventionModelBuilder.Namespace`, or `EntityTypeConfiguration.Namespace` under `AdvancedConfigure` — and re-keyed the nav-suppression map off `ClrTypeAnnotation`. The same call survived at four read-path sites: `ResolveProfilesForClrType` (the Model B pushdown gate's candidate resolution), `IsMemberInitProjectable`, `ScalarStructuralClrProps`, `TryGetKeyClrProperty`, plus `GetNavSuppressedOptions`' residue fallback. All five now go through **`EdmClrTypeMap`** (`EdmClrTypeMap.cs`), one per-`IEdmModel` `CLR type -> IEdmStructuredType` map read off the builder's own `ClrTypeAnnotation`, held in a `ConditionalWeakTable` so it is collected with the model. **Measured** end-to-end on a schema with ONE renamed type, `GET /NmParents?$expand=Children($expand=Tags)`: `200` with `"Children":[]` on every row and a SQL log whose only statement is `SELECT "n"."Id", "n"."Name" FROM "NmParents"` — the child table never touched, nothing logged above `Debug`. Post-fix the same request emits one `LEFT JOIN`ed query carrying both levels. `SeedNavSuppressionModel` shares the same map, which is what makes (1) and (2) one change rather than two.

**`EdmClrTypeMap` lookup is EXACT and deliberately offers no base-chain walk** — the one thing it does not share with `InheritedTypeConfig`/`InheritedNameSets`. Those walk because per-type *configuration* declared on a base must apply to a derived **runtime** instance; the question here is "what does the EDM declare for exactly this type", and a base type's answer would be actively wrong: `ResolveProfilesForClrType`'s own comment records that matching a base/derived CLR type rather than the exact EDM type is what made #293's first fix over-broad, and `IsMemberInitProjectable`/`ScalarStructuralClrProps` would project the **base**'s structural properties and silently drop the derived ones. `BuildNavClrNames` still walks the chain itself, over this map, and **unions** — a navigation set is a suppression boundary.

**(3) The key was the DECLARED element type while the runtime element type was derived (#497).** `WrapBoundOpResult`'s collection branch required an implemented `IEnumerable<E>` with `E == modelType`, while the single-entity branch immediately below already accepted a derived instance via `IsAssignableFrom`. A handler declared `Task<IEnumerable<TModel>>` returning a `List<TDerived>` — the ordinary EF Core TPH shape — lists only `IEnumerable<TDerived>`, so it missed the collection branch, missed the single branch (`IsAssignableFrom` fails on a `List`), missed the Edm-primitive map and fell into the final **raw-graph** `PreRenderedJson`. **Measured**: `[{"Special":"s","Id":1,"Name":"derived","Parts":[{"Id":9,"Label":"PART-LEAK"}]}]` — a bare array, no `@odata.context`, no `value` envelope, the declared navigation served **inline** (§4.5.1 and #179 both bypassed), no `@odata.etag`; a cyclic derived graph made the same request a 500. It is `modelType.IsAssignableFrom(elementType)` now, and **`AddBoundOperationProduces` carries the same predicate over the declared return type** so the OpenAPI document and the wire cannot disagree — that advertise-vs-serve half is why the two must move together. `UnboundOperationDefinition.GetCollectionElementType` and its `EntitySetProfile` twin were checked and **left alone**: they extract an element type from a declared type and never compare it to the model type, so they are not instances of this idiom.

**#344 was already closed by #462, and this is the coverage it never had.** #344 reports that a navigation **inherited from a base class** is silently dropped from `$expand` — 200, missing data, no diagnostic — because `IsNavVisibleInBaseOptions` compared `PropertyInfo`s with `!=`. #462 found and fixed that comparison (`HasSameMetadataDefinitionAs`) as a follow-on neither issue named, which closed #344 with it. What was missing was a fixture in **#344's own shape**: every existing suite roots its entity set at the **base** type, where the two reflection walks agree, whereas #344 roots it at the **derived** type with the navigations declared on the base EDM type (`<EntityType Name="PbDerived" BaseType="…PbBase">`). `RuntimeTypeResolutionFollowOnTests.InheritedNavigation_IsServed_WhenTheSetIsRootedAtTheDerivedType` is that fixture; **verified to fail** (all four cases, collection and GetById, collection- and single-valued navigation) by restoring the single `!=`, with the base-rooted byte-identity control staying green. #344's **second face was tracked separately as #529 and is now fixed**: the EF `$expand` pushdown rebuilt rows via a member-init over the *declared* type, so asking for `$expand` on a TPH-derived row dropped its derived structural properties — see the next paragraph.

**A member-init can construct nothing but the DECLARED type, so a polymorphic root is refused the projection outright (#529).** The expand pushdown folds engaged navigations into a member-init over `TModel`; on a TPH hierarchy every row therefore materialized as the base and the derived types' own properties vanished — silently, under a `200`, **decided by whether the request carried `$expand`**. **Measured**: `GET /P529Things` emitted `SELECT Id, Discriminator, Name, Extra, Rank` while `?$expand=Children` emitted `SELECT t0.Id, t0.Name, c.Id, c.BaseId, c.Body` — the discriminator not even selected, so EF could not have materialized the derived type had the projection wanted to. `TryBuildProjectionInit` now answers ineligible for a root with derived types in the EDM (`HasDerivedEntityTypes`, walking `BaseType` over `SchemaElements` rather than an Edm extension so the net8.0 and net10.0 builds agree, and resolving through `EdmClrTypeMap` per #508), which routes the request to the **Include path** (#305 Path A) — real entities, so each row keeps its own runtime type. **Probed before choosing**: an entity-carrier projection (`new { Entity = x, Kids = ... }`) preserves the runtime type too and EF translates an `object`-typed slot, but Include needs no post-materialization mutation of user entities, which a get-only navigation or an `AsNoTracking()` query would defeat. **Scoped to the EXPAND path**: a `$select`-only projection emits just the selected members, where no derived property is reachable and the runtime type is unobservable, so refusing there would cost the pushdown for a difference nothing can see.

**That fix REQUIRED lifting the Include path's nested-`$filter`/`$orderby` refusal, and the stated reason for it was false.** The path answered `400` because *"a plain EF Include cannot carry a predicate/ordering at all"*. EF Core's **filtered** Include does — in exactly the `Where → OrderBy/ThenBy → Skip/Take` sequence `ApplyNavShape` was already composing for that path (**measured** on EF Core 10 / SQLite: filter, ordering and `Take` all applied, derived type intact). `ApplyIncludeFallback` now binds them through the **same `BindNavShape`** the projection path uses rather than a second transcription. Not optional: a polymorphic root reaches this path on *every* request, so leaving the refusal would have traded wrong data for a `400` on every nested-option query — the trade #529 exists to avoid. **BREAKING**: a nested `$expand`/`$levels` under a polymorphic root now answers `400` where it answered `200` with the derived properties missing. `FindNestedExpandOrLevels` is **unchanged**; what moved is that a polymorphic root now reaches it, and the envelope names the new reason (#322's rule holding — it names the check that failed, not the eligibility rule). `ThenInclude` support is **#616**. The two tests that pinned the lifted `400` are **inverted, not deleted**, and assert the resulting data rather than the status; the #322 message-discipline assertions they carried moved to a fixture that can actually reach the remaining `400` — that branch was already uncovered, since neither `NoCtorParent` (child declares no navigation) nor `NoCtorCyclicParent` (back-reference is convention-discovered, not declared) engages a nested expand.

**Delta mapping is a separate, dependency-free subsystem (#243).** `DeltaProfile` (non-generic, `For<TModel,TEntity>()` + fluent `.Rename`/`.Ignore`/`.Convert`, no `.Build()`) declares DTO→entity write mappings; the single DI-singleton `IDeltaFactory` exposes `Create<TModel,TEntity>(Delta<TModel>)` and `Create<TModel,TEntity>(TModel)`, both returning a `Delta<TEntity>` the handler applies with `Delta<TEntity>.Patch(entity)` — the framework never applies or persists. Registration is symmetric: `AddEntitySetProfile<T>()` (the former `AddProfile<T>()` — hard-renamed, no alias) and `AddDeltaProfile<T>()`; the existing `AddProfilesFrom*` scanner discovers **both** profile kinds in one pass (widened predicate in `ProfileScanner`, routed in `OhDataBuilder.AddProfilesFrom`). Delta profiles accumulate in a cross-registration `DeltaProfileRegistry` (instance singleton, like `GlobalProfileRegistry`); `IDeltaFactory` is built lazily from it and **forced at `MapOhData()`** for startup fail-fast. `DeltaMappingCompiler` validates every writable model property is mapped/renamed/converted/ignored and every mapping is type-compatible (automatic subset = identity / `target.IsAssignableFrom(source)` / nullable-wrap `T→T?`; everything else needs an explicit `.Convert` — never `Convert.ChangeType`), then compiles an immutable `DeltaMappingPlan` keyed by `(TModel,TEntity)`. `Delta<TEntity>.UpdatableProperties` is seeded from the model allowlist minus `Ignore()`d names, translated through the rename map, so security constraints survive the boundary. Scalars/structural only — **but read that as an intent, not an enforcement, and see #488 item 3 below.** Also ships `Delta<T>` sugar `IsChanged`/`TryGetChanged` (expression-based). Files: `DeltaProfile.cs`, `DeltaFactory.cs`, `IDeltaFactory.cs`, `DeltaExtensions.cs`.

**The entity half of that validation is READ OFF `Delta<TEntity>`, never transcribed from it (#479/#480).** One root cause, two shipped symptoms: `DeltaMappingCompiler` validated against a model of `Delta<TEntity>` that is not the model `Delta<TEntity>` implements. `ResolveEntityProp` checked `SetMethod is { IsPublic: true }` and nothing else, while `Delta<T>.InitializeProperties` (`DeltaOfT.cs:699-705`) *additionally* requires a public **getter** and applies `IsIgnoredProperty` (`:722-741` — `[NotMapped]`, `[IgnoreDataMember]`, and an unmarked property of a `[DataContract]` type). A target outside that set is absent from `_allProperties`, intersected out of `_updatableProperties` (`:709`), and `TrySetPropertyValue` answers `false` — which both `Create` overloads **discarded**, so a `[NotMapped]` entity property (routine on EF entities) passed startup and lost every write with no exception and no log. Separately, `Delta<T>.Reset` calls `Activator.CreateInstance(structuralType)` (`:688`) on every `Create`, so an entity with only a *protected* parameterless ctor beside a public parameterized one — **the standard EF Core entity shape**, plus positional records and abstract types — passed startup and then `MissingMethodException`'d on every request. Closed **structurally, not case by case**: `Compile` now takes a `Func<IReadOnlyCollection<string>>` probe, supplied from `DeltaMapping<TModel,TEntity>.Compile()` where `TEntity` is closed (no reflection), which constructs a real `Delta<TEntity>` with a **null** `updatableProperties` — for which `UpdatableProperties` *is* the `_allProperties` key set (`:706-715`) that `TrySetPropertyValue` tests membership in. So there is no copy of Microsoft's predicate to drift; `DescribeWhyDeltaSkips` mirrors it for the **message only** and says so, and falls back to a generic sentence. `DescribeUnconstructableEntity` runs **before** the probe (the probe is the thing that would otherwise throw) and the probe's own failure is caught into the same error list — which is why a **different-typed `new`-shadowed** entity property (#488 item 2, `ToDictionary` duplicate key) now also fails at startup, incidentally and pinned by `DifferentTypedShadowedEntityProperty_FailsFastAtStartup` rather than deliberately fixed. The new rejection is **one-way narrowing**: OhData's public-setter rule stays *ahead* of the tracked-set check (its message is clearer), so `Delta<T>`'s setter-less-**collection** admission was not adopted then — that widening is #488 item 4, and it has since happened; see below. Nothing that still compiles reaches `UpdatableEntityProperties` differently, so the documented "an ignored or unmapped property cannot be patched onto the entity even by a hostile request body" boundary is untouched. And both `Create` overloads now **throw** on a `false` from `TrySetPropertyValue` instead of dropping it: after startup validation a `false` means the validation is wrong, so it is an invariant assertion rather than an error path — a 500 in the OData envelope beats a `200` that silently persisted a partial write, and it is the only signal that exists.

**The MODEL half was transcribed too, and the entity half's answer was "does it track it", not "does the write land" (#488).** The remaining gaps from the same round-2 pass, treated one at a time because only three of the five were real.

**Item 4 (real, both halves, and the interesting one).** The in-scope model surface was "public getter AND public setter", on the stated premise — repeated in `docs/delta-mapping.md` — that *"a get-only computed property can never appear in a `Delta<TModel>`"*. **Measured false for collections**: `Delta<T>` admits a setter-less collection (`DeltaOfT.cs:703`, `GetSetMethod() != null || TypeHelper.IsCollection(...)`), so `public List<int> Tags { get; }` entered the change set, the compiler never saw it, `Create` found no rule, and the client's PATCH returned **200 with nothing persisted**. The surface is now the public-getter properties that are settable **OR** that a real `Delta<TModel>` tracks — a second probe of the same shape as #479's, not a second copy of Microsoft's predicate. **Union, not replacement**: `Create(TModel)` reads the model *directly*, so a property `Delta<TModel>` refuses (`[NotMapped]`) is still mappable on that path and stays in scope. Widening the in-scope surface also pulls a get-only `List<Order>` into `IsNavigationCollectionType`'s reach, which previously could not see it at all — so a get-only navigation collection is now refused instead of silently ignored. **The entity half is where the "just ask `Delta<T>`" reflex is not enough.** `ResolveEntityProp`'s outright public-setter requirement is gone, and the decision is `Delta<T>`'s with the setter check demoted to choosing the clearer of two messages — but **tracking is necessary and not sufficient**: measured on .NET 10.0.11, a tracked setter-less `byte[]` throws `SerializationException: … does not have a Clear method` out of `TrySetPropertyValue`, because the setter-less path clears and refills the instance already there and an array cannot be cleared. Adopting "tracked ⇒ writable" would have converted a startup rejection into a guaranteed per-request 500 — the exact defect class this issue is about, one layer down. So `CanApplySetterlessWrite<TEntity>` **performs the write** on a throwaway `Delta<TEntity>` seeded with the property's own value from a fresh instance; a null seed or any throw answers `false`, which is the fail-closed direction. `Issue488DeltaMappingGapTests.SetterlessArrayEntityTarget_StaysRejectedAtStartup` pins that limit deliberately. The `UpdatableEntityProperties` allowlist widens with the surface — a newly in-scope property that maps is now in it — and the #243 boundary is intact rather than weakened: the property was previously *neither* in the allowlist *nor* persisted, and the developer now has to choose `Ignore()` or a mapping at startup instead of discovering the silent drop in production.

**Item 1 (real; the only one closed by refusal rather than by asking).** `DeltaMapping.Convert`'s converter is hoisted **verbatim** into the plan, which is a process-lifetime singleton, from a profile `DeltaFactory.Build` resolves in a scope it disposes on the next line — and delta profiles are `AddScoped`, the same lifetime whose scoped injection entity profiles advertise. Measured: a converter calling an injected scoped `IDisposable` passed startup and threw `ObjectDisposedException` on every `Create`; a non-disposable dependency was worse, silently reusing the startup instance. Unlike #483 there is **no seam** — a delegate is opaque, the plan is a singleton, and `Create` has no scope — so the shape is refused at the call site (`InvalidOperationException` naming the model property and the remedy) rather than recompiled per request. `CapturedState.IsCapturedByDelegate` walks the invocation list and asks two questions in order, and **the field count alone is not one of them**: measured on .NET 10.0.11, a non-capturing lambda *and* an explicitly `static` one both compile to Roslyn's cached `<>c` singleton (`[CompilerGenerated]`, zero instance fields), a capturing one to a `<>c__DisplayClass` (`[CompilerGenerated]`, one field per capture), a static method group to a null target — but an **instance method group** (`_dep.Convert`) binds the receiver itself, and a receiver declaring no fields reports zero, so a field-count-only test would let a disposed scoped service straight through. So a non-`[CompilerGenerated]` target is a captured receiver outright, and a compiler-generated one is captured only when it holds something. Neither test matches a compiler-generated type by name, and `ConverterBoundToAFieldlessReceiver_FailsFastAtStartup` pins the case the simpler rule missed. It is **sound rather than minimal**: a converter capturing only an immutable local is refused too, and that is a real breaking change, accepted because the remedy is one keyword and because "captures nothing" is the only property that can be checked from outside the delegate.

**Items 5(a)/5(b)/5(c) (real, small).** `ProfileScanner.Scan` filtered `IsAbstract` but not `ContainsGenericParameters`, so an open-generic profile was discovered, registered, and killed `MapOhData()` with a raw `MemberAccessException` naming no remedy — one predicate serves both profile kinds, so the entity-set path the issue notes shares the gap is covered by the same line. `Rename`/`Convert` used `_map[key] = value` and silently dropped the first of two declarations for one source, alone among a declaration surface that rejects every other ambiguity; both throw at the call site now. And `AddDeltaProfileType` threw *"Remove the duplicate AddDeltaProfile call"* when a scan had already found the type and the user then made **one** explicit call — the reverse order was silently fine, so the outcome depended on declaration order and the message blamed the wrong line. Explicit registrations are now tracked per builder, so only a genuine second explicit call throws. **The entity-profile path has the identical 5(c) shape in `RegisterProfileType` and was deliberately NOT changed** — it carries #424's cross-registration semantics and belongs in its own issue.

**Item 2 was already closed** — incidentally, by #479's probe, and pinned by `DifferentTypedShadowedEntityProperty_FailsFastAtStartup`; verified before touching anything. **Item 3 was closed as documentation, deliberately.** `IsNavigationCollectionType` guards collections only; a single reference-typed property is exempt because reflection genuinely cannot separate an EDM complex type from an entity type, and the `DeltaFactory.cs` comment has always said so while `CLAUDE.md` and `docs/delta-mapping.md` stated "no navigation writes" unqualified. Consulting the EDM instead — the issue's option (a) — would couple a subsystem whose whole design point is that it is dependency-free to a per-registration EDM that the single global `IDeltaFactory` has no ordering relationship with. Both documents now state the exemption as loudly as the code does. **The issue's own closing note is confirmed and pinned**: `typeof(int?).IsAssignableFrom(typeof(int))` is **true**, so `IsAutomaticallyCompatible`'s nullable-wrap line is dead code — harmless, and `NullableWrap_IsAlreadyCoveredByIsAssignableFrom` exists so nobody "simplifying" it concludes the nullable case is unhandled.

**`net8.0` on the two shipping libraries is load-bearing, not vestigial.** Several deliberate API
choices exist *because* of it and will silently break the net8.0 build if "simplified" against the
net10.0 API surface: `OpenTypeJsonOptions.FindInvalidDynamicKey` resolves array element and
dictionary value types by CLR reflection rather than `JsonTypeInfo.ElementType` (.NET 9+), and
`ETagValueFormatter.StableTypeName` avoids `Type.FullName` because a constructed generic embeds
`Version=8.0.0.0` on net8.0 and `Version=10.0.0.0` on net10.0. Each is commented at the site; check
the TFM before removing one. `dotnet build src/OhData.sln` builds every TFM, so a net8.0-only break
does surface locally.

### `InternalsVisibleTo`

|---|---|

| `OhData.AspNetCore.NSwag` | Same as above. |
| `OhData.AspNetCore.Swashbuckle` | Same as above. |
