## Build & Test

All commands run from the repo root.

```bash
# Build everything
dotnet build src/OhData.sln

# Run all tests - all seven test projects in one pass. CI (.github/workflows/ci.yml) runs the
# same seven one project at a time, so this is the local equivalent, not a superset.
dotnet test src/OhData.sln

# Run the main suite only - the fast inner loop (~80% of the tests; no companion-package,
# client, or test-bench coverage)
dotnet test src/OhData.AspNetCore.Tests/OhData.AspNetCore.Tests.csproj

# Run a single test by name
dotnet test src/OhData.AspNetCore.Tests/OhData.AspNetCore.Tests.csproj --filter "FullyQualifiedName~GetAll_Returns200"

# Run a single test class
dotnet test src/OhData.AspNetCore.Tests/OhData.AspNetCore.Tests.csproj --filter "ClassName~EndpointMappingTests"

# Run the test bench (interactive demo, browse to http://localhost:5099/scalar)
dotnet run --project src/OhData.TestBench.AspNetCore
```

## Architecture

OhData is a convention-based OData server framework that turns declarative profile classes into registered ASP.NET Core minimal API endpoints at startup - no controllers required.

### The core flow

```
EntitySetProfile<TKey, TModel>
    └─► IVisitModelBuilder       → builds the OData EDM model (Microsoft.OData.ModelBuilder)
    └─► IEntitySetEndpointSource → runtime-typed interface for OhDataEndpointFactory to call handlers

AddOhData(builder => builder.AddEntitySetProfile<MyProfile>())
    └─► OhDataBuilder collects profile types + prefix
    └─► Profiles registered as AddScoped (not singleton) to support DbContext injection
    └─► OhDataRegistration (keyed singleton) built lazily:
          temporary scope resolves each profile → visits EDM, collects IEntitySetEndpointSource
    └─► Stored in DI as AddKeyedSingleton<OhDataRegistration>(name)

app.MapOhData()  →  returns RouteGroupBuilder
    └─► OhDataEndpointFactory.MapAll()
        ├─► routes.MapGroup(prefix)  ← outer group for the whole OData surface
        │      endpoint filters: OData-Version response header, OData-MaxVersion request-header
        │      validation (§8.2.7 - rejects < 4.0 with 400), $format/Accept negotiation
        ├─► GET  ""              → service document
        ├─► GET  /$metadata      → CSDL XML
        ├─► startup validation: throws InvalidOperationException if a structural property name
        │      collides with an entity-level bound function name, if a navigation property's
        │      `post` handler collides with an entity-level bound action name (both POST
        │      /{EntitySet}({key})/{segment}), if an unbound function/action name collides with
        │      another unbound operation or with an entity set's own collection GET/POST route,
        │      or if a BindEntityFunction/BindEntityAction handler's first parameter isn't the
        │      entity key (TKey), or (#313, opted-in registrations only) if an entity-level bound
        │      function name collides with a PAGEABLE navigation's continuation route, or (#465)
        │      if a Priority-1 profile (GetODataQueryable) also sets a Search handler, or (#468)
        │      if EdmValidator.Validate rejects the built EDM as invalid CSDL
        └─► per profile (only routes whose handler delegate is non-null):
            GET    /{EntitySet}              (GetAll or GetQueryable)
            GET    /{EntitySet}/$count
            GET    /{EntitySet}({key})       (GetById)
            POST   /{EntitySet}              (Post - deep insert / @odata.bind handling, see AllowDeepInsert below)
            PUT    /{EntitySet}({key})       (Put)
            PATCH  /{EntitySet}({key})       (Patch)
            DELETE /{EntitySet}({key})       (Delete - returns Task<bool>; false→404 or 204, per IdempotentDelete)
            GET    /{EntitySet}({key})/{nav}          (navigation routes with handler, batch or per-entity)
            GET    /{EntitySet}({key})/{nav}?$skip=N  (#313: bare-$expand continuation, delegate-LESS navs only,
                                                       registered only when ExpandPagingEnabled && MaxExpandTop is set)
            GET    /{EntitySet}({key})/{nav}/$count   (collection-navigation count)
            GET/POST/PUT/DELETE /{EntitySet}({key})/{nav}/$ref  (addRef/setRef/removeRef)
            POST   /{EntitySet}({key})/{nav}          (HasMany `post` - create a related entity)
            GET    /{EntitySet}({key})/{Property}          (structural property read - rides GetById, gated by PropertyAccessEnabled)
            GET    /{EntitySet}({key})/{Property}/$value   (raw property value, same gate)
            PUT/PATCH/DELETE /{EntitySet}({key})/{Property} (structural property write - rides Patch, gated by PropertyAccessEnabled)
            GET    /{EntitySet}/{FunctionName}  (bound functions, query-string params)
            POST   /{EntitySet}/{ActionName}    (bound actions, JSON body params)
            Each route gets .WithTags(EntitySetName) and .RequireAuthorization(...) if configured.
```

### Key design decisions

**Handler presence drives route registration.** If a profile sets `GetAll = null` (the default), no `GET /EntitySet` route is registered.

**Two paths for GET collection.**
- `GetQueryable` (IQueryable): framework constructs `ODataQueryOptions<TModel>` and applies `$filter`/`$orderby`/`$skip`/`$top` via `ApplyTo(IQueryable)`, enabling EF Core SQL pushdown. `$select` is applied via JsonNode post-processing to keep camelCase consistent.
- `GetAll` (IEnumerable): simple enumeration - developer chose the opt-in simple path. It is **not** "no query options applied": `$top`/`$skip` are applied in-memory as `Skip()`/`Take()` after materialization, and `$select`/`$expand` in the JSON pass. But `$filter` and `$orderby` are **rejected with `400` (`UnsupportedQueryOption`)** - *"This resource does not support $filter or $orderby. Configure GetQueryable to enable server-side query processing."* - not silently ignored. Pinned by `OpenTypeLimitationTests.OpenTypeDynamicKeyReadPathTests`, which asserts it for a declared property as well as a dynamic key, since the rejection is about the path having no `IQueryable`, not about what is being filtered.
- `IODataEntitySetEndpointSource` (Priority 1): profile receives `ODataQueryOptions` directly and applies them itself.

**`$select` uses JsonNode post-processing** (not `ISelectExpandWrapper`) to avoid the PascalCase/camelCase inconsistency that `ApplyTo` with `$select` introduces.

**A malformed query option returns 400, whatever it throws (#402).** Two separate guards, with deliberately different catch widths. (1) `ODataQueryOptions` construction runs inside `TryBuildQueryOptions`, whose try contains *nothing but* the construction and whose catch is **everything except `OperationCanceledException`** → `400` `InvalidQueryOption`. (2) The surrounding whole-handler try on each read route keeps its narrow `catch (Microsoft.OData.ODataException)`, which covers the deferred, parse-on-first-access failures (most malformed values parse lazily) and `ValidatePropertyAllowlists`. The widths are not interchangeable: the whole-handler try also contains `InvokeGetQueryableAsync`, so broadening the catch *there* would relabel a database outage as a client error and destroy the guarantee below from the other direction; conversely narrowing (1) to a type list is what produced the bug. **Measured** construction-time throw set (`QueryOptionConstructionFaultTests` probes every system query option the framework accepts with empty, malformed and hostile values, and pins the result as a live regression): `ODataException` for an empty `$filter`/`$orderby`/`$top`/`$skip`/`$count`/`$search`/`$apply`/`$compute`, and **`System.ArgumentException`** for `$skiptoken=` or a valueless `$skiptoken` — from `SkipTokenQueryOption`'s own ctor, which is what escaped to the group filter as a client-reachable 500. That set is a measurement, not a contract: `BuildQueryOptions` news up one option object per recognized `$`-option, each with its own argument validation, and nothing in `Microsoft.AspNetCore.OData`'s contract restricts those to `ODataException`. `ODataException` keeps its message pass-through (so the eight empty-value cases stay byte-identical); anything else gets a generic message and the real exception is logged at `Warning`. **All five** construction sites are guarded — Priority-1 collection, `GetQueryable` collection, `GetAll` collection, `/$count`, and `GetById` (which builds options only when `$select`/`$expand` is present).

**`ODataQueryContext` is per request; `ODataQuerySettings` is not (#426).** `TryBuildQueryOptions` takes the `IEdmModel` and builds a fresh `ODataQueryContext` on every call — deliberately, so no caller can hand it a shared one. It used to be built once per entity set at startup and captured by all five read-route closures under the comment *"Both are read-only after construction"*, which was **false and production-reachable**: `ODataQueryOptions`' constructor WRITES `context.RequestContainer` and `context.Request` on every use (`ODataQueryOptions.cs:76-80`, opening with `Contract.Assert(context.RequestContainer == null)` — Microsoft stating the type is per-request), and `Initialize` reads `context.Request` back off that shared field (`:1165`) rather than using the constructor's own `request` parameter. Two concurrent requests therefore race on `Request`, and the loser dereferences another request's `HttpContext` — concurrently with its owner, or after it has been recycled — which tears the `FeatureReferences` read and throws `NullReferenceException` out of `DefaultHttpContext.get_RequestServices`. #402's deliberately broad catch then relabels it `400 InvalidQueryOption`, so a **valid** request, including one with no query string at all, intermittently 400s under load. **Measured**: 16-89 failures per 32,000 constructions across 16 threads sharing one context, 0 per 32,000 with a fresh context (`QueryContextPerRequestTests`, which also pins the invariant deterministically — two sequential requests must not be handed the same instance — via the Priority-1 profile seam, the only place the framework's context is observable). #384's intermittent `ConcurrencyTests` failure was this, not a flaky test. **The `(IEdmModel, IEdmType, ODataPath)` overload is NOT the cheap path** it looks like: it leaves `ElementClrType` null and `ODataQueryOptions<TEntity>`'s constructor throws on that (`FilterQueryOption.ApplyTo` too), and it skips only the CLR-to-EDM lookup, not `GetNavigationSource`'s linear scan of every entity set — which both overloads run on every construction. **Cost** (`QueryContextConstructionBenchmarks`): +263 to +362 ns and +448 B per options build, i.e. under 1% of the time and 2.7% of the allocation of the cheapest measured end-to-end read route (GetById, 36.8 us / 15.95 KB) and under 0.05% / 0.4% of a collection page. The `ODataQuerySettings` instances cached on the same startup line **stay** cached: verified against the `Microsoft.AspNetCore.OData` source, every consumer those instances reach (`FilterQueryOption`/`OrderByQueryOption`/`SkipQueryOption`/`TopQueryOption.ApplyTo`, and `QueryBinderContext`, which holds one behind a get-only property) only reads them, and every settings-mutating path there mutates an instance it created itself — `ODataQueryOptions.ApplyTo` opens with `querySettings = Context.UpdateQuerySettings(querySettings, query)`, which `CopyFrom`s into a new object. Safe because of how it is used, not because the type is immutable; it is a mutable POCO.

**Query-capability flags and property allowlists are enforced at runtime, not just advertised.** `FilterEnabled`/`OrderByEnabled`/`SelectEnabled`/`ExpandEnabled`/`CountEnabled` (all default `false`) and `FilterProperties`/`OrderByProperties`/`SelectProperties`/`ExpandProperties` gate the `GetQueryable`, `GetAll`, and Priority-1 collection paths, plus `$select`/`$expand` on `GetById`: a disabled option in the request returns `400` (`UnsupportedQueryOption`); a non-allowlisted property returns `400` (`InvalidQueryOption`) via the EDM's model-bound `NotFilterable`/`NotSortable`/`NotSelectable`/`NotExpandable` annotations. `$expand` is also implemented on the single-entity `GetById` route (reuses the collection expansion pipeline). Navigation-collection routes reject unimplemented system query options (`$filter`, `$expand`, `$search`, `$apply`, `$compute`, `$skiptoken`, `$deltatoken`) with `400` rather than silently ignoring them. **One exception to the allowlists, and it is not a bug in the enforcement (#401): a dynamic (open-type) property is not in the EDM, so it carries no `NotFilterable`/`NotSortable`/`NotSelectable` annotation and is not gated at all** - `Microsoft.AspNetCore.OData` behaves identically. Do not read the allowlists as a security boundary over a model with an open complex type; `docs/open-types.md` has the measured matrix, and `OpenTypeAllowlistBypassTests` pins it. **The allowlists are scoped per CLR model type, not per entity set, and that is now enforced at startup (#458).** `EntitySetProfile.VisitModelBuilder` applies them via `entityType.Filter/OrderBy/Select/Expand`, and `entityType` is the shared per-CLR-type `EntityTypeConfiguration<TModel>`; `ModelBoundQuerySettings` is keyed by type while OhData's configuration surface is keyed by entity set, so two profiles over one model type **unioned** their allowlists and each set silently accepted what the other allowed - **measured for all four options, in both registration orders**, with responses byte-identical to the correctly-gated case. **Per-entity-set model-bound settings do not exist**: in `Microsoft.OData.ModelBuilder` 2.x the fluent `Filter`/`OrderBy`/`Select`/`Expand`/`Count`/`Page` API is declared only on `StructuralTypeConfiguration<T>` and `PropertyConfiguration` (`EntitySetConfiguration`/`NavigationSourceConfiguration` expose bindings, `EntityType`, `Name`, `ClrType`, `VocabularyTermConfigurations` and nothing else), every `GetModelBoundQuerySettings` overload in `Microsoft.AspNetCore.OData` resolves off an `IEdmStructuredType` (optionally plus an `IEdmProperty`) rather than a navigation source, and the capability-vocabulary annotations that *can* sit on an entity set are never read by the query validators - metadata-only advertisement. So `ModelBoundAllowlists.Validate` throws `InvalidOperationException` from `MapOhData()` on a divergent pair, mirroring `IgnoredPropertyJsonOptions.BuildIgnoredPropertyMap`'s `Ignore()` check. It compares the **literal arrays handed to the model builder** - recorded at the four call sites, post EDM-name resolution and post navigation merge - because that array *is* the shared state; re-deriving from the raw profile allowlists would both miss and invent divergences. Not a conflict: two unset (permissive) allowlists, a sibling whose capability flag is off (it makes no call, and its own requests die at the flag gate), an `AdvancedConfigure` override (ejects before the call sites), or a separate registration (its own `ODataConventionModelBuilder`). `SiblingEntitySetAllowlistTests` pins all of it, including that `WidgetProfile`/`QueryableWidgetProfile` still co-register.

**Unhandled handler exceptions get the OData error envelope, not an empty 500.** A group-level endpoint filter (registered alongside the `OData-Version`/`OData-MaxVersion` filters in `OhDataEndpointFactory.MapAll`) catches any exception a handler throws - as opposed to an `ODataError` result a handler deliberately returns - and converts it into `500` + `{"error":{"code":"InternalServerError",...}}`, logging the real exception (never leaking its message/stack trace to the client). Does not catch `OperationCanceledException` (left to ASP.NET Core's own client-disconnect handling) or startup-time validation exceptions (`MapOhData()` throws those once, before any request is served).

**That filter only covers what runs *inside* the pipeline, so nothing may defer serialization (#396).** A minimal-API `IResult` is executed by `RequestDelegateFactory` **after** the endpoint-filter chain has unwound, so a fault while the result executes is outside the filter's `try` — and the status line and headers are already committed. Measured on the pre-fix tree: a bound function whose result faults during serialization logged `Request finished … - 200` and shipped a truncated body, with nothing logged. That is worse than an envelope-less 500 — a success status with a malformed body defeats client-side error handling completely — and it is generic to any throwing converter, cyclic graph, or faulting getter. The invariant is therefore **every route materializes its response body before returning**: most already did, because they build a `JsonObject`/`JsonArray` in the handler (`SerializeBounded` / `ODataEntityNode` / `ApplyCollectionPipelineAsync` / `BuildNavEnvelope`), so all user code runs where the filter can see it and executing a materialized `JsonNode` afterwards cannot re-enter it. The four routes that handed a **raw CLR graph** to `Results.Json` now go through `PreRenderedJson`, which serializes to UTF-8 bytes in the handler and returns a `Utf8JsonHttpResult` that only writes: the two unbound function/action results, `WrapBoundOpResult`'s final branch (a non-`TModel`, non-Edm-primitive DTO — its other two branches emit a materialized `JsonArray` or an Edm primitive), and the structural-property read envelope (whose `value` is a complex property's whole sub-graph). Byte-identical by construction — same declared `TValue`, so the same `JsonTypeInfo` resolves; do **not** "simplify" those call sites to pass `object`. `Content-Length` is now explicit. **Measured cost** (`OperationResultBufferingBenchmarks`, against a free `Stream.Null` write): a small DTO — the common shape — gets *faster* (0.74×, the async state machine dominates a tiny payload); 189 KB costs +18%, 9.4 MB +74%, all of it the extra full-payload `byte[]`. A pooled `Utf8JsonWriter` beats every arm (0.66×/0.97×/1.43×, no LOH traffic) and is deliberately **not** shipped: it requires transcribing the `JsonSerializerOptions`→`JsonWriterOptions` mapping by hand, and one wrong or missing member changes the response bytes. Residual, knowingly out of scope: `WrapBoundOpResult`'s Edm-primitive branch and every other `Results.Ok(JsonNode)` still serialize at execute time, but their payloads are materialized nodes or BCL primitives, so only a host-registered converter for a primitive type could fault there.

**Advertise only what the route serves; the EDM is validated at startup (#465/#467/#468).** Three separate claims the server did not honour, one shape. (1) The **Priority-1** collection route appended `", $search"` to its OpenAPI description whenever the profile had a `Search` handler and never invoked it — there is no `$search` leg in that route body at all. Invoking is **not** coherent with the Priority-1 contract: on the `GetQueryable`/`GetAll` paths `Search` *replaces the source* and the framework applies the remaining options on top, which it can because it owns the pipeline there; Priority-1 hands the whole `ODataQueryOptions` to the profile, so there is no seam to feed a search-derived source into, and honouring it would mean bypassing the profile — dropping `$filter`/`$orderby` on exactly the requests carrying `$search` (the same defect one option over) and routing around any row-level scoping the handler applies, which is a common reason to choose Priority-1. So the advertisement is gone and `GetODataQueryable` + `Search` is **refused at startup**; `$search` there is the profile's own business via `options.Search`. (2) **`OhDataQueryOptionsMetadata` fields mean "this route honours this option", never "this route is of kind X"** — it is attached to five route shapes (three collection GETs, `/$count`, GetById) and read by three companion packages, so a field with two meanings produces the same wrong document in all three. `$top`/`$skip` were added on metadata *presence* alone (documented on GetById and `/$count`, both of which drop them) → new `TopSkipSupported` field; `/$count` set `CountEnabled: true` to mean "this route IS a count" while the transformers read "documents the `$count` option" → reduced to the single meaning, `false` there; and `/$count`'s `FilterEnabled` mirrored the profile flag although its GetAll fallback answers `400` for any `$filter` → gated on the source (`countSourceAppliesFilter`), matching the "B1 fix" the sibling collection route already had. **The fix site is `OhDataEndpointFactory`'s metadata attachment, not the transformers** — one site, three consumers, which is why they agree byte-for-byte; keep it that way. (3) `$metadata` emitted `IncludeInServiceDocument="true"` on every unbound **function** import (the `Microsoft.OData.ModelBuilder` default, never set) while the service document was hand-built from `registration.Profiles` and listed entity sets only. For a **parameterized** import that claim is invalid CSDL (§13.6 — it cannot be invoked by name alone); those now clear the flag, parameterless ones keep it and are really listed, and the service document is **derived from the EDM container** so the two generators cannot diverge again. Action imports are never listed (not GET-addressable, no such attribute in CSDL). Riding along: **`EdmValidator.Validate` is now called from `MapOhData()`** — it was called nowhere in the assembly. `CsdlWriter.TryWriteCsdl` does not run these rules and `CsdlReader.TryParse` does not police them either, so an invalid construct reached the wire and broke only consumers that validate (codegen tools). Measured when first wired in: it catches this issue's own violation in four fixtures, **and** the compiler-generated name from `AddFunction` with an un-named lambda (`InvalidName`, `<Method>b__0_1`), which had been shipping invalid `$metadata` silently. That second one is now caught **earlier and better**, at registration: `AddFunction`/`AddAction` validate the resolved name themselves and throw `ArgumentException` naming the parameter and the remedy (pass an explicit `name`), because a generic CSDL-validation failure quoting `<Method>b__0_1` at `MapOhData()` tells a developer neither what caused it nor what to do. **They call `OpenTypeJsonOptions.IsValidDynamicPropertyName` — the shipped validator, never a second transcription of the ABNF**; the whole point of the fast-path/rune-walk oracle relationship recorded above is that a third hand-rolled copy would drift from it. The `*Cached` variant is deliberately not used: its 1024-entry cache memoises per-request dynamic keys on the serialize path, and startup-time operation names would only evict them. `EdmValidator` remains the backstop for what a name check cannot see — the parameterized `IncludeInServiceDocument` violation among them.

**`Delete` returns `Task<bool>`.** `false` → 404 OData error **when `IdempotentDelete = false`**; the framework default is `IdempotentDelete = true`, under which `false` → 204 No Content instead. No `KeyNotFoundException` idiom.

**ETags.** Set `GetETag = model => "..."` to opt in. Adds `ETag` response header to GET/POST/PUT/PATCH. Checks `If-Match` header on PUT/PATCH/DELETE; returns 412 on mismatch.

**Named registrations.** `AddOhData("v1", ...)` / `MapOhData("v1")` uses `AddKeyedSingleton<OhDataRegistration>("v1")`. Unnamed `AddOhData()` uses the `__default__` key. Multiple registrations coexist.

**Bound functions and actions.** `BindFunction(delegate)` / `BindAction(delegate)` in the profile constructor registers HTTP routes at startup and registers the operation in the EDM. Functions: `GET /{EntitySet}/{Name}?param=value`. Actions: `POST /{EntitySet}/{Name}` with JSON body `{ "paramName": value }`. `CancellationToken` parameters are detected and passed automatically.

**Type erasure via `IEntitySetEndpointSource`.** Profiles are generic (`EntitySetProfile<TKey, TModel>`) but the factory iterates them as `IEntitySetEndpointSource` (non-generic, internal). The factory re-introduces the generic types via `MakeGenericMethod(KeyType, ModelType)` once per entity set at startup - not per-request.

**Profiles are scoped; two sources per handler.** Each route handler closure captures two `IEntitySetEndpointSource` references: the startup `source` for structural queries (`HasGetById`, `MaxTop`, auth config, nav route metadata) and a per-request `s = ResolveHandlers(ctx)` resolved from `ctx.RequestServices` for all `Invoke*()` calls. This allows profiles to safely inject scoped dependencies (e.g. `DbContext`) in their constructor. Compiled delegates that don't capture scoped state (ETag, key-to-string) are cached in `static ConcurrentDictionary<Type, ...>` so `Expression.Compile()` runs at most once per type.

**`MapGroup` slash insertion - critical routing rule.** `MapGroup` inserts a `/` between the group prefix and any route template that doesn't start with `/`. This breaks OData key syntax (`Widgets({key})` vs `Widgets/({key})`). All entity-set routes are therefore mapped on the top-level `/prefix` group with the entity set name embedded in the template (e.g. `"/Widgets({key})"`) rather than on a per-entity sub-group. If you add new routes, follow this pattern.

**Authorization is per-profile, all-operations.** `RequireAuthorization()` / `RequireRoles()` on a profile applies the same auth requirement to every route for that entity set. No per-operation granularity.

**`AdvancedConfigure` eject hatch.** Overriding `AdvancedConfigure(EntitySetConfiguration<TModel>)` gives full EDM control and disables automatic EDM config. Detected at startup via `MethodInfo.DeclaringType` comparison.

**Profile types have no ASP.NET Core dependency.** Auth config is stored as plain `AuthorizationConfig` data; the factory applies `RequireAuthorization`. Keep it this way.

**Property routes ride `GetById`/`Patch`; no new handler delegates.** `PropertyAccessEnabled` (profile-level `bool?`, inherits `EntitySetDefaults.PropertyAccessEnabled`, **default `true`**) gates `GET /{EntitySet}({key})/{Property}` and `/$value` (requires `GetById`) and `PUT`/`PATCH`/`DELETE /{EntitySet}({key})/{Property}` (requires `Patch`, built as a one-property `Delta<TModel>`). Structural properties are computed once at startup as every public readable CLR property minus every navigation property name, so property and navigation routes never collide by construction. The one remaining collision risk - an entity-level bound function sharing a name with a structural property - is caught by a startup validation pass in `app.MapOhData()` (`InvalidOperationException`), since two routes can't otherwise register the same `(template, method)` pair.

**`AllowDeepInsert` controls what `Post` receives, not a new route.** Profile-level `bool?` (inherits `EntitySetDefaults.AllowDeepInsert`, **default `false`**), entity-level granularity only - no per-navigation opt-in. Default: nested navigation-property values (`HasMany`/`HasOptional`/`HasRequired`) that System.Text.Json already bound during deserialization are stripped (nulled) before `Post` runs. Opt-in (`true`): the full deserialized graph is passed through; the handler owns atomic persistence (the framework does not open a transaction). `@odata.bind` anywhere in a POST body is detected and rejected with `501 Not Implemented` regardless of `AllowDeepInsert` - it is not implemented at all. The collection POST runs that check **unconditionally**; `PUT`, `PATCH`, the navigation-POST create route, the structural-property writes and each bound/unbound action parameter run the same check inside `PrepareWriteBody`, so they answer `501` too but only on a registration whose EDM declares an open complex type - the only condition under which those routes buffer the body at all (buffering every PUT body would break the byte-identical no-op `OpenTypeDefaultOnIsByteIdenticalTests` pins).

**Batch-aware `$expand` via an additive `BatchHandler`.** `HasMany`/`HasOptional`/`HasRequired` accept an optional `batchGetAll`/`batchGet` delegate (`IReadOnlyList<TKey> → ILookup<TKey,TNavigation>` or `IReadOnlyDictionary<TKey,TNavigation?>`) alongside the existing per-entity `getAll`/`get`. When present, `$expand` calls it once per expanded property per page instead of once per parent entity (collapsing N×P sequential calls to P). A per-entity `Handler` is auto-derived from the batch delegate by calling it with a single-key list, so the standalone nav-GET route, `$count`, and `$ref` keep working without a second handler. Falls back byte-identically to the per-entity path when no batch handler is registered.

**Entity-id URLs use a shared canonical key formatter.** `Location`/`Content-Location`/`OData-EntityId`/`@odata.id` values built from a CLR key (POST, and the parsed key on `GetById`/`PUT`/`PATCH`/`$ref`/nav-POST responses) go through `ODataEntityKeyUrlFormatter`, which single-quotes and percent-encodes string keys and doubles embedded quotes - the same escaping `ODataKeyParser` expects on the way back in. `int`/`Guid`/other non-string keys format unchanged.

**PATCH cannot move the entity key, and the guard validates exactly what the loop applies (#454).** The key-mismatch guard and the delta-building loop used to consult different sets: `TryGetJsonProperty` returns the FIRST case-insensitive match and stops, and matched on the key's CLR name, while the loop resolves EVERY body property through `FindClrPropertyByEdmName` (case-insensitive **and** `[JsonPropertyName]`-aware) into a last-writer-wins `Delta<T>` with no key exclusion. Three bodies therefore rewrote the key and returned `200`: `{"Id":1,"Id":999}`, `{"id":1,"Id":999}`, and - with a renamed key - a single `{"code":"ZZ"}`, which the CLR-name lookup could not see at all. Both halves now resolve through `FindClrPropertyByEdmName` against the same CLR property: every occurrence is validated, and the key is **never written into the delta**, so immutability is structural rather than a consequence of the guard having seen every occurrence. A mismatch is **rejected** with `400` (target `key`) rather than silently dropped - consistent with the pre-existing single-occurrence 400 and with the structural-property write route's `KeyImmutableError`. **PUT is structurally immune** and must stay that way: it deserializes to `TModel` first and reads the key off the materialized model (`InvokeGetKeyString`), so STJ has already collapsed duplicates to the value the handler will receive. `KeyImmutabilityTests` pins both halves, including two PUT tests whose only job is to fail if PUT is ever refactored toward raw-`JsonElement` parsing.

**POST/PUT/PATCH deserialize the request body by hand.** All three read and JSON-deserialize the body manually (rather than an ASP.NET Core minimal-API bound parameter) so malformed JSON, non-object bodies, and non-JSON `Content-Type` values return the OData error envelope (400/415) instead of ASP.NET Core's implicit binder short-circuiting with an empty body. This is also why PATCH's non-object-body case (JSON array/string/number/bool/null) is caught explicitly - `JsonElement.EnumerateObject()` throws `InvalidOperationException` for non-`Object` `ValueKind`, which is now caught and mapped to 400.

**Open types are EDM-driven, complex-only, attribute-free, and ON BY DEFAULT (#389).** `OhDataRegistration.OpenTypesEnabled` defaults to `true`; `AddOhData(o => o.WithOpenTypes(false))` is the escape hatch, and with it `MapAll` never builds the container map, `OpenTypeJsonOptions.Build` returns the base options reference-equal, and no write-path validation runs — that registration is byte-identical to pre-#389. Default-on because a complex type with a dictionary member **is** an open type: the CSDL has always said `OpenType="true"` and omitted the container, so a nested wire shape made `$metadata` and the payload disagree, and `Microsoft.AspNetCore.OData`'s `ODataResourceSerializer.AppendDynamicProperties` reads the same annotation and flattens with no opt-in flag at all. The hazard that justified opt-in is unchanged and is mitigated by a **startup warning**: flattening *re-binds* an existing adopter's body — once the container is extension data it is no longer a declared property, so `{"Meta":{"Bag":{...}}}` becomes a dynamic key named `Bag`, and the echo of that mis-bound value is byte-identical to the correct one (so it is **not** detectable by diffing responses). `OpenTypeJsonOptions.WarnWireShapeIsFlat` therefore logs one `Warning` per open complex type at `MapOhData()`, naming the CLR type and the container member and pointing at `WithOpenTypes(false)`; a model with no open complex type logs nothing. `OpenTypeJsonOptions` reads `ODataConventionModelBuilder`'s own `DynamicPropertyDictionaryAnnotation` (via `EdmAnnotationExtensions.GetDynamicPropertyDictionary`) for every complex type the EDM marks `IsOpen`, and layers one more `TypeInfoResolver` modifier onto `effectiveJsonOptions` that sets `JsonPropertyInfo.IsExtensionData = true` on exactly that member. Ordering: after `IgnoredPropertyJsonOptions.Build` and before the per-request nav-suppression modifier (which derives from these options, so `WithAddedModifier` chains all three) — but the three can never contend for a member. Nav suppression only removes EDM navigations, of which a complex type has none; and the ignored-property map is keyed by `profile.ModelType` (an **entity** type) while `Ignore(...)` takes a root member of that entity, so it and the open-type modifier never see the same `JsonTypeInfo` at all. The member is matched by `MemberInfo.HasSameMetadataDefinitionAs`, **not** `==`/`ReferenceEquals` — the builder's annotation and STJ's `AttributeProvider` come from independent reflection walks that disagree on `ReflectedType` (the builder can report a *derived* type there), so `PropertyInfo` equality returns false for the same member; `HasSameMetadataDefinitionAs` is *not* whole-member identity (it matches across generic instantiations), and what makes it safe is that the container is only ever resolved by walking the looked-up type's own CLR base chain against a map keyed by `DeclaringType`. Three behaviors that ride along: a dynamic key that is not an OData simple identifier is rejected with 400 (`OpenTypeJsonOptions.ScanWriteBody`, walked over the raw `JsonElement` against `JsonTypeInfo`) on **every** route that binds a body reaching a bag — POST/PUT/PATCH, the property-route writes, the navigation-POST create route, and each bound/unbound **action parameter** (checked per parameter against its declared type, so the `{"paramName": value}` envelope is never treated as a bag) — and the walk descends into the **value** of an accepted dynamic key at every depth, arrays and dictionary-valued declared members included (a `IDictionary<string, TOpenComplex>` member is `JsonTypeInfoKind.Dictionary`, so the walk recurses into its VALUES; its own map keys are declared-member keys, not dynamic property names, and are not policed), since everything below a bag key is stored verbatim; the grammar is the ABNF's Unicode categories (`L`/`Nl` leading, `L`/`Nl`/`Nd`/`Mn`/`Mc`/`Pc`/`Cf` following) counted in **code points**, not `char.IsLetter` over UTF-16 units, so NFD and NFC spellings of the same key cannot get different status codes for any name within the 128-code-point cap (decomposition adds code points, so only a name already at the cap can differ); and **two conditions throw** `InvalidOperationException` from the wrapped `JsonPropertyInfo.Get` (→ 500 + the OData error envelope via the group filter), checked in one pass over the bag per serialized instance. (1) A bag key equal to a declared property name, instead of emitting a duplicate JSON key — matching MS's `DynamicPropertyNameAlreadyUsedAsDeclaredPropertyName`, since the spec does not decide it (CSDL §6.3/§9.3 "uniquely named"; JSON Format defers to RFC 8259's SHOULD) and the condition is systematic rather than per-row (a client cannot cause it — STJ binds a body key matching a declared name to the declared property). (2) A bag key that is **not a valid `odataIdentifier`** — the same grammar the write path applies, so keys are policed identically in both directions (400 in, 500 out) and the container's contents are fully validated rather than merely checked for emptiness. This was widened from a bare `string.IsNullOrWhiteSpace` ("not a name at all"), which had let `"has space"`, `"@odata.type"` and a key of only `Cf` format characters through; the widening is a **deliberate divergence from MS**, which skips the empty key (`ODataResourceSerializer.cs:820`) and polices nothing else on this path. Affordability comes from `IsValidDynamicPropertyNameCached`: an ASCII `SearchValues<char>` + `ContainsAnyExcept` fast path (within `[A-Za-z0-9_]` the grammar reduces to a length test plus a leading-digit test) falling back to the unchanged rune-and-category walk — `IsValidDynamicPropertyNameByRuneWalk`, kept as the normative oracle the tests prove the fast path equivalent to — plus a 1024-entry process-wide cache of validated **non-ASCII** keys only, since an ordinal cache lookup hashes the whole string and so costs *more* than the fast path it would be memoising. Measured in isolation: 4.6 ns/key vs 16.9 naive and 5.4 for the declared-name lookup beside it. **In situ** (BenchmarkDotNet, 1,000 rows × 20 dynamic keys, full-grammar validation vs the whitespace-only check) the widening costs **+4.0%** on repeating ASCII keys — the common shape — at 5.8 ns/key marginal; **+6.1%** (9.0 ns/key) on 20,000 distinct ASCII keys; and **+14.7%** (28.8 ns/key) on 20,000 distinct non-ASCII keys, the only shape that saturates the 1024-entry cache and therefore implies a handler synthesising per-row non-ASCII key names rather than a schema-like vocabulary. An earlier stopwatch harness put this at ~+26% (~56 ns/key); that number is **refuted** and should not be requoted. Neither throw is quoted with the offending key when it is the grammar failure (it can carry control characters into a log line); the collision message does quote it, since a declared name is bounded developer-authored text. The getter now only *inspects* and always returns the same reference, which is what removed the old drop-and-clone machinery (`TryCreateEmptyLike`, the `Activator.CreateInstance` fallback, the read-only degradation) and with it the #389 M2 corner where a pre-seeded container silently lost every write. Comparison is **ordinal**, so a case-differing key does not throw. And a container STJ cannot use as extension data (getter-only, most often) throws from `MapOhData()` rather than being skipped. The per-request gate is `OhDataRegistration.OpenTypesActive` (enabled **and** the EDM really has an open complex type), **not** `OpenTypesEnabled` — and now that the flag defaults to `true`, that EDM half is the whole blast-radius bound; gating on the flag alone left a registration with no open types buffering every PUT body, which changed its malformed-body error message and broke the documented byte-identical no-op (`OpenTypeDefaultOnIsByteIdenticalTests` pins it across every write route and body shape). Entity-root containers and `$filter`/`$orderby` over individual dynamic keys are deliberately out of scope, and `PATCH` of a complex member is whole-value **replace**, not merge; `docs/open-types.md` and `OpenTypeLimitationTests` record all of it.

**Open types, #398 stages 0–2 (entity-root groundwork; the widening itself is stages 3–5 and is NOT done).** Three amendments to the paragraph above. **(1) Two false claims were corrected.** `IsNavVisibleInBaseOptions`' comment said `[JsonIgnore]` removes a member from `typeInfo.Properties`; measured false on .NET 10.0.11 — those members stay in `Properties` with `Get`/`Set` null and a `ShouldSerialize` returning false, so the method's answer comes from the `ShouldSerialize` branch, not the fallthrough. This matters because the open-type modifier snapshots `declaredNames` from that same collection, so a `[JsonIgnore]`d navigation still collides with a bag key rather than being shadowed by one. And `OpenTypeJsonOptions.cs` / `docs/open-types.md` claimed `Delta<T>` "has no mechanism" for routing an undeclared key — false: `Delta<T>` has had a `dynamicDictionaryPropertyInfo` ctor parameter all along (`DeltaOfT.cs:112`), MS supplies it from the EDM in `ODataResourceDeserializer.cs:270-286`, and it was measured working (merge semantics, dictionary creation, `updatableProperties` refusing a withheld name). That claim was the stated blocker for entity roots and it does not exist. **(2) `Ignore()` containment ships, and is a deliberate no-op at complex scope.** `Ignore()` works by *removing* a member in a `TypeInfoResolver` modifier, and extension data captures exactly what a modifier removed — so at entity scope a withheld name would bind into the bag and be echoed back under the withheld name (a write-then-read oracle; measured at raw STJ level). `IgnoredPropertyJsonOptions.BuildIgnoredJsonNameMap` captures the withheld **JSON** names off the *pre-ignore* contract (never re-derived from the naming policy) into `OhDataRegistration.IgnoredJsonNamesByType`; those cross into `OpenTypeJsonOptions` as **data**, checked as a **separate set alongside** `ThrowOnKeysThatCannotBeEmitted`'s `declaredNames` on the read side and dropped from the body on the write side. **The withheld sets carry the BINDER's comparer** (`IgnoredPropertyJsonOptions.WithheldNameComparer` - `OrdinalIgnoreCase` whenever `PropertyNameCaseInsensitive`, i.e. always in production) at the one place they are built and at all three places they are consulted; `declaredNames` stays **ordinal** and the two must never be merged. That merge is what made the containment case-sensitive while body binding was case-insensitive: a body key `secret` against a withheld `Secret` missed `declared` (the member is gone from the contract), missed an ordinal withheld set, and was bagged then echoed - measured on both the write and the read side, and they fail independently. The comparers answer different questions: ordinal for `declaredNames` because only a byte-for-byte repeat is a duplicate JSON key, the binder's for withheld names because a case-differing spelling is the bypass rather than a false positive. It cannot fire today — `Ignore(...)` names a root member of an *entity* type, containers live on *complex* types — and `OpenTypeIgnoreContainmentTests` asserts that no-op explicitly. A write naming a withheld property is **silently dropped**, not 400: the spec does not settle it (Protocol §11.4.2's "MUST fail if unable to persist all property values" turns on "property value" as a term of art that does not clearly cover a name the type does not declare, and no clause contemplates a server that *conceals* a declared property), so it follows MS, which clears `ThrowOnUndeclaredPropertyForNonOpenType` deliberately in `ODataInputFormatter.cs:203`. **(3) `@` is control information — a behaviour change to a shipped path.** Any unmatched key containing `@` at *any* position (JSON Format §4.5 leading form, §18 embedded `Property@annotation` form, and the `a@b`/`x@`/`@` residue, which `@` being `OtherPunctuation` already made ungrammatical) is classified as control information: not policed, and **stripped from the body before binding** by `RewriteWithoutUnbindableKeys`. Stripping is not optional — STJ bags every unmatched member, and the read path's identifier check would then 500 the row forever, which is worse than the 400 it replaces. So `@odata.type` inside a complex value goes **400 → silently ignored**. Declared names are matched first (a `[JsonPropertyName("weird@name")]` member still binds), `@odata.bind` is still 501 on **every** write route (that check runs earlier - it was on the collection POST alone for one commit, which turned a 400 into a silent 200/201 on PUT/PATCH/nav-POST/property-writes; see the `AllowDeepInsert` paragraph for where it lives now and how it is gated), and an `@` key *below* an accepted dynamic key is still 400 (no contract down there; the subtree is opaque stored data). **`OpenTypeModifierOrderingTests` is the tripwire** for the modifier order the whole delegate-safety argument rests on (ignore → open-type → nav-suppression); verified to fail when nav suppression is derived from `startupJsonOptions` instead of `effectiveJsonOptions`. Every open-type fixture added here is an **existing feature's fixture with a container added** (`IgnProduct` gained `IgnSpec.Extras`), not a green-field model built around a bag — #395's suite was green while shipping a CRITICAL defect precisely because every fixture in it was the latter.

**Per-type configuration is resolved for the RUNTIME type, through one shared base-chain walk (#462/#343).** Both serialization substrates resolve the runtime type's contract - the batched collection path hands System.Text.Json an `object`-declared element, and the single-entity path calls `SerializeToNode(value, value.GetType(), ...)` - so **any** per-type map keyed by the exact CLR type silently misses a derived instance, which is an ordinary EF Core TPH shape. That had been fixed three times independently (#293, delegate-backed navigation names) before it was recognised as one defect class. `InheritedTypeConfig`/`InheritedNameSets` (`InheritedTypeConfig.cs`) is now the only route: `InheritedNameSets.Resolve(Type)` walks `Type.BaseType` (stopping at `object`, interfaces deliberately not walked) and **unions** every entry on the chain, memoized per runtime type; `InheritedTypeConfig.TryResolveNearest` is the other policy, nearest-wins, for a **single-valued** configuration where a derived declaration replaces the base's (`OpenTypeJsonOptions.TryFindContainer`'s `new`-shadowed dynamic-property container - the walk that was already correct and whose comment named the problem). The two policies are not interchangeable: a withheld-name set is a **disclosure boundary**, so a derived profile's own `Ignore(...)` set must not shadow its base's. Structural, not conventional: `IgnoredPropertyJsonOptions.Build`, `OpenTypeJsonOptions.Build`/`ScanWriteBody`/`RewriteWithoutUnbindableKeys` and `OhDataRegistration.IgnoredJsonNamesByType` all take/carry `InheritedNameSets`, whose entire callable surface is `Resolve` + `IsEmpty` - there is no longer a dictionary in scope for a fifth site to write `TryGetValue(typeInfo.Type, ...)` on, and `RuntimeTypeConfigResolutionTests` asserts that by reflection. The **single-contributor** case returns the declared set **by reference**, so each set keeps its own comparer (`WithheldNameComparer` for withheld JSON names, ordinal for CLR names - never merged; see #398 review HIGH-1); only a genuine multi-level union allocates.

Three concrete defects this closed, all reproduced on a **plain GET with no query string**. (1) **#462**, disclosure: `Ignore()`d `Secret` was withheld on the base row of a page and **served** on the derived row, on both the collection and GetById routes. (2) **#343**, unrequested data plus a reachable 500: `GetNavSuppressedOptions` built its suppression set from `edmType.NavigationProperties()` - the **declared** EDM type - so a navigation declared only on a derived EDM type never reached the set, emitted inline with no `$expand` naming it, and 500'd (`JsonException: A possible object cycle was detected`) when two derived instances referenced each other through one. It now unions in the navigations of the runtime type's own EDM type, resolved via `model.FindDeclaredType(clrType.FullName)` - the same CLR->EDM convention `ResolveProfilesForClrType` uses - which is why `IEdmModel` is now **threaded** through `SerializeBounded`/`SerializeBoundedCollection`/`SpliceKeptNavigations`/`ODataEntityNode`/`ODataEntityResult`/`BuildNavEnvelope`/`WrapBoundOpResult`: `Microsoft.OData.Edm` gives an `IEdmEntityType` no back-reference to its model. Derived-declared navigations are **suppressed, never served** - JSON Format §4.5.1/§11.2.4.2 require a non-expanded navigation to be omitted, and the clause binds against the declared type (as does `SpliceKeptNavigations`), so such a nav can never be asked for and "serve it" would mean serving it unconditionally; consistent with #293's frozen Model B (which matches the **exact** EDM type and has no opinion about a nav no clause can name) and with #440's omit-rather-than-null split. (3) The **mirror image of #343**, found by the shared fixture and in neither issue: `IsNavVisibleInBaseOptions` compared `PropertyInfo`s with `!=`, which also compares `ReflectedType`, and for an **inherited** navigation on a derived instance the two sides disagree - **measured** on .NET 10.0.11, `FindClrPropertyByEdmName` reports `ReflectedType = RtDerived` while STJ's `AttributeProvider` reports `RtBase`, so `==` is false while `HasSameMetadataDefinitionAs` is true. The loop never matched, the trailing `return false` answered "not visible", and a navigation the client **explicitly `$expand`ed** was silently dropped from every derived row while base rows in the same page kept theirs. Now `HasSameMetadataDefinitionAs`, safe for the same reason `OpenTypeJsonOptions.Build` is: both sides are members of `clrType` or one of its bases, and one type's member list cannot hold two instantiations of a single generic definition.

**`RuntimeTypeConfigResolutionTests` is the fixture the whole area was missing.** Every serialization suite here - ignore, open-type, modifier-ordering, nav-suppression - used fixtures where runtime type == declared type, and the one suite that varies runtime type (`PolymorphicExpandSerializationTests`) gives its derived types only **scalar** members. That is why three defects lived in three green suites. The new fixture is a derived instance carrying an inherited `Ignore()`d member **and** a derived-declared navigation, plus the mutual-reference cycle shape; its byte-identity assertions for non-derived shapes were captured from the **pre-fix** build at `6de41d4` and pasted verbatim, never read off the post-fix output.

**Delta mapping is a separate, dependency-free subsystem (#243).** `DeltaProfile` (non-generic, `For<TModel,TEntity>()` + fluent `.Rename`/`.Ignore`/`.Convert`, no `.Build()`) declares DTO→entity write mappings; the single DI-singleton `IDeltaFactory` exposes `Create<TModel,TEntity>(Delta<TModel>)` and `Create<TModel,TEntity>(TModel)`, both returning a `Delta<TEntity>` the handler applies with `Delta<TEntity>.Patch(entity)` — the framework never applies or persists. Registration is symmetric: `AddEntitySetProfile<T>()` (the former `AddProfile<T>()` — hard-renamed, no alias) and `AddDeltaProfile<T>()`; the existing `AddProfilesFrom*` scanner discovers **both** profile kinds in one pass (widened predicate in `ProfileScanner`, routed in `OhDataBuilder.AddProfilesFrom`). Delta profiles accumulate in a cross-registration `DeltaProfileRegistry` (instance singleton, like `GlobalProfileRegistry`); `IDeltaFactory` is built lazily from it and **forced at `MapOhData()`** for startup fail-fast. `DeltaMappingCompiler` validates every writable model property is mapped/renamed/converted/ignored and every mapping is type-compatible (automatic subset = identity / `target.IsAssignableFrom(source)` / nullable-wrap `T→T?`; everything else needs an explicit `.Convert` — never `Convert.ChangeType`), then compiles an immutable `DeltaMappingPlan` keyed by `(TModel,TEntity)`. `Delta<TEntity>.UpdatableProperties` is seeded from the model allowlist minus `Ignore()`d names, translated through the rename map, so security constraints survive the boundary. Scalars/structural only — no navigation writes. Also ships `Delta<T>` sugar `IsChanged`/`TryGetChanged` (expression-based). Files: `DeltaProfile.cs`, `DeltaFactory.cs`, `IDeltaFactory.cs`, `DeltaExtensions.cs`.
