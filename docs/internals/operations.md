# Bound and Unbound Operations

Read this when touching bound/unbound functions or actions, MaxTop paging of operation results, or entity returns from operations.

**Bound functions and actions.** `BindFunction(delegate)` / `BindAction(delegate)` in the profile constructor registers HTTP routes at startup and registers the operation in the EDM. Functions: `GET /{EntitySet}/{Name}?param=value`. Actions: `POST /{EntitySet}/{Name}` with JSON body `{ "paramName": value }`. A **trailing** `CancellationToken` parameter is detected and passed automatically; one anywhere else, or a nullable one, is refused at bind time (#498).

**A bound FUNCTION returning a collection of TModel is bounded by `MaxTop` and pages (#357, BREAKING).** `WrapBoundOpResult`'s collection branch used to hand the whole collection back with no cap, no `@odata.nextLink`, and `$top`/`$skip` neither applied nor rejected - so the DoS ceiling the framework advertises and enforces on all three ordinary collection routes was fully bypassable through any operation that returned a collection (measured on `MaxTop = 50`: `?$top=1000` -> 400 on the collection route, 200 with all 77 entities on `/TopRated`). `TryApplyOperationCollectionPaging` is **#201's `ApplyGetAllPaging`, not a new scheme** - the situation is identical (a fully materialized array, the framework owning the pipeline from there, so an offset continuation is one it can always honour), and it is a second implementation only because that one is a local function closing over the route's `ODataQueryOptions`, which a bound-op route does not build. `$top`/`$skip` are read the way the **navigation-collection** route reads them (`int.TryParse` + that route's existing *"is invalid. It must be a non-negative integer."* wording), the other place in this file that pages a materialized collection with no `ODataQueryOptions` behind it: building a whole `ODataQueryOptions` would additionally start rejecting malformed values of options this route still ignores (`$filter=`, `$skiptoken=`), a wire change #357 does not ask for and whose surface is set by somebody else's constructors, and MS's individual `TopQueryOption`/`SkipQueryOption` both require an `ODataQueryOptionParser` that needs an `ODataPath` this route never parses. The `$top > MaxTop` message **is** shared with the collection routes verbatim - the same condition must not produce two envelopes depending on which route reached the same set.

Three decisions worth keeping. (1) **Breaking by default**: `EntitySetDefaults.MaxTop` is `1000`, not null, so an operation returning more than 1000 entities now truncates to a page plus a continuation. `MaxTop = null` opts out, exactly as on `GetAll`. (2) **The bound is applied in the RUNTIME collection branch, the metadata from the DECLARED return type.** A handler declared `Task<object>` returning a `List<TModel>` must not be a way around the ceiling; conversely `AddBoundOperationPagingMetadata` attaches `OhDataQueryOptionsMetadata` (only `TopSkipSupported` + `MaxTop`; every other field false) off `BoundOperationDefinition.ReturnType`, at the ONE metadata site #467 requires, sharing `DeclaresCollectionOf` with `AddBoundOperationProduces` so the three consumers cannot disagree. The only divergence this leaves is serving a bound the document did not promise - the safe direction. (3) **The paging source is the STARTUP source, and that is load-bearing**: `WrapBoundOpResult`'s `source` parameter is the request-scoped instance, whose `MaxTop` is null (profiles are `AddScoped`; `_resolvedMaxTop` is assigned in `VisitModelBuilder`, which only runs on the startup instance), so reading the ceiling off it silently disables the whole bound - measured, 25 rows returned and `$top=1000` accepted on a profile with `MaxTop = 10`. It is the two-sources rule stated above, and `MaxTop` is named in it. **Actions were excluded and that exclusion is REVERSED by #543; see below.**

**A bound ACTION is bounded too, and a result that does not fit is REFUSED (#543, BREAKING).** #357 excluded actions and defended it with two claims, both **measured false on `d2d96d8`**. Its `pagingSource` parameter was doing two jobs at once - "is this route pageable" *and* "here is the startup source" - and both action call sites passed `null`, so an action skipped the bound entirely: on `MaxTop = 10` over 25 rows, `POST /Set/Dump` answered `200 len=25 nextLink=<none>`, and so did `?$top=999`, `?$top=5`, `?$skip=20` and `?$top=abc`, while the sibling **function** capped at 10 with a `$skip` continuation and `400`d `$top=999`. That is the exact wire shape #357's own entry says it closed. Refuted claim 1: *"a handler declared `Task<object>` returning a `List<TModel>` is not a way around the ceiling"* - it was precisely that, for an action. Refuted claim 2: *"moot in practice besides, `ActionConfiguration.Returns`/`.ReturnsCollection` refuse an already-declared entity type"* - true only of a **declared** entity return (that throw is real and is #539); `Task<object>` registered fine. The flag is now `continuable`, a separate parameter, and every caller passes the startup source: **an action IS bounded, it just cannot be CONTINUED.** Conflating "no continuation available" with "no ceiling applies" is how the ceiling became bypassable.

Everything except one branch is shared verbatim with the function path - an explicit `$top` applied and validated against `MaxTop` with the identical message, `$skip` applied, a malformed value the same `400` - because the same condition must not produce two envelopes depending on which route reached the same set. The branch that differs is **no `$top`, result larger than `MaxTop`**: three shapes were available and two are unavailable here. *Cap and emit `@odata.nextLink`* is invalid (§11.2.5.7 makes a nextLink a URL the client **GETs**, while §11.5.4.1 invokes an action by **POST** to its action URL - there is no GET-addressable continuation of an action invocation, so the link would answer 405, and re-POSTing a side-effecting action to collect page 2 is not a continuation). That argument used to run through §11.5.4 "has no representation" and #478's ETag exclusion; the phrase is not in the spec and the exclusion is a known deviation (#566), so neither is cited here any more. *Cap silently* is forbidden by M1. So it **throws**, which the group filter turns into `500` + the OData envelope with the count, the ceiling and the three remedies logged - and it is a `500` rather than a `400` for #496's reason: the condition is decided entirely by server-side state (the profile declared the ceiling, the handler exceeded it, identically for every request), so blaming the client would be the defect #496 removed one route over. `Prefer: maxpagesize` is deliberately **not** honoured on an action and no `Preference-Applied` is emitted - RFC 7240 makes preferences advisory and forbids claiming one that was not applied, and there is no paging here to drive. `AddBoundFunctionPagingMetadata` is renamed `AddBoundOperationPagingMetadata` and attached to the two action routes as well (an action now really does honour `$top`/`$skip`, which is what an `OhDataQueryOptionsMetadata` field means under #467); the dangling *"see `AddBoundFunctionPagingMetadata` for why actions are excluded"* cross-reference in `WrapBoundOpResult` - which pointed at a method containing no such rationale - is gone with the exclusion it described.

**An entity return is declared through `ReturnsFromEntitySet`, on BOTH operation kinds (#539, BREAKING).** `ActionConfiguration.Returns<T>()`/`.ReturnsCollection<T>()` throw `InvalidOperationException` **at the call**, not at `GetEdmModel()`, for a CLR type already declared as an entity type, naming `ReturnsFromEntitySet`/`ReturnsCollectionFromEntitySet`; the `FunctionConfiguration` twins accept it (measured, ModelBuilder 2.0.0 / .NET 10.0.11). OhData called only the first pair, so `BindAction` over `TModel` or `IEnumerable<TModel>` - `POST /Widgets/Archive` answering with the archived rows - died at `MapOhData()` quoting a method OhData neither called nor exposed, while the function twin worked. `RegisterEdmReturnType` calls the `FromEntitySet` pair whenever the (element) return type is the profile's own `TModel`, **unconditionally across kinds** rather than behind an is-this-an-action branch: the CSDL is byte-identical either way (no `EntitySetPath`, no extra attribute - pinned by `BoundActionEntityReturnTests.BoundFunction_MetadataDeclarationIsUnchanged`), it is what MS's own E2E fixtures do for an entity return on both kinds, and one unconditional rule cannot drift between them. **The entity-set name is always the one `VisitModelBuilder` opened with**, never derived from the return type, because `ReturnsFromEntitySet` does **not** validate that the name exists - it CREATES the set (measured: a bogus name silently added `EntitySet:Ghosts` to the container and to `$metadata`). Residual, and the #539 "floor": an entity return of some *other* profile's model type still cannot be expressed, and now throws an OhData-authored message naming the operation and the remedies with MS's as the inner exception, rather than a raw ModelBuilder string. The two issues interact - #539 turns #543's ceiling from a `Task<object>` corner into the ordinary shape.
