# Query Option Handling

Read this when touching query option handling, a 400/501 decision, $count, $format, or capability flags and allowlists.

**`$select` uses JsonNode post-processing** (not `ISelectExpandWrapper`) to avoid the PascalCase/camelCase inconsistency that `ApplyTo` with `$select` introduces.

**A malformed query option returns 400, whatever it throws (#402).** Two separate guards, with deliberately different catch widths. (1) `ODataQueryOptions` construction runs inside `TryBuildQueryOptions`, whose try contains *nothing but* the construction and whose catch is **everything except `OperationCanceledException`** → `400` `InvalidQueryOption`. (2) The surrounding whole-handler try on each read route keeps its narrow `catch (Microsoft.OData.ODataException)`, which covers the deferred, parse-on-first-access failures (most malformed values parse lazily) and `ValidatePropertyAllowlists`. The widths are not interchangeable: the whole-handler try also contains `InvokeGetQueryableAsync`, so broadening the catch *there* would relabel a database outage as a client error and destroy the guarantee below from the other direction; conversely narrowing (1) to a type list is what produced the bug. **Measured** construction-time throw set (`QueryOptionConstructionFaultTests` probes every system query option the framework accepts with empty, malformed and hostile values, and pins the result as a live regression): `ODataException` for an empty `$filter`/`$orderby`/`$top`/`$skip`/`$count`/`$search`/`$apply`/`$compute`, and **`System.ArgumentException`** for `$skiptoken=` or a valueless `$skiptoken` — from `SkipTokenQueryOption`'s own ctor, which is what escaped to the group filter as a client-reachable 500. That set is a measurement, not a contract: `BuildQueryOptions` news up one option object per recognized `$`-option, each with its own argument validation, and nothing in `Microsoft.AspNetCore.OData`'s contract restricts those to `ODataException`. `ODataException` keeps its message pass-through (so the eight empty-value cases stay byte-identical); anything else gets a generic message and the real exception is logged at `Warning`. **All five** construction sites are guarded — Priority-1 collection, `GetQueryable` collection, `GetAll` collection, `/$count`, and `GetById` (which builds options only when `$select`/`$expand` is present). Since #359 the `/$count` and `GetById` guards are no longer *reachable* via `$skiptoken` — neither route implements it, so it is refused by name (now `501`) before construction; the guard itself is unchanged and is still exercised end-to-end by the three collection routes. **`QueryOptionConstructionFaultTests.EmptySkipToken_ReturnsODataErrorEnvelope` is the sharpest statement of the 501/400 taxonomy in the suite**: one option, one empty value, five routes — `400 InvalidQueryOption` on the three that implement it (a malformed VALUE for supported functionality) beside `501 UnsupportedQueryOption` on the two that do not (unimplemented FUNCTIONALITY).

**`ODataQueryContext` is per request; `ODataQuerySettings` is not (#426).** `TryBuildQueryOptions` takes the `IEdmModel` and builds a fresh `ODataQueryContext` on every call — deliberately, so no caller can hand it a shared one. It used to be built once per entity set at startup and captured by all five read-route closures under the comment *"Both are read-only after construction"*, which was **false and production-reachable**: `ODataQueryOptions`' constructor WRITES `context.RequestContainer` and `context.Request` on every use (`ODataQueryOptions.cs:76-80`, opening with `Contract.Assert(context.RequestContainer == null)` — Microsoft stating the type is per-request), and `Initialize` reads `context.Request` back off that shared field (`:1165`) rather than using the constructor's own `request` parameter. Two concurrent requests therefore race on `Request`, and the loser dereferences another request's `HttpContext` — concurrently with its owner, or after it has been recycled — which tears the `FeatureReferences` read and throws `NullReferenceException` out of `DefaultHttpContext.get_RequestServices`. #402's deliberately broad catch then relabels it `400 InvalidQueryOption`, so a **valid** request, including one with no query string at all, intermittently 400s under load. **Measured**: 16-89 failures per 32,000 constructions across 16 threads sharing one context, 0 per 32,000 with a fresh context (`QueryContextPerRequestTests`, which also pins the invariant deterministically — two sequential requests must not be handed the same instance — via the Priority-1 profile seam, the only place the framework's context is observable). #384's intermittent `ConcurrencyTests` failure was this, not a flaky test. **The `(IEdmModel, IEdmType, ODataPath)` overload is NOT the cheap path** it looks like: it leaves `ElementClrType` null and `ODataQueryOptions<TEntity>`'s constructor throws on that (`FilterQueryOption.ApplyTo` too), and it skips only the CLR-to-EDM lookup, not `GetNavigationSource`'s linear scan of every entity set — which both overloads run on every construction. **Cost** (`QueryContextConstructionBenchmarks`): +263 to +362 ns and +448 B per options build, i.e. under 1% of the time and 2.7% of the allocation of the cheapest measured end-to-end read route (GetById, 36.8 us / 15.95 KB) and under 0.05% / 0.4% of a collection page. The `ODataQuerySettings` instances cached on the same startup line **stay** cached: verified against the `Microsoft.AspNetCore.OData` source, every consumer those instances reach (`FilterQueryOption`/`OrderByQueryOption`/`SkipQueryOption`/`TopQueryOption.ApplyTo`, and `QueryBinderContext`, which holds one behind a get-only property) only reads them, and every settings-mutating path there mutates an instance it created itself — `ODataQueryOptions.ApplyTo` opens with `querySettings = Context.UpdateQuerySettings(querySettings, query)`, which `CopyFrom`s into a new object. Safe because of how it is used, not because the type is immutable; it is a mutable POCO.

**Query-capability flags and property allowlists are enforced at runtime, not just advertised.** `FilterEnabled`/`OrderByEnabled`/`SelectEnabled`/`ExpandEnabled`/`CountEnabled` (all default `false`) and `FilterProperties`/`OrderByProperties`/`SelectProperties`/`ExpandProperties` gate the `GetQueryable`, `GetAll`, and Priority-1 collection paths, plus `$select`/`$expand` on `GetById`: a disabled option in the request returns `400` (`UnsupportedQueryOption`) - `400` and not the `501` of the sigil rule below, because the service implements the option and this resource switched it off, which is not §9.3.1's *"functionality not implemented"*; a non-allowlisted property returns `400` (`InvalidQueryOption`) via the EDM's model-bound `NotFilterable`/`NotSortable`/`NotSelectable`/`NotExpandable` annotations. `$expand` is also implemented on the single-entity `GetById` route (reuses the collection expansion pipeline). Every read route additionally rejects any `$`-prefixed option it does not implement at all - see the next paragraph, which supersedes the closed name lists this sentence used to enumerate. **One exception to the allowlists, and it is not a bug in the enforcement (#401): a dynamic (open-type) property is not in the EDM, so it carries no `NotFilterable`/`NotSortable`/`NotSelectable` annotation and is not gated at all** - `Microsoft.AspNetCore.OData` behaves identically. Do not read the allowlists as a security boundary over a model with an open complex type; `docs/open-types.md` has the measured matrix, and `OpenTypeAllowlistBypassTests` pins it. **The allowlists are scoped per CLR model type, not per entity set, and that is now enforced at startup (#458).** `EntitySetProfile.VisitModelBuilder` applies them via `entityType.Filter/OrderBy/Select/Expand`, and `entityType` is the shared per-CLR-type `EntityTypeConfiguration<TModel>`; `ModelBoundQuerySettings` is keyed by type while OhData's configuration surface is keyed by entity set, so two profiles over one model type **unioned** their allowlists and each set silently accepted what the other allowed - **measured for all four options, in both registration orders**, with responses byte-identical to the correctly-gated case. **Per-entity-set model-bound settings do not exist**: in `Microsoft.OData.ModelBuilder` 2.x the fluent `Filter`/`OrderBy`/`Select`/`Expand`/`Count`/`Page` API is declared only on `StructuralTypeConfiguration<T>` and `PropertyConfiguration` (`EntitySetConfiguration`/`NavigationSourceConfiguration` expose bindings, `EntityType`, `Name`, `ClrType`, `VocabularyTermConfigurations` and nothing else), every `GetModelBoundQuerySettings` overload in `Microsoft.AspNetCore.OData` resolves off an `IEdmStructuredType` (optionally plus an `IEdmProperty`) rather than a navigation source, and the capability-vocabulary annotations that *can* sit on an entity set are never read by the query validators - metadata-only advertisement. So `ModelBoundAllowlists.Validate` throws `InvalidOperationException` from `MapOhData()` on a divergent pair, mirroring `IgnoredPropertyJsonOptions.BuildIgnoredPropertyMap`'s `Ignore()` check. It compares the **literal arrays handed to the model builder** - recorded at the four call sites, post EDM-name resolution and post navigation merge - because that array *is* the shared state; re-deriving from the raw profile allowlists would both miss and invent divergences. Not a conflict: two unset (permissive) allowlists, a sibling whose capability flag is off (it makes no call, and its own requests die at the flag gate), an `AdvancedConfigure` override (ejects before the call sites), or a separate registration (its own `ODataConventionModelBuilder`). `SiblingEntitySetAllowlistTests` pins all of it, including that `WidgetProfile`/`QueryableWidgetProfile` still co-register.

**An unrecognized or unimplemented `$`-prefixed option is REFUSED with `501` on every read route, by the sigil rather than by a name list (#359/#380/#353).** Part 1 §11.2.5 - *"If a data service does not support a system query option, it MUST fail any request that contains the unsupported option"* - Minimal item 7. Three separate closed lists used to answer this and between them left most of the surface unexamined: four names on the collection GETs (`$apply`/`$compute`/`$index`/`$deltatoken`), seven on the navigation route, and **nothing at all** on `GetById`, on `/{Set}/$count`, or on the navigation `/$count`. **Measured on `3781681`**: `?$unknown`, `?$slect`, `?$fliter`, `?$expandx` and a top-level `?$levels` were all `200` on every collection route - and echoed verbatim into the `@odata.nextLink` the server itself generated; `GET /Set(1)?$filter=…` was `200` with the entity and the filter dropped (a client reasonably concludes it was applied); `GET /Set/$count?$search=alpha` was `200` with the **unfiltered** total while the sibling collection route honoured the same option. **`FindUnsupportedSystemQueryOption` is the one matcher**, consulted by sixteen route shapes - the three collection GETs, `/{Set}/$count`, `GetById`, **both branches** of the navigation route, its `/$count`, the #313 continuation (whose own inline `$`-sigil loop was the precedent and which now shares this one instead of carrying a copy, #467's "one site, N consumers" rule), the six operation routes (four bound, two unbound), and (#560) the two structural-property READ routes. Three wordings ride on it and only three: the generic *"The query option '$x' is not supported."* - **byte-identical to the message the four names have carried since 1.0.0**, because generalising a rule must not re-word the cases it already covered - and the navigation route's two, one per branch, each naming what that branch actually accepts.

**`501` OR `400`: `501` IS "CAN'T", `400` IS "WON'T".** An earlier revision of this change answered `400` everywhere, reasoning from §11.2.5's status advice being a SHOULD. That reading does not survive two other clauses: **§9.3.1** is a MUST - *"If the client requests functionality not implemented by the OData Service, the service MUST respond with 501 Not Implemented and the response body SHOULD describe the functionality not implemented"* - and **§13.1.1 item 7** puts that same `501` inside the **Minimal Conformance MUST list**, which this project claims. So every sigil refusal is `501`, and `400` now means one specific thing. **The test is mechanical: could any setting on the profile make this same request succeed on this same route? Yes -> `400` ("won't"). No -> `501` ("can't").** `501`: an unrecognized `$`-name; `$apply`/`$compute`/`$index`/`$deltatoken` (implemented nowhere); an option implemented on OTHER routes but not the one addressed; and the two flag-INDEPENDENT structural refusals (`GetAll`'s `$filter`/`$orderby`, and the `/$count` GetAll fallback's `$filter`), which no profile setting turns on. `400`: a capability flag left false, a property allowlist rejection, `$search` on a route that HAS a `$search` leg but no configured handler, everything #402 owns (a malformed or empty option VALUE), and an out-of-range value (`MaxTop`, `MaxExpandTop`). **`$search` splits on that test and is the worked example**: no `Search` handler is `400` on the collection GETs (the route invokes one when configured) and `501` on `/$count`/`GetById` (no `$search` leg exists there at all). **A consequence worth stating so nobody "fixes" it: the SAME option can be `501` on one entity set and `400` on another**, decided by which read handler the profile supplies - `$filter` is `501` on a `GetAll`-backed set (no `IQueryable`, so the framework CANNOT filter it under any configuration) and `400` on a `GetQueryable`-backed set with `FilterEnabled = false` (it can, and the adopter chose not to expose it). Correct rather than inconsistent: conformance is per-RESOURCE, and the two answers tell a client genuinely different things - *"no configuration of this endpoint will ever do that"* versus *"this endpoint could, and is not offering it"*. **BREAKING, and the largest wire change on the branch**: `$apply`/`$compute`/`$index`/`$deltatoken` answered `400 UnsupportedQueryOption` from 1.0.0 through 1.6.0 and answer `501` now. The error CODE and the message BYTES are deliberately unchanged on every route (§9.3.1's *"body SHOULD describe"* is already satisfied by text naming the option), so a client matching on the envelope keeps working and only status-code branching moves - `ErrorEnvelopeFidelityTests` pins those bytes across the change. One condition still produces one envelope; what moved is which envelope, not how many.

**The navigation route is ONE template with TWO handlers, and gating them with one set was a defect of exactly the kind #380 names.** `GET /{Set}({key})/{Nav}` is mapped once and branches on `NavigationRouteDefinition.IsCollection`. Every option it applies is applied inside the collection branch - `$select` in `BuildNavEnvelope`, `$orderby`/`$skip`/`$top`/`$count` in the branch body - while the single-valued branch (`HasOptional`/`HasRequired`) returns `ODataEntityNode(...)` and reads nothing off the query string. **Measured**: `?$select=Name` served the full entity, `?$top=1`/`?$orderby=Name`/`?$count=true` were `200` and ignored, i.e. #380's own sentence - *"known, implemented-elsewhere options being silently dropped on a route that does not implement them"* - one route over, and `GET /Set(1)?$orderby=X` a `400` beside `GET /Set(1)/Owner?$orderby=X` a `200`. `s_navSingleImplementedOptions` is `$format` alone. Refused rather than taught `$select`: this rule is about refusing what is not implemented, and `$select` there needs the projection, the allowlist validation and the `@odata.context` projection suffix `ODataEntityResult` carries and `ODataEntityNode` does not. The set is chosen from the **startup-captured** `navIsCollection`, so the message describes the branch the request will actually reach.

**The operation routes carry #359's `@odata.nextLink` half, and nothing else did.** `TryApplyOperationCollectionPaging` calls `BuildNextPageLinkWithSkip`, which copies the **whole** incoming query string, and #357/#543 gave that route a `nextLink` in this same release while it had no option gate at all. **Measured** on `MaxTop = 2`: `GET /odata/SqOps/TopRated?$unknown=evil` -> `200` with `"@odata.nextLink": ".../TopRated?%24unknown=evil&%24skip=2"`, and `?$apply=...` -> `200` + `nextLink` where the sibling collection route says `400` - byte for byte #359's evidence block. `s_boundOperationImplementedOptions` is `$top`/`$skip`/`$format`; `s_unboundOperationImplementedOptions` is `$format` alone (no collection branch, no `MaxTop` bound, no continuation there). **`$top`/`$skip` are listed UNCONDITIONALLY**, not derived from `BoundOperationDefinition.ReturnType` the way `AddBoundOperationPagingMetadata`'s `TopSkipSupported` is, and the asymmetry is the point: the ceiling is applied in the RUNTIME collection branch (#357 decision 2 - a `Task<object>` handler returning a `List<TModel>` must not be a way around it), so such a route really can emit a `$skip=N` link, and deriving the set from the declared type would make the server refuse a link it had just issued. Where the result is not a collection they are accepted no-ops - the same ANSWER the two `/$count` routes give them, reached by a different road (there §11.2.9 requires them to be present and ignored; here they are real on the collection shape and the declared type cannot tell the route which shape it will get). An operation's own parameters are non-`$` keys and are never examined. The gate runs **before** parameter binding and before the handler delegate, so a refused ACTION provably mutates nothing.

**Three properties of the rule, each of which would be a defect if changed.** (1) **The sigil, not a name list.** Part 2 §5.2 reserves `$` for system options, so a non-`$` key is a *custom* option and is untouched (`ohdata-skiptoken`, #360's continuation offset, is deliberately spelled without one), and a `@`-prefixed parameter alias (§5.3) likewise. A `$`-name is refused whether or not any OData version defines it: fail-closed, so a future system option cannot quietly start being dropped. (2) **`OrdinalIgnoreCase`, which is ALIGNMENT and not leniency.** `ODataQueryOptions.IsSystemQueryOption` lowercases the name before comparing whenever the URI resolver enables case-insensitivity, which is the default (`ODataQueryOptions.cs:283` for the comment, `:284-287` for the branch it guards, `:289-290` for the lowercasing), so `$Select`/`$TOP` are applied today and stay applied. #359 reported *"`$Select` is applied while `$slect` is ignored and neither is rejected"* as one inconsistency; it is resolved by rejecting `$slect`, **never** by starting to reject `$Select`. The change *is* a deliberate divergence from MS in the other direction - its own `BuildQueryOptions` carries `default: // we don't throw if we can't recognize the query` (`:1061`) - and §11.2.5's MUST is what outweighs `feedback_align_with_msodata_conventions` here. MS's `IsSystemQueryOption` (`:172-198`) recognizes **thirteen** names and `$index` is **not** among them, so nothing here should read as "MS knows `$index`"; it is refused by the sigil like `$unknown`. **This `OrdinalIgnoreCase` is itself a behaviour change on one route**: the #313 continuation's own loop compared `Ordinal`, so `$SKIP`/`$FORMAT` were `400` there and are honoured now - the only direction in which this change makes the server more accepting, pinned by `MixedCaseSkipAndFormat_AreHonoured_NotRejected`. (3) **The set is per route and the sets differ** - and on ONE route it is per PROFILE (#475): the Priority-1 collection GET hands the whole `ODataQueryOptions` to the profile, so the framework cannot know which options are honoured and asks instead (`HonouredQueryOptions`, defaulting to what `ApplyTo` applies). That default excludes `$search`, because `SearchQueryOption.ApplyTo` returns the query untouched without an `ISearchBinder` (*"If the developer doesn't provide the search binder, let's ignore the $search clause"*) - so a P1 profile that merely calls `ApplyTo` used to answer `200` with the FULL collection to a client that asked for a subset, undetectably (an unfiltered result is indistinguishable from a search matching everything). §11.2.5's MUST outweighs aligning with MS here, exactly as it did for the sigil rule itself. The rest of the sentence still holds: `$filter` is implemented on a collection GET and meaningless on `GetById`; `$skiptoken` is honoured on the `GetQueryable` path and was never read on `GetAll` (#201 continues that one with `$skip`), so it is accepted on one and refused on the other. A recognized-but-not-implemented-here name and an unrecognized one share **one** code, because the client's remedy is identical; a second code would distinguish nothing actionable.

**`$format` is in every set and must stay there** - not a data option: §11.2.10 negotiation is implemented once on the group filter wrapping the whole surface, never reaches a route handler, and cannot change a row; an unsupported *value* is still rejected there. **A `/$count` route's implemented set is decided by §11.2.9, which partitions the system query options into exactly two classes and specifies the answer for each.** Verbatim: the count MUST be *"of items matching the request after applying any `$filter` or `$search`"*, and *"MUST NOT be affected by `$top`, `$skip`, `$orderby`, or `$expand`"*. So: an option that AFFECTS the count (`$filter`, `$search`) is applied where the route can and **refused** where it cannot - ignoring one would answer a wrong number under a `200`, which is #353's defect; an option the clause says MUST NOT affect it (`$top`/`$skip`/`$orderby`/`$expand`) is **accepted and IGNORED**, because under §13.1.1 item 7's disjunction (*"either follow the specification or return 501 ... for any unsupported functionality"*) ignoring it IS following the specification; anything outside the clause (`$apply`, `$compute`, `$index`, `$deltatoken`, `$skiptoken`, `$count`, any unrecognized `$`-name) is refused as everywhere else. `s_countRouteImplementedOptions` is therefore `$filter` + `$top`/`$skip`/`$orderby`/`$expand`/`$select` + `$format`; `s_navCountImplementedOptions` is the same **minus `$filter`**, because that handler invokes the navigation delegate and counts the result, so it can apply neither `$filter` nor `$search` and refuses both. **A previous revision refused all five of `$top`/`$skip`/`$orderby`/`$select`/`$expand` here, asserting in the code that §11.2.9 "mandates nothing either way". The clause had not been consulted; it names four of those five.** That refusal was reverted before shipping - the options behave exactly as they did from 1.0.0 through 1.6.0 and no wire change reached a release. **`$select` is accepted-and-ignored by ruling**: §11.2.9's MUST-NOT sentence does not name it, but the positive half is exhaustive about what moves the number (*"items matching the request"*), and `$select` changes an item's SHAPE, never its membership - the body is a bare `text/plain` scalar besides. Refusing it alone among the five options a grid URL carries would be the unprincipled split the revert removed. **`$format` is accepted-and-ignored by ruling too, and it is the OPPOSITE error, so the array says so**: §11.2.9 states content negotiation *"is not allowed"* on this segment, so the entry cannot mean "negotiated here" as it does everywhere else - it means "not refused". Refusing it was rejected on three grounds - the clause binds the CLIENT and prescribes no server response; `$format` IS implemented service-wide, so `501` would be false while the `400` arm needs a capability flag this condition has none of; and the group filter already answers `400 UnsupportedFormat` for a non-JSON `$format` BEFORE the route runs, so refusing here would give one disallowed option two envelopes (`$format=xml` -> `400`, `$format=json` -> `501`). **`Accept: application/xml` used to `406` here and does NOT any more (#580)**, reversing the ruling this sentence carried - *"§11.2.9 forbids the CLIENT to negotiate, not the server to decline a media type the client refused (RFC 9110 §12.5.1)"*. Defensible in isolation, but it was never checked against `Microsoft.AspNetCore.OData`, which settles it the other way: `ODataCountMediaTypeMapping` matches every `/$count` path at quality **1** and `ODataOutputFormatter.CanWriteResult` then OVERRIDES the content type (*"If a media mapping was found, use that and override the value specified by the controller"*), so MS never negotiates on this segment and never `406`s. §11.2.9 is the SPECIFIC rule over minimal item 5.1's general *"MUST conform to the semantics [of] Accept ... or fail the request"*, and this is the direction that un-breaks a working client rather than breaking one. `$format` moves with it - the clause names both in one sentence, so refusing one while ignoring the other would give a single disallowed act two answers; `$format=xml` on `/$count` was `400 UnsupportedFormat` and is now `200 text/plain`. The negotiation filter skips the segment entirely rather than widening its producible list, so nothing else changes: an ordinary read still `406`s a client that refuses JSON. **This AGREES with `Microsoft.AspNetCore.OData`, and the agreement is load-bearing**: verified against the vendored source at `a05e1ad0` (9.5.0-7), `ODataQueryOptions`' constructor synthesises `Count = "true"` for any path ending in `/$count` (`ODataQueryOptions.cs:1072-1084`), so `ApplyTo`'s `Request.IsCountRequest()` early return (`:425-429`) always fires - before the `$orderby`/`$skip`/`$top` block and before `SelectExpand` - and MS ignores all five. **`Microsoft.OData.Client` DEPENDS on it**: it translates `LongCount()` by appending `/$count` to the query string it has ALREADY built and strips nothing, so `q.OrderBy(...).LongCount()`, `q.Take(n).LongCount()` and `q.Skip(n).LongCount()` all send the option along - measured against 8.4.4, and refusing them broke standard pagination for the industry-standard OData client rather than merely a hand-built grid URL. `MsODataClientIntegrationTests`' `Count_*` cases pin every one of those shapes through the real client, which is the coverage whose absence let the narrowing pass a full green suite. The bound-OPERATION routes reach the same accepted-no-op answer for `$top`/`$skip` by a different road: there the option really can be real on the collection shape and the route cannot know at startup which shape a `Task<object>` handler will return, so refusing them would refuse a link the server itself issued. **`OhDataQueryOptionsMetadata.TopSkipSupported` stays `false` on the entity-set `/$count`** - the field means "this route HONOURS this option", and §11.2.9 requires the opposite, so documenting a parameter that provably cannot change the response would be the advertise-vs-serve mismatch #467 exists to remove; the nav `/$count` carries no `OhDataQueryOptionsMetadata` at all. **`GetById`'s zero-cost no-option path is intact**: the check reads query-string KEYS only - no parsing, no `ODataQueryOptions` - and returns on `Request.Query.Count == 0` before touching anything, so a request with no query string allocates nothing new on the hottest read route. **#359's nextLink half needed no separate fix on the routes that were already gated, and needed exactly the operation gate on the ones that were not** - see the operation paragraph above; on a gated route, once the option is refused no link is built at all (`Collection_UnrecognizedOption_IsNeverEchoedIntoANextLink`, against a control on the same fixture that does emit one). Riding along, **two routes changed error CODE AND STATUS**: `GET /{Set}({key})?$select=…&$skiptoken=` and `GET /{Set}/$count?$skiptoken=` answered `400 InvalidQueryOption` from #402's construction guard and now answer `501 UnsupportedQueryOption`, because neither implements `$skiptoken` and it is refused by name before any option object is built - strictly better, since the old message implied a non-empty value would have worked. #402's guarantee is untouched and still exercised end-to-end on the three collection routes. **Deliberate residuals, three of them.** (1) The structural-property WRITE routes (`PUT`/`PATCH`/`DELETE /{Set}({key})/{Prop}`), the service document and `$metadata` still ignore every query option - measured, `GET /odata?$unknown=1` -> `200` - and none of them generates a link, so none carries #359's echo. `docs/query-options.md` names them so its table is not read as the whole URL surface. The writes are ungated *consistently with the entity writes* (`PUT`/`PATCH`/`DELETE /{Set}({key})`, also ungated), so query options are ignored the same way across every write route (the split is along the verb: `GET …/{Prop}?$unknown=1` is `501` while `PATCH …/{Prop}?$unknown=1` is `200`). **The property READS were in this list and are not any more (#560)**: they were the one residual that produced exactly the split this rule exists to remove - `GET /Widgets(1)?$filter=…` -> `501` beside `GET /Widgets(1)/Name?$filter=…` -> `200` with the filter dropped, measured on both the `/{Prop}` and `/{Prop}/$value` routes for every option probed. Their set is `$format` alone: the handler goes from the property accessor straight to the envelope and reads no option, so `$select`/`$expand` are refused there although `GetById` implements them - the `s_navSingleImplementedOptions` situation exactly, one route over. The gate runs **before** the `/$value` complex-property `400`, so the answer does not depend on which property was addressed. (2) The `GetAll` route answers `InvalidQueryOption` rather than `UnsupportedQueryOption` for an *empty-valued* unimplemented option (`?$skiptoken=`) because `TryBuildQueryOptions` runs before the gate there - a pre-existing asymmetry `$apply=` has had since #196, not one this change introduced. (3) **The one thing that WAS honoured before and is refused now**: a Priority-1 profile reading a `$`-prefixed option of its own off `options.Request.Query` (a shape #465's note endorses) never sees the request. Remedy is to spell it without the `$`, which Part 2 §5.2 requires of a custom query option anyway. `UnrecognizedSystemQueryOptionTests` pins every gated route in both directions, and `BareExpandContinuationFailClosedTests.MixedCaseSkipAndFormat_AreHonoured_NotRejected` pins the one acceptance widening.
