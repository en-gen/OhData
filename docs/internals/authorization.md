# Authorization

Read this when touching authorization configuration, per-operation rules, or auth composition across navigations.

**Authorization is declared per profile.** `RequireAuthorization()` / `RequireRoles()` on a profile applies the same auth requirement to every route for that entity set. `ConfigureAuthorization(...)` narrows that per operation category - `Read`/`Create`/`Update`/`Delete`/`Invoke`, plus the `Writes` and `All` selectors and a named `Invoke(name, ...)` - and `.RequireResource()` adds ASP.NET Core resource-based authorization against the `{key}` entity. Evaluation is entirely ASP.NET Core's; profiles store plain policy/role/claim names.

**Three auth seams compose into a quiet fail-open; two are closed, the third is documented (#487).** No single one was an undocumented bypass - `docs/authorization.md` was candid about all three. The finding is the composition, and the absence of any startup signal. All three were **confirmed by measurement** before anything changed.

**(1) Unbound operations had no per-operation authorization at all, and no way to acquire one.** `MapUnboundOperations` took no auth configuration; they are mapped on the outer group, so no profile's `RequireAuthorization()`/`RequireRoles()`/`ConfigureAuthorization(...)` reaches them. **Measured** on a registration whose only profile declares `RequireAuthorization()`: `GET /odata/{Set}` -> `401`, `POST /odata/Mutate` -> `204` **with the handler executed**, `GET /odata/Peek` -> `200` with its body. This is the seam where a warning alone would have been wrong: the docs' own remedy is "apply group auth", which also covers `$metadata`, so a developer who wanted a *gated* unbound operation beside anonymous schema discovery had no expressible configuration and a warning with no opt-out. So the **capability was built** - `AddFunction`/`AddAction` take an optional `authorize` lambda over the same `ICategoryAuthorizationBuilder` `ConfigureAuthorization` uses, and all four overloads funnel through one `AddUnboundOperation` so #468's name check and #498's signature check cannot drift between the authorized and unauthorized spellings. `RequireResource()` is **refused at the call site**: Layer B evaluates against the entity loaded from a `{key}` segment and an unbound operation has neither key nor entity set, so the rule could only ever be a silent no-op - the exact fail-open shape the overload exists to remove. `AllowAnonymous()` there deliberately does **not** emit `AllowAnonymousAttribute`: it means "I am not adding a requirement", never "I am removing the host's", so an unbound operation cannot open seam 3.

**(2) A `ConfigureAuthorization` category with no rule fails OPEN, silently.** **Measured** on the migration shape `.Read(r => r.RequireAuthenticatedUser()).Writes(w => w.RequireAuthenticatedUser())` - which reads as a refinement of `RequireAuthorization()` and is a **widening**: the collection `GET` answered `401` while `POST /{Set}/{Action}` and `POST /{Set}({key})/{Action}` both answered `204` with the handler executed. The identical surface under the legacy `RequireAuthorization()` answered `401`. Made loud, not changed.

**(3) A category-level `.AllowAnonymous()` overrides a host-applied group requirement - UNCHANGED and UNWARNED, deliberately.** Confirmed, and confirmed to be **ASP.NET Core's own `AllowAnonymousAttribute` semantics rather than OhData's**: a control test containing no OhData at all - a plain `MapGroup` with `RequireAuthorization()` applied *after* its routes - serves the `.AllowAnonymous()` endpoint `200` while its sibling answers `401`, whichever order the two were applied in. Not warned about because `.AllowAnonymous()` is the ONLY way to express a deliberate public hole in an otherwise-gated surface, so a warning would fire on correct configuration with no silencer - the failure mode #440 and #481 both establish as worse than no warning. `docs/authorization.md` gains the section that owns the composition, and the "Global auth" section's claim that a group requirement covers every route in the group is narrowed: it is a backstop for routes nobody has an opinion about, not a floor.

**The diagnostic runs from an `IEndpointConventionBuilder.Finally` convention, and it has to.** `MapOhData()` returns the group and the host applies `RequireAuthorization()` to it *afterwards* - the mitigation the docs recommend for exactly these routes - so at map time a route with no rule of its own is indistinguishable from one about to inherit that backstop, and warning inside `MapAll` would fire on the correct configuration. `Finally` runs after every convention on the endpoint, the host's included. **Measured** on .NET 10.0.11: a `Finally` registered before `group.RequireAuthorization()` observes that requirement's `IAuthorizeData` on every endpoint, including endpoints under a nested `MapGroup("")` - which is how every entity-set route is mapped. It can run more than once per endpoint, so `AttachAnonymousRouteAudit` dedupes on `OhDataAnonymousRouteAudit.Key`; one warning per unbound operation and per (entity set, category), never per route. `ApplyOperationAuth`'s "no rule" branch and `ApplyUnboundOperationAuth` attach the audit metadata, so all the static reasoning stays where the route is mapped and the `Finally` only asks "did anything authorize this in the end". A `Require*` anywhere on the profile (for a category) or anywhere in the registration (for an unbound operation) is the **intent gate** - a service that is simply public is never reported, and an explicit `AllowAnonymous()` never reaches the audit because it produces a non-null rule. **Firing scope across the repo's own seven test projects: emissions come only from single-purpose auth fixtures that deliberately configure one category; the TestBench and all six other projects are silent, and no test outside `Issue487AuthSeamTests` changed.** (A "46 emissions / 24 distinct subjects" figure stood here and is **withdrawn** - it is not reproducible from source and no test pins it, which this repo's measurement-provenance rule does not permit. Restore it only with a test that asserts it.) `ApplyAuthRequirements` is the one endpoint-gate replay, shared by `ApplyOperationAuth` and `MapUnboundOperations` rather than transcribed - the two authorize the same `AuthRequirement` list. **No request-path behaviour changed anywhere**; the whole fix is a diagnostic plus one opt-in capability.

**A named `Invoke` auth rule is matched case-insensitively and must resolve, or startup throws (#525).** `ResolveOperationRule` compared `OperationAuthRule.BoundOperationName` with `StringComparison.Ordinal` while every route template and operation segment it governs matches case-insensitively, so `ConfigureAuthorization(a => a.Invoke("stamp", …))` against an operation declared `Stamp` matched **nothing**: the rule was discarded in silence and the route fell back to the generic `Invoke` rule — or, with no generic rule, to **no requirement at all**. Fail-OPEN on an authorization rule, with no startup error and no warning. The comparer is `OrdinalIgnoreCase` now, and that alone is **not the fix**: a *misspelled* name evaporates identically and no comparer rescues it, so `MapEntitySet` also refuses any `Invoke(name, …)` rule that resolves to no declared bound operation (`source.BoundFunctions ∪ source.BoundActions`, entity- and collection-level alike), naming the rule and listing the declared operations. Refused rather than warned: there is no configuration in which authorizing a nonexistent operation is meaningful. The startup check uses **the same comparer as the resolution it guards** — a stricter one there would reject exactly the miscased rules the comparer fix just made work, i.e. this bug re-introduced one layer up wearing an exception. Placed **before** the #486 GetById guard, which itself resolves rules by name, so a typo is reported as a typo. `Issue525NamedInvokeAuthRuleTests` pins both halves plus the generic-rule-fallback direction.

**Two named `Invoke` rules resolving to ONE operation are refused at startup (#546).** #525's `OrdinalIgnoreCase` is correct, but `ResolveOperationRule` keeps last-write-wins, so two rules differing only in case now collapse onto each other and **the declaration order decides whether the operation is protected**: `.Invoke("Stamp", RequireRole("admin")).Invoke("stamp", AllowAnonymous())` answered `200` anonymously while the reverse order answered `401`, both starting cleanly under #525's new validation. The first order was deterministically PROTECTED under the pre-#525 `Ordinal` comparer, so #525 fixed a fail-open and created one - which its own check could not see, because it asks only *"does this name resolve to a declared operation?"* and both members of a colliding pair do. `MapEntitySet` now throws `InvalidOperationException` naming both spellings and the operation, **including for two identically spelled rules** (same mechanism, same consequence; case only changes how easy the pair is to spot). Grouped by the declared operation each rule resolves to, under the **same comparer `ResolveOperationRule` uses** - a second, independently derived comparison would reject a different set of configurations than the one that actually collapses at runtime, which is #525's own reasoning. **Generic `Invoke(...)` rules are deliberately unaffected**: `generic = rule` is last-write-wins by design there, as for every category selector, and `All(...)` then `Invoke(...)` is a documented refinement idiom. BREAKING in the security direction - an app in this state is running under an authorization rule it did not choose, and there is no configuration in which two rules for one operation are meaningful.

**It also does not COMPOSE ACROSS A NAVIGATION, and that is a warning rather than a gate (#481/#368).** There are exactly two authorization-state reads in `OhDataEndpointFactory` (`source.Authorization`, `source.OperationAuthorization`) and both are on the profile being mapped, so every navigation-family route and every `$expand` call site runs under the **declaring** set's rule; the target set's own profile is never consulted. **Measured across 19 route shapes**: with an admin-gated child set and an anonymous parent declaring a navigation into it, the nav `GET`, its `/$count`, all four `$ref` shapes, the nav-`POST` create route and `$expand` (delegate, batch and pushdown) all succeeded anonymously — and `$ref` `POST`/`PUT`/`DELETE` and nav-`POST` **executed the write**, so this was never read-only disclosure. **Enforcement was refused** (owner ruling): `Microsoft.AspNetCore.OData` behaves identically and cannot do otherwise — verified against its source, it contains **no authorization code at all** and routes the navigation action onto the *parent's* controller — so fail-closed would be a divergence from OData norms; it would also break the idiomatic scoped-navigation shape with no opt-out flag to point at, is undefined where sibling sets share one EDM type (#458), and is precisely the retroactive poisoning #293's frozen Model B forbids one concern over. So `WarnNavigationTargetAuthorization` emits one `Warning` per (declaring set, navigation, stricter target set) at `MapOhData()`, `WarnWireShapeIsFlat` being the precedent for shape and tone. **Three targeting rules, each a probe result, each silently wrong if changed**: (1) the target is the **EDM navigation property's own target type** resolved through `ResolveProfilesForEdmType` — NOT `ChildEntitySetName` (the `batchGetAll` overload never sets it; probe case 7 leaked through exactly that) and NOT `NavItemType` (`HasOptional`/`HasRequired` never set it); (2) it fires on the **DECLARED** navigation, not the routed one — probe B-1, a bare `HasMany(x => x.Children)` with no handler and no route, still leaks via `$expand`, while an **undeclared** convention-discovered navigation (probe B-2) is deliberately silent because #440/#446 made it reachable by nothing and `WarnUndeclaredConventionNavigations` already names it, which is why the two checks partition the EDM's navigations on the *same* `NavigationPropertyNames` test; (3) the **union**, never the binding — per the decision at `ResolveProfilesForEdmType`, exactly one exposing set yields a real `IEdmEntitySet` (and a one-element union, so they agree) while two-or-more and none both yield an `EdmUnknownEntitySet` placeholder, so a binding-only check stops working the moment an unrelated second set is registered over the child type. The comparison is **per operation category** (`Read` always — `$expand` needs no route; `Create` only with a `post` handler; `Update` only with `$ref` handlers; `Delete`/`Invoke` never, no nav route is mapped in either) because a target declaring `Read(AllowAnonymous)` + `Writes(RequireRole)` is an ordinary shape that a read-only navigation loses nothing to, and a warning that fires on correct configuration gets ignored. `NavigationTargetAuthorization` normalizes both authorization models to one token vocabulary, sorting role and claim-value lists so a re-ordered declaration is not reported as a difference. **Measured over the repo's own seven test projects: zero emissions from any pre-existing fixture.** `docs/authorization.md`'s *"there's no bypass"* sentence is narrowed to the declaring profile's own rule in the same commit.
