# Error Handling and Fault Classification

Read this when touching exception handling, the OData error envelope, provider-fault classification, or response serialization.

**A provider fault is classified by WHEN it was raised, not by what it was (#494).** The three `$expand`-pushdown execution sites (the count-carrier materialization, the #305 Include fallback, and the ordinary pushed-query materialization) wrapped a whole `ToArray()` in `catch (ex is InvalidOperationException or NotSupportedException or ODataException)` and answered `400 InvalidQueryOption` - *"could not be translated by the underlying data provider"* - logging the real exception at **`Debug`**. The rationale, recorded in those comments **and pinned by `ExpandPushdownExceptionClassificationTests`**, was that a real infrastructure fault could only arrive as a `DbException` subclass or a `TimeoutException`. **That taxonomy is false**, and the counterexamples are the ones that matter under load: SqlClient reports connection-pool exhaustion as a plain `InvalidOperationException` (*"Timeout expired … max pool size was reached"*) from `SqlConnection.Open`, raised at enumeration inside those exact `try` blocks; **`ObjectDisposedException` derives from `InvalidOperationException`**, so a disposed `DbContext` matched; and EF's *"a second operation was started on this context instance"* is one too. Under any of them an `$expand` request answered **`400` - telling client retry logic not to retry** - while the same request without `$expand` correctly `500`d, and at `Debug` the operator saw a spike of client errors and no server-side signal at all. **The type cannot separate the populations, so it is no longer asked to.** `TranslateThenMaterialize` splits the provider's **translation** phase from its **materialization** phase: `IQueryable<T>.GetEnumerator()` is what compiles the query (`EntityQueryProvider.Execute`) and the connection is not opened until the first `MoveNext()`. **Verified** on EF Core 10 / .NET 10.0.11 against SQLite - an untranslatable `Where` throws `InvalidOperationException` out of `GetEnumerator()`, enumerator never created. Only the translation window (the query **factory** too, so `ApplyIncludeFallback`'s reflective `Include` construction stays a 400 - it deliberately unwraps its own `TargetInvocationException` so the real type reaches the classifier) yields the 400, now logged at **`Warning`** to match `TryBuildQueryOptions`/`BadKeyError`; everything from the first row onward propagates untouched to the group filter's logged 500. `ObjectDisposedException` is excluded from the translation window as well - *"the object is gone"* is never a statement about the client's query. A provider that translated lazily inside `MoveNext` would surface translation failures as 500 rather than 400: loud either way, never a false *"retry is pointless"*, and EF Core does not do it. **The expression-*construction*-time catch in `TryBuildProjectionInit` keeps its type list** and is not an inconsistency: no database I/O happens inside it, so there is no materialization phase to separate translation from. The pinning test's expectation was **inverted, not deleted** - its injection point (`ReaderExecuting`) was always the materialization phase, which is exactly what made the suite assert the defect as correct behaviour - and the "IOE ⇒ 400" branch is now covered by a **real** EF translation failure (`MlAuthorUntranslatableProfile`, a client-side method in a `Where` over the existing `MlAuthor` fixture) instead of an injected one.

**#662 applied that same split to the ROOT read, and the hard half was ATTRIBUTION, not detection.** #494 reached the three `$expand` execution sites and stopped there, so one condition produced two answers - `400` through `$expand`, `500` without it. Measured: a profile whose `GetQueryable` projects a DTO and serves its navigation with `batchGetAll` (so the navigation is not in the projected query) answered **500** to `?$filter=Tags/any(...)`, while the sibling that projects the navigation eagerly answered `200`. `MaterializeRootQuery` now wraps the `GetQueryable` collection read; `CountRootQuery` wraps the inline `$count=true` count and the `GetQueryable` arm of `/$count`.

**`TheClientsOptionsAreToBlame` carries three conditions and every one was a confirmed defect when absent** - the first cut had only the middle one and an adversarial review refuted it, so do not "simplify" any of them away. (1) **The provider must be EF Core.** The whole split rests on `GetEnumerator()` compiling without doing I/O, which is an EF Core property and NOT a contract of `IQueryable`; #494 established it for the `$expand` sites, which are gated on an EF provider (`ResolveEfCoreAssembly`), whereas `GetQueryable` accepts any queryable and the repo's own docs and fixtures use non-EF ones. Measured against a provider that executes on `GetEnumerator()`: a transient, retryable remote fault answered `400` *"simplify the expression"* - #494's inversion verbatim - and `CanCompile` re-executed the query against the already-failing backend, so the failure path amplified load on a degraded dependency. (2) **The framework must have composed the option**, not merely received it in the request. This is what removes the two **Priority-1** sites from the change: there the PROFILE applies the whole `ODataQueryOptions`, so the framework composed nothing it could attribute a failure to, and they keep their `500`. It also dissolves an `$orderby` gate defect that existed only on the P1 `/$count` arm, which counts the profile's already-`ApplyTo`'d queryable. (3) **The unmodified source must compile.** Presence is not attribution: measured, `?$filter=Name eq 'Hammer'` - a translatable comparison over a real column - answered `400` on a profile whose OWN `Where` was the untranslatable clause, telling the client to simplify a predicate that was not the problem, and making the same permanent misconfiguration answer `400` or `500` depending on whether an option happened to be present.

**The count probe lives in the CATCH BODY, never the exception filter.** A filter runs before the failed frames unwind, so probing there re-enters the provider mid-unwind (an undocumented dependency on EF internals, in the last place anyone would look), and the CLR silently swallows anything the filter itself throws - the probe's own faults would vanish without a log line. `RootTranslationFailure` also takes the provider's OWN exception from both callers rather than unwrapping one and not the other, which had been discarding EF's outer *"The LINQ expression … could not be translated"* message on the count path. `Issue662RootFilterTranslationTests` pins all of it - the defect, the server-fault control, the broken-source control, the non-EF control and the Priority-1 residual; the two guard conditions are ablation-verified (removing the EF gate fails 2, removing the source probe fails 8).

**Unhandled handler exceptions get the OData error envelope, not an empty 500.** A group-level endpoint filter (registered alongside the `OData-Version`/`OData-MaxVersion` filters in `OhDataEndpointFactory.MapAll`) catches any exception a handler throws - as opposed to an `ODataError` result a handler deliberately returns - and converts it into `500` + `{"error":{"code":"InternalServerError",...}}`, logging the real exception (never leaking its message/stack trace to the client). Two exclusions: startup-time validation exceptions (`MapOhData()` throws those once, before any request is served), and **a cancellation on a request the client actually aborted** - left to ASP.NET Core's own client-disconnect handling, because there is no response left to write.

**It is NOT the outermost group filter, and the comment that said so was false (#496 finding 3).** The #200 observability filter is added first and therefore wraps it, so the guarantee register's *"Registered as the outermost group filter (added first)"* was wrong on both halves. What the filter really covers is every route handler plus every filter registered **after** it - the #203 body-limit filter, the `$format`/`Accept` filter, the `OData-MaxVersion` filter. What escapes it: an exception raised in the observability filter's own body (`DescribeOhDataEndpoint`, activity/tag setup, the instrument calls) or in its `Response.OnCompleted` callback. That is **accepted rather than closed**: making the claim true means putting the exception filter outermost, which moves its `LogError` outside the request's `Activity` and loses trace correlation on the single most important log line the framework emits - a worse trade for framework-only code that does no I/O and runs no user code. Riding along, **the `OData-Version: 4.0` header moved to the outermost filter** (#496 finding 2): it was written by the `$format`/`Accept` filter, fourth of five, so the #203 `Content-Length` fast-reject `413` - registered third - short-circuited above it and shipped with no `OData-Version` at all (measured), which §8.1.5 requires on every response. Its placement in the first-registered filter is load-bearing; `Issue496ErrorHandlingTests` pins it from the outside by asserting the header on that 413.

**A read route's narrow catches used to claim USER code's exceptions, and now cannot (#496 finding 4).** Two clauses, one shape, both wider than the condition their message describes. (1) Every keyed route wraps its whole body in `catch (FormatException) -> BadKeyError`, so a handler throwing `FormatException` from its own code (a downstream parse, a `decimal.Parse` on a CSV column) was answered `400 "Invalid key format for <set>: '<key>'"` for a request whose key had parsed one line earlier. Fixed **structurally**: `ODataKeyParser.Parse` has exactly one throw site and it now raises `ODataKeyFormatException : FormatException`, which is the only thing the eighteen clauses catch. (2) Every read route's `catch (Microsoft.OData.ODataException)` answers `400 InvalidQueryOption` with `ex.Message` **verbatim** - a targeted bypass of the no-disclosure rule for one exception type - and that try also encloses handler invocation, so a handler proxying a downstream OData service turned a dependency fault into a client-blamed 400 carrying its own message. That catch **cannot** be narrowed by scope: `Microsoft.AspNetCore.OData` parses most option values lazily, and the framework itself deliberately THROWS `ODataException` from inside `ApplyCollectionPipelineAsync` (`NestedWindowRejection`, `EnsureWithinExpandCeiling`) precisely because these clauses convert it to a 400. So the marking goes on **user code**, not on the framework's option-touching calls - the direction matters, because enumerating framework calls fails toward turning a legitimate 400 into a 500 (a missed one), while marking user code fails toward the status quo (a missed seam behaves as before). `AsHandlerFault` wraps the seam in `HandlerFaultException`; the group filter unwraps it for the log. It takes the already-started `Task` rather than a `Func` so nothing is allocated on the hottest routes, which is safe only because every `Invoke*` member returns a Task that already carries a synchronously-thrown exception - for seven of them because they are `async` methods, which capture a throwing lambda into the returned Task. **Two members have had to earn that property explicitly.** `InvokeDeleteAsync` was a plain forwarder until #581 made it `async`; a synchronously-throwing `Delete` escaped while the arguments were still being evaluated, before any wrapper around the call could see it (measured: #581's mapping fired on all seven other seams and not on `Delete`). `InvokeGetQueryableAsync` is **not** `async` since #653 - its delegate is synchronous, so there is nothing to await - and it therefore wraps the invocation in `try`/`catch` returning `Task.FromException`. **Measured which consequence that prevents rather than assuming it**: with a plain forwarder the generic 500 envelope still appears (the throw is inside the route handler, so the group filter catches it), and what breaks is `WithExceptionMapping`, which never sees the exception - so a `ConfigureExceptions` rule that should answer `403` answers `500`. Since `ConfigureExceptions` is #653's documented replacement for returning a rejection from that seam, that is the regression `Issue653SyncGetQueryableTests` pins. Both fixture shapes are in the suite, so the invariant is pinned rather than assumed. Marked seams: the five read routes' `InvokeGetODataQueryableAsync`/`InvokeGetQueryableAsync`/`InvokeGetAllAsync`/`InvokeSearchAsync`/`InvokeGetByIdAsync`, `GetById`'s ETag selector, `ApplyCollectionPipelineAsync`'s whole ETag stage (one try per page, not one closure per row), and `ExpandLevelAsync`'s `Handler`/`BatchHandler` calls. **Deliberate residual**: the *enumeration* of a deferred `IQueryable` a handler returned runs later, inside `EvaluateQueryWithArithmeticFaultGuard`, and is not marked - user LINQ raising `ODataException` from a provider callback would still be a 400.

**A `Post` handler returning `null` is a logged 500, not a 400 (#496 finding 1).** It answered `400 {"code":"BadRequest","message":"Post handler returned null."}` - a server-side contract violation reported as a client error, with the server's own handler named back to the client, and the only 4xx null policy in the framework (`GetAll` -> 200 with an empty collection, `GetById`/`PUT`/`PATCH` -> 404, a bound operation -> 204). It throws now, which is the same invariant-assertion shape `DeltaFactory` uses for a `false` from `TrySetPropertyValue`: after the framework's own checks a null here means the handler broke its contract, so the group filter's logged 500 is the correct and only honest answer. A profile that means to reject a create deliberately has to do it BEFORE the handler - `Post` is typed `Task<TModel?>`, as is every other entity-set handler delegate, so it cannot return an `IResult` and there is no "return an `ODataError` from the handler" idiom here. Use a `Create` authorization rule, `RequestBodyNullabilityValidationEnabled`, or throw (the same 500).

**That second exclusion is a statement about the REQUEST, not about the exception type (#493).** The filter condition used to be `ex is not OperationCanceledException` alone, so the whole OCE family escaped whether or not anything had been aborted - and `TaskCanceledException` is what `HttpClient` throws on **its own timeout**, i.e. a server-side dependency fault wearing cancellation's clothes. Blast radius: every handler that awaits `HttpClient`, a database driver, or any API using linked or internal tokens. **Measured** on the pre-fix tree, a `GetAll` throwing `TaskCanceledException` on a request that was never aborted: HTTP `500` with an **empty body**, no envelope, and **no OhData log at all** - only Kestrel's - which is exactly the failure mode this filter exists to eliminate, on arguably the most common outbound-dependency failure there is. The condition now also asks `ctx.HttpContext.RequestAborted.IsCancellationRequested`, and `TryBuildQueryOptions`' catch got the same refinement (lower stakes - no handler runs inside its try - but the asymmetry would invite the bug back). `CancellationTests` still pins the genuine-abort path unchanged; `ErrorEnvelopeFidelityTests` pins the new one. Until this fix the sentence above ("catches any exception a handler throws") was simply false for that family.

**That filter only covers what runs *inside* the pipeline, so nothing may defer serialization (#396).** A minimal-API `IResult` is executed by `RequestDelegateFactory` **after** the endpoint-filter chain has unwound, so a fault while the result executes is outside the filter's `try` — and the status line and headers are already committed. Measured on the pre-fix tree: a bound function whose result faults during serialization logged `Request finished … - 200` and shipped a truncated body, with nothing logged. That is worse than an envelope-less 500 — a success status with a malformed body defeats client-side error handling completely — and it is generic to any throwing converter, cyclic graph, or faulting getter. The invariant is therefore **every route materializes its response body before returning**: most already did, because they build a `JsonObject`/`JsonArray` in the handler (`SerializeBounded` / `ODataEntityNode` / `ApplyCollectionPipelineAsync` / `BuildNavEnvelope`), so all user code runs where the filter can see it and executing a materialized `JsonNode` afterwards cannot re-enter it. The four routes that handed a **raw CLR graph** to `Results.Json` now go through `PreRenderedJson`, which serializes to UTF-8 bytes in the handler and returns a `Utf8JsonHttpResult` that only writes: the two unbound function/action results, `WrapBoundOpResult`'s final branch (a non-`TModel`, non-Edm-primitive DTO — its other two branches emit a materialized `JsonArray` or an Edm primitive), and the structural-property read envelope (whose `value` is a complex property's whole sub-graph) (#713: that envelope is pre-rendered through `EnvelopeOptions`, like `WrapBoundOpResult`'s, so a host `DictionaryKeyPolicy` cannot rename its keys; the same clearing applies to a dictionary-valued complex property's own keys, which is a residual of reusing the one rule). Byte-identical by construction — same declared `TValue`, so the same `JsonTypeInfo` resolves; do **not** "simplify" those call sites to pass `object`. `Content-Length` is now explicit. **Measured cost** (`OperationResultBufferingBenchmarks`, against a free `Stream.Null` write): a small DTO — the common shape — gets *faster* (0.74×, the async state machine dominates a tiny payload); 189 KB costs +18%, 9.4 MB +74%, all of it the extra full-payload `byte[]`. A pooled `Utf8JsonWriter` beats every arm (0.66×/0.97×/1.43×, no LOH traffic) and is deliberately **not** shipped: it requires transcribing the `JsonSerializerOptions`→`JsonWriterOptions` mapping by hand, and one wrong or missing member changes the response bytes. The residual this paragraph used to declare - *"only a host-registered converter for a **primitive** type could fault there"* - was **under-scoped in two directions, and #495 closed both.**

**Every OData envelope built as a `Dictionary<string, ...>` was serialized at execute time under the HOST's `HttpJsonOptions` (#495).** Two separate consequences, and the non-faulting one is the worse of the pair. (1) **Shape.** System.Text.Json applies `DictionaryKeyPolicy` to dictionary keys, and OhData's envelope keys - `error`/`code`/`message`/`target`, `@odata.context`/`value`/`@odata.count`/`@odata.nextLink` - are contractual identifiers, not names a policy may rewrite. **Measured** with the host's `DictionaryKeyPolicy` at `SnakeCaseUpper`: `{"ERROR":{"CODE":"NotFound",...}}` on **every** error response the framework produces, and `{"@ODATA.CONTEXT":...,"VALUE":[...]}` on **every collection GET, the service document, and both `WrapBoundOpResult` envelopes** - the collection route being the half #495 itself did not name. It ships a parseable body no OData client can read, under a 200 or a 4xx, with nothing anywhere reporting a problem. (`JsonObject` responses - GetById, the nav-single route - were never affected: STJ writes a node's member names verbatim.) (2) **Fault.** The fault surface is not the primitives; it is any converter matching `string`, `Dictionary<string, object>`, or a primitive. A throwing host `JsonConverter<string>` took the **group filter's own 500 envelope** with it, so the last-resort error path was itself the thing that failed: an empty, envelope-less 500 with no OhData log.

The split is **OhData owns the envelope's names; the host owns value formatting** - #252's division, one level out. Concretely: `ODataError` and the service document, whose content is *entirely* framework-generated, pre-render through `PreRenderedJson` with `_frameworkEnvelopeSerializerOptions`, a standalone host-free instance; `WrapBoundOpResult`'s collection and Edm-primitive branches pre-render with the registration's own options; and every remaining payload-bearing envelope (the three collection GETs, the nav-collection route, the #313 continuation, the four `$ref` shapes) goes through `ODataEnvelopeResult`, which stays **deferred** (`Results.Json`, no buffering - its `value` is an already-materialized `JsonArray`, so there is no user code left to fault and buffering a whole page would cost for nothing) but passes `EnvelopeOptions(...)`. `EnvelopeOptions` returns the source instance **by reference** when `DictionaryKeyPolicy` is null - i.e. always, on a default host - so no options are copied and no second `JsonTypeInfo` cache is created; only a host that really set one pays. `_frameworkEnvelopeSerializerOptions` sets `Encoder = UnsafeRelaxedJsonEscaping` **explicitly and load-bearingly**: ASP.NET Core's own `Http.Json.JsonOptions` overrides the Web default the same way, and a bare `new JsonSerializerOptions()` is *not* the same bytes (measured: a 404 quoting the requested key went 78 -> 88 bytes, every apostrophe escaped). `ErrorEnvelopeFidelityTests` pins the default-host bytes for all seven shapes, captured pre-fix and pasted verbatim, and pins each defect with a throwing-converter and a key-policy probe. **The remaining residual is now measured rather than assumed, and it is not the one #396 named.** A `JsonNode` does **not** re-enter host converters when it is written: `JsonValuePrimitive<T>.WriteTo` goes through `JsonMetadataServices`' own converter, not `options.Converters` - verified directly on .NET 10.0.11 with a throwing `JsonConverter<string>` and a throwing `JsonConverter<int>` over a `JsonObject` carrying both, neither of which fired. So #396's original claim about nodes was right, and every `Results.Ok(JsonNode)` route is genuinely immune. What a host converter *can* still reach at execute time is the **framework's own** members of the deferred envelopes - the `@odata.context` / `@odata.nextLink` / `@odata.id` strings and the `@odata.count` number, which are `object`-typed dictionary values and so resolve a converter. A throwing one there is an envelope-less 500 (reachable only when the payload itself contains no string to fault on first, e.g. an empty page); a merely reformatting one rewrites a framework-generated URL. Left open deliberately: closing it means either buffering every collection page or allocating a second `JsonSerializerOptions` per registration unconditionally, and neither is worth it for a surface this size.
