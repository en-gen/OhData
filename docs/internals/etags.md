# ETags

Read this when touching ETag generation, If-Match/If-None-Match preconditions, or CheckETagAsync.

**ETags.** Set `GetETag = model => "..."` to opt in. Adds `ETag` response header to GET/POST/PUT/PATCH. `CheckETagAsync` is the single precondition gate, and it now covers **every state-changing route the framework owns and can key** (#478): entity PUT/PATCH/DELETE, the structural-property writes, all three `$ref` link-management routes (`POST`/`PUT`/`DELETE /{Set}({key})/{Nav}/$ref`), the navigation-POST create route and (#566) the entity-bound ACTION route (`POST /{Set}({key})/{Action}`). Read the route list literally — the four `$ref`/nav-POST routes previously **discarded** `If-Match` and performed the write with a 204/201, which was a lost update on relationship state. **Collection-bound and unbound actions remain excluded, and that half survives on its own reasoning** - neither has a `{key}` segment or an addressed entity, so there is nothing to load an entity tag from, and §11.5.4.1's *"or collection of entities"* half would need a collection ETag the framework does not compute. The ENTITY-bound action was excluded too until #566, defended by saying the action-invocation resource *"has no representation and so no entity tag"*, citing Protocol §11.5.4; **that phrase appears nowhere in Part 1** (`grep -ic "no representation"` returns 0), and four clauses say the opposite - §11.4.1.1 is a MUST for *"a Data Modification Request **or Action Request**"*, §8.2.4 names Action Requests in both its `428` and its `412` sentences, §8.3.1 says the ETag may be used *"in updating, deleting, **or invoking the action bound to the entity**"*, and §11.5.4.1 tells the client to send `If-Match` for exactly this case. Measured before the fix: `POST /v1/Movies(3)/Rate` with a stale `If-Match` answered `200` and MUTATED the entity while `PATCH /v1/Movies(3)` carrying the same header answered `412`. Do not re-derive the withdrawn justification. The gate fires **before** the body is read and before the handler delegate runs, so a refused write provably mutates nothing (`ConcurrencyTests` asserts delegate non-execution, not just the status code). It is still **not atomic** — no transaction is opened, so the TOCTOU window between the gate's `GetById` and the delegate's write is unchanged and `docs/etags.md` says so. Comparison follows RFC 9110 §13.2.2 evaluation order: `If-Match` first (**strong** comparison per §13.1.1 — a `W/`-prefixed entry is *dropped*, never unwrapped, so `If-Match: W/"<current>"` is a 412), and `If-None-Match` only when `If-Match` is absent (**weak** comparison per §13.1.2, so `W/"<current>"` *does* match there). `ParseETagList` and `ParseStrongETagList` are the two readers and are **not** interchangeable; both delegate to `SplitETagList`, which detects the `W/` sentinel case-insensitively on purpose — leniency there is the fail-closed direction for both headers. A non-`*` `If-None-Match` on a write is now honoured (412 on match); the separate `AllowUpsert` `If-None-Match: *` create-guard on PUT stays where it is because it must work **without** `UseETag`, which `CheckETagAsync` requires.
