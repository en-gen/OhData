# EDM, Metadata and Startup Validation

Read this when changing $metadata, startup validation, operation signature checks, AdvancedConfigure, or Ignore() behaviour.

**Advertise only what the route serves; the EDM is validated at startup (#465/#467/#468).** Three separate claims the server did not honour, one shape. (1) The **Priority-1** collection route appended `", $search"` to its OpenAPI description whenever the profile had a `Search` handler and never invoked it — there is no `$search` leg in that route body at all. Invoking is **not** coherent with the Priority-1 contract: on the `GetQueryable`/`GetAll` paths `Search` *replaces the source* and the framework applies the remaining options on top, which it can because it owns the pipeline there; Priority-1 hands the whole `ODataQueryOptions` to the profile, so there is no seam to feed a search-derived source into, and honouring it would mean bypassing the profile — dropping `$filter`/`$orderby` on exactly the requests carrying `$search` (the same defect one option over) and routing around any row-level scoping the handler applies, which is a common reason to choose Priority-1. So the advertisement is gone and `GetODataQueryable` + `Search` is **refused at startup**; `$search` there is the profile's own business via `options.Search`. (2) **`OhDataQueryOptionsMetadata` fields mean "this route honours this option", never "this route is of kind X"** — it is attached to five route shapes (three collection GETs, `/$count`, GetById) and read by three companion packages, so a field with two meanings produces the same wrong document in all three. `$top`/`$skip` were added on metadata *presence* alone (documented on GetById and `/$count`, both of which drop them) → new `TopSkipSupported` field; `/$count` set `CountEnabled: true` to mean "this route IS a count" while the transformers read "documents the `$count` option" → reduced to the single meaning, `false` there; and `/$count`'s `FilterEnabled` mirrored the profile flag although its GetAll fallback answers `400` for any `$filter` → gated on the source (`countSourceAppliesFilter`), matching the "B1 fix" the sibling collection route already had. **The fix site is `OhDataEndpointFactory`'s metadata attachment, not the transformers** — one site, three consumers, which is why they agree byte-for-byte; keep it that way. (3) `$metadata` emitted `IncludeInServiceDocument="true"` on every unbound **function** import (the `Microsoft.OData.ModelBuilder` default, never set) while the service document was hand-built from `registration.Profiles` and listed entity sets only. For a **parameterized** import that claim is invalid CSDL (§13.6 — it cannot be invoked by name alone); those now clear the flag, parameterless ones keep it and are really listed, and the service document is **derived from the EDM container** so the two generators cannot diverge again. Action imports are never listed (not GET-addressable, no such attribute in CSDL). Riding along: **`EdmValidator.Validate` is now called from `MapOhData()`** — it was called nowhere in the assembly. `CsdlWriter.TryWriteCsdl` does not run these rules and `CsdlReader.TryParse` does not police them either, so an invalid construct reached the wire and broke only consumers that validate (codegen tools). Measured when first wired in: it catches this issue's own violation in four fixtures, **and** the compiler-generated name from `AddFunction` with an un-named lambda (`InvalidName`, `<Method>b__0_1`), which had been shipping invalid `$metadata` silently. That second one is now caught **earlier and better**, at registration: `AddFunction`/`AddAction` validate the resolved name themselves and throw `ArgumentException` naming the parameter and the remedy (pass an explicit `name`), because a generic CSDL-validation failure quoting `<Method>b__0_1` at `MapOhData()` tells a developer neither what caused it nor what to do. **They call `OpenTypeJsonOptions.IsValidDynamicPropertyName` — the shipped validator, never a second transcription of the ABNF**; the whole point of the fast-path/rune-walk oracle relationship recorded above is that a third hand-rolled copy would drift from it. The `*Cached` variant is deliberately not used: its 1024-entry cache memoises per-request dynamic keys on the serialize path, and startup-time operation names would only evict them. `EdmValidator` remains the backstop for what a name check cannot see — the parameterized `IncludeInServiceDocument` violation among them.

**The startup validation set has to track the ROUTE set, and four ways it did not (#492/#416/#486).** One defect, five fix sites, one signature: startup passed silently and the request hit `AmbiguousMatchException` — thrown by **routing, before the group filter**, so a raw 500 with no OData error envelope and a framework exception in the log instead of a configuration problem. (1) The unbound-op-vs-entity-set pass asked `HasGetAll || HasGetQueryable`, enumerating **two of the three** collection-read paths; a Priority-1 profile reports both `false` (its flag lives on `IODataEntitySetEndpointSource`) while `MapEntitySet` registers the route anyway, so `AddFunction(…, "MySet")` beside it made **every collection read of that set** a raw 500. Cured by asking the single question — `IEntitySetEndpointSource.HasCollectionGet`, implemented once on `EntitySetProfile` and phrased as "or this instance implements the Priority-1 interface", so a fourth read path cannot repeat it. (2) Three of the collision checks compared **`Ordinal`** while ASP.NET Core literal-segment matching is case-insensitive — which `OhDataBuilder.Register()`'s own sibling checks already knew and said so in a comment; measured, structural property `Price` + a handler named `price` passed startup and made **both** spellings of the URL ambiguous. All three are `OrdinalIgnoreCase` now. (3) **#416**: an entity-level bound function versus a **navigation route** had no check at all — the structural-property check cannot see it, because `BuildStructuralProperties` subtracts every declared navigation (which is exactly what makes structural and navigation routes disjoint). The new check keys off `NavigationRoutes`, not off which delegate was supplied: `MapEntitySet` maps a GET for **every** entry, including a `post`/`addRef`-only navigation whose GET 404s. A navigation declared with **no** handler is absent from that list, registers nothing, and stays legal — #313's continuation check governs that one once the route exists. #416 asked whether to warn instead, on the theory that an app might rely on whichever route wins; measured, none can — `AmbiguousMatchException` means **neither** endpoint runs, so there is no working configuration to break. (4) Duplicate bound-operation names within one profile were never validated, and the duplicate is ambiguous in the **dispatch** layer too (`BoundFunctions.First(f => f.Name == …)`), so picking a winner fixes neither half. Refused at **bind time**, per (kind, binding level), because `Microsoft.OData.ModelBuilder` rejects a repeated ACTION name itself — earlier, from inside `VisitModelBuilder`, with *"Found more than one action with name 'X'"* and no mention of the profile, the entity set, or the remedy. Riding along, **#486**: the #199 Layer B guard named Read/Update/Delete, three of the **five** categories that reach `AttachResourceFilter` — it also attaches on **Create** (the key-based navigation-POST route) and on **Invoke** (entity-bound operations), and it calls `GetById!.Invoke(...)`, so those two configurations passed startup and then `NullReferenceException`'d on 100% of requests. It fails closed, so nothing was exposed; it is the configuration the guard exists to make unreachable. The collection POST and collection-bound operations are deliberately **excluded** from the widened guard — the former evaluates its Create requirement inline against the deserialized model and the latter has no `{key}` segment, so both are legal without `GetById`.

**An operation handler's signature is validated where it is declared (#498).** Five gaps, each producing either a hostile startup failure or a silently-wrong runtime result where a bind-time refusal naming the operation was available and cheap. (1) A **void-returning FUNCTION** killed `GetEdmModel()` with a raw `ArgumentNullException: 'returnType'` from inside `Microsoft.OData.ModelBuilder` — no OhData message, no operation name — while `BoundOperationDefinition`'s XML doc, `AddUnboundOperationProduces`' comment and `docs/bound-operations.md` all promised 204. CSDL requires a function to declare a return type, so refusing is right; all three claims are now narrowed to **actions**, which really do produce 204. (2) A **non-trailing (or nullable) `CancellationToken`** made the operation unreachable: `AsyncDispatchHelper.SplitCancellationToken` strips only a trailing token by exact type while `RegisterEdmOperation` filtered one out at every position, so `$metadata` declared one parameter list, the route demanded another, and **no value could satisfy it** (there is no string→`CancellationToken` conversion). (3) A handler returning **`IResult`** started fine (`Returns<IResult>` maps the interface into the EDM) and served the result object's own property bag as the 200 body. All three live in `OperationSignatureValidation`, called from the four `Bind*` methods and from `AddFunction`/`AddAction` — one implementation, six call sites, because each rule is a statement about how the dispatcher works and a second transcription would drift from it. Called from `Bind*` rather than from `BoundOperationDefinition.From` so the throw carries the developer's own constructor on the stack: `From` runs inside `VisitModelBuilder`, whose exceptions are wrapped in a generic *"failed to build EDM for profile"*. For the unbound half it fires at `AddFunction`/`AddAction` — i.e. at `AddOhData(...)`, not `MapOhData()` — following #468's deliberate choice for the same reason. (4) **`byte[]`** was declared `Collection(Edm.Byte)` while `WrapBoundOpResult`'s primitive map hits `byte[] → Edm.Binary` first and serves `#Edm.Binary`: a clean advertise-vs-serve mismatch, special-cased the way `string` already was, in **both** copies of `GetCollectionElementType`. (5) `RegisterEdmOperation` formatted an optional parameter's default with `$"{param.DefaultValue}"`, i.e. under `CurrentCulture`, so `decimal maxPrice = 1.5m` rendered as `1,5` in the CSDL on a de-DE server; `InvariantCulture` now, `bool` keeping its explicit lowercase mapping and a null default keeping its pre-existing empty string. **Not** fixed, and tracked separately: a `Dictionary<K,V>` return is still declared `Collection(KeyValuePair<K,V>)` while the wire serves a JSON object — excluding dictionaries from collection inference does not by itself produce a correct EDM (there is no CSDL shape for a map short of an open complex type), so it is a design decision rather than a special case, unlike `byte[]`.

**`AdvancedConfigure` eject hatch.** Overriding `AdvancedConfigure(EntitySetConfiguration<TModel>)` gives full EDM control and disables automatic EDM config. Detected at startup via `MethodInfo.DeclaringType` comparison.

**That eject drops `Ignore()`'s EDM half, and the residue is a value oracle — documented and warned, deliberately not fixed (#489).** `Ignore()` withholds on two levels: the EDM removal rides the `_configurators` pipeline, runtime suppression (routes, wire, PATCH binding) is applied separately from `IgnoredPropertyNames`. `VisitModelBuilder` returns **before** the pipeline runs when the override is present, so the property is back in `$metadata` and query-addressable while the wire still omits it — `$filter` over it answers truthfully one predicate at a time, so the value is never served and still discoverable, and `$metadata` discloses its name and type regardless of which capabilities the override re-enabled. In the ordinary case the EDM removal makes the property indistinguishable from one that never existed (ODL fails with the same *"could not find a property named…"*), so the 400 cannot confirm existence. **Not fixed**, on two grounds: re-imposing `Ignore()` on top of the override defeats the hatch outright, and `HasOptional`/`HasRequired`/`HasMany` ride the same pipeline and stay ejected — a half-ejected pipeline whose membership is decided by consequence severity is a worse contract than the one it replaces. So it takes the `WarnWireShapeIsFlat` shape instead: `WarnIgnoredPropertiesStillInEdm` logs one `Warning` per affected property at `MapOhData()`, naming the entity set, the property and the one-line remedy (`configuration.EntityType.Ignore(...)` inside the override). **Gated on the EDM as built**, not on the mere presence of an override — re-applying the removal by hand is what the docs prescribe, and warning on the *correct* configuration teaches developers to tune the warning out. The query-capability half is deliberately not in the gate (taking the hatch also drops the automatic `Filter()`/`OrderBy()`/`Select()` calls, so a capability added later must not silently un-warn). CLR→EDM name resolution goes through `ODataPropertyNaming`, so a `[JsonPropertyName]`-renamed ignored property is still found. `docs/ignoring-properties.md` carries the security warning and the fix; `docs/architecture.md` cross-references it. `Issue489IgnoreUnderAdvancedConfigureTests` pins the oracle itself as characterization on both sides, the warning's content, and its targeting.
